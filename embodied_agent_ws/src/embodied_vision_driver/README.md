# embodied_vision_driver — 视觉 Driver

> 把「画面里有没有某个东西、在哪一侧」变成一句**可回答的话**，给上层的 Skill 用。

## 🔒 一条不对称的规则（本包的全部理由）

| 情况 | 回答 |
|---|---|
| **找到了** | ✅ **可信**。看到了就是看到了 —— 正面证据不因为画面差而作废 |
| **没找到，且画面质量达标** | ✅ **确认真没有** |
| 没找到，但**画面过糊** | ❌ **「不知道」** —— 不是「没有」 |
| **没有新鲜图像 / 模型没就绪 / 类别不在模型表里** | ❌ **「不知道」** |

**为什么**：2026-10-09 我们发现这台车的相机**出厂就是失焦的**，而当时所有的
"检测结果"都是 **0 个检出** —— 它和"画面里真没东西"**看起来完全一样**。
把前者读成后者，上层就会得出"这里没有目标 / 这地方安全"的结论，
而那正是本项目的铁律一直在防的：**不知道 ≠ 安全**（D-028）。
详见 `docs/DEV_NOTES.md` 坑 43。

同族还有一条：**问一个模型不认识的类别名**（比如问"杯子"而模型只认 `cup`）如果按
"没找到"回答，它会**永远**说"没有那个东西"，而且**永远不会报错** —— 所以那也是「不知道」。

## 用

```bash
ros2 launch embodied_vision_driver vision_driver.launch.py
```

前置：**相机在出图**（厂商 `usb_cam` 在跑）。⚠️ 还有一件本节点管不了、却会让它
整体失效的事：**镜头对焦** —— 手动镜头只有一个清晰距离，用
`tools/focus_assist.py` 对着你要用的那个距离调。

| 接口 | 说明 |
|---|---|
| `/embodied/vision/detections` | 每帧一条：`stamp`（**本节点收到帧的时刻**，不是图像 header 的戳）、`image_quality`、`objects[]`（类别 / 置信度 / 像素框 / `side`） |
| `/embodied/vision/diag` | `Float64MultiArray` = `[推理帧率Hz, 清晰度, 检出数, 模型就绪0/1, 最近一帧龄ms, 累计帧, 丢弃帧]` |
| `~/find_in_view` | `(label, min_score)` → `(valid, found, score, bbox, side, image_quality, detail)`。**先看 `valid`，再看 `found`** |

⚠️ `side` 只是**画面里的左右**（−1 最左 … +1 最右）：**不含距离、不含世界坐标** ——
本机是单目相机，给不出距离（D-017）。

## 模型从哪来

**从厂商 SDK 借**，不改厂商任何文件：

```
~/ros2_ws/src/example/example/yolo_detect/models/26/yolo26n.engine   ← 80 类通用 COCO
```

厂商默认加载的是同一个目录里的 `best_traffic_26`（**6 类交通标志**），
所以他们的视觉 app 在这台车上从来认不出别的东西。类别表**从模型自己读**
（`model.names`），不需要人配 —— 换模型不会出现"名字全错却不报错"（DEV_NOTES 坑 44）。

## 为什么不用厂商那个 `yolo_node`

它能跑，但有两个**静默失效点**（DEV_NOTES 坑 44）：初始化后要等一个**硬编码的
全局服务 `/yolo/start`** 才检测；类别表是**启动参数**、换模型忘了换它就全是错名字。
自己加载没有这两个坑，话题名与语义也归我们 —— 与相机 / 电机 Driver 同一个路子。

## 测试

```bash
cd src/embodied_vision_driver && python3 -m pytest test/ -q
```

判定的全部逻辑在 `vision_query.py`（**纯 Python，不依赖 ROS**），单测把它钉住：
**"糊画面上的没找到"必须是「不知道」** 那一条尤其不能松。
