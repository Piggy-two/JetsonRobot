## 2026-10-07（续）— 语音「唤醒不通」查到根因：**控制串口完全沉默**；并更正三条文档错误

### 做了什么

1. **发现 `enable_setting` 默认 `false`**：`mic_init.launch.py:12` 把它声明为默认 `false`，
   而 `awake_node.py` 里 `switch_mic()` / `set_wakeup_word()` **只在它为真时才调用**
   → **唤醒词从来没有写进过硬件**。
2. **用"只在该分支才有"的副作用定案**：journal 里 `setting wakeup keywords need about 30s`
   **从来没出现过**（坑 14）。
3. **强制打开它（`enable_setting:=true` 单起麦克风栈）→ 卡死在 `switch_mic`**：
   `CircleMic.send()` 的握手等待是 `while True:` **无超时**。27 s 无任何输出，
   进程停在 `do_select`，连 `Wake up word:` 那行日志都没打出来（⇒ 参数确实生效、确实进了分支）。
4. **直接对 `/dev/ring_mic` 做串口探测**：4 种 RTS/DTR 组合下握手**收到 0 字节**；
   再纯监听 **180 s**、每 2 s 补发一次握手（共 90 次）—— **仍然 0 字节**。
5. **确认音频侧是活的**：3 s 采集峰值 6.4% FS、无削顶。
6. **更正三条文档错误**（见下）。
7. **把声音调小**：`Speaker` 由 91%（−5.82 dB）→ 77%（−14.50 dB），用户确认可听清。
8. 恢复厂商栈（`systemctl start start_app_node.service`，`/scan` 回到 10.000 Hz）。

### 为什么这么做（思路）

原文档把卡点定在"唤醒这一环"，依据是一条**看起来很像证据**的话：
「`/awake_node/init_finish` 服务存在 → 该服务建在两次串口握手之后 → 握手成功过」。
**这条推断是错的**：那个服务在 `__init__` **末尾无条件创建**，握手只在条件分支里发生。
于是前一轮把力气花在了发音、音量、解析上 —— 而真正该问的是
「**这个证据是只有走那条路才会有，还是无论如何都会有？**」（**坑 14**）。

第二个思路转折是「**0 字节**」的读法。第一反应是"波特率不对"，但
**波特率错会收到乱码，不会收到什么都没有** —— 采样率不匹配时电平跳变照样被采到，
只是解成垃圾。所以 0 字节说明**这条线收方向根本没有电平活动**（**坑 15**），
结论才能从"配置不对"升级为"**这条线是死的**"。

### 测试结果

| 探测 | 读数 |
|---|---|
| journal 里 `setting wakeup keywords...` | **从未出现** ⇒ 该分支从未执行 |
| `enable_setting:=true` 重启 | **卡死在 `switch_mic`**（27 s 无输出，`do_select`） |
| 握手应答（4 种 RTS/DTR 组合） | **0 字节** |
| 纯监听 180 s / 90 次握手补发 | **0 字节** |
| 调制解调器控制线 CTS/DSR/CD/RI | 全 `False`（⚠️ **弱证据** —— CH340 常不驱动这些线） |
| 音频采集 3 s | ✅ 峰值 6.4% FS、RMS 260、直流 0.13、削顶 0% |

**结论**：唤醒事件走的**就是这条串口**，而它**完全沉默** ⇒
**唤醒在结构上不可能产生**，与唤醒词、音量、发音都无关。

⚠️ **边界（诚实）**：**用户当时没有出声**（现场不便），所以"说了唤醒词串口仍无反应"
这半边的直接证据**尚未取得**；结论建立在"握手被应答"这条**不依赖人说话**的探测上。

### 遇到的问题

三条文档错误，全部更正：

1. ❌「`/awake_node/init_finish` 存在 ⇒ 两次串口握手成功过」
   → 该服务**无条件创建**，不能当证据（坑 14）。
2. ❌「卡点在唤醒/解析/发音」→ 卡点在**更上游：串口不回话**。
3. ⚠️「厂商 ASR 栈正常启动 = 语音硬件通过」→ 那只证明**节点起得来**。

**影响面（本轮新增）**：Safety Runtime（**D-027**）的本地安全指令通路订阅的正是
`/asr_node/voice_words` ⇒ **语音急停词当前也是不可用的**（`~/estop` 服务本身正常）。
这条以前没意识到 —— 它意味着"不经 LLM 的本地安全通路"目前**只有服务入口是活的**。

### 最终结果

- **#25 的根因定为「控制串口完全沉默」**，不再是"卡点未定位"。
- **用户决定暂缓**语音（现场不便说话）与电机真机运动测试（判断后续开发用不上）；
  两者都已在 `PROJECT_STATUS.md` 标为 ⏸️ 并写清**重启条件**。
- **下一步两条候选**（待用户定）：① 物理侧三条观察（指示灯 / CH340 后面接了什么 / 重插复测）；
  ② 若确认硬件不通，**改在 Jetson 上做软件唤醒**（本地 KWS，用已证实可用的采集通路）——
  这更符合 D-006「全本地、不经云端、不经 LLM」。
- `DEV_NOTES.md` 新增 **坑 14 / 坑 15**（无条件创建的证据 / 0 字节 ≠ 波特率错）。

## 2026-10-07 — LiDAR 环境剖面：判明「67% 近场回波」是**外部环境**而非自身结构；顺带修掉新工装自己的墙上钟 bug

### 做了什么

1. **新增验收工装 `tools/lidar_environment_probe.py`** —— 把 LiDAR 的**距离-角度剖面**
   量化下来：按角度分格统计中位/最小距离与点数、画柱状概览，并直接算出
   `path_clear(±30°, 1 m)` 的判据值、贴身回波（< 0.35 m）覆盖的角度区间、
   以及「正前方是否是一个平整面」的 `d·cosθ` 检验。**可 `--json` 存档，用于两次摆位对比。**
2. **现场判定 D-028 留下的悬案**：项目处于"车在另一处摆位"的状态下重测同一张剖面。
3. **修掉工装自己的一个 bug**：初版用 `time.time()`（墙上钟）算采集时长，
   把 `/scan` 的 **10.000 Hz** 算成 **16.85 Hz**（见「遇到的问题」，已记入 `DEV_NOTES.md` 坑 13）。
4. 文档同步：`PROJECT_STATUS.md`（§1 / §4 / §7）、`DECISIONS.md`（D-028 补充）、
   `DEV_NOTES.md`（§1.4 新方法论 / §2 可信度表 / 坑 13 / §4 诚实清单）、`README.md`（tools 索引）。

### 为什么这么做（思路）

D-028 记录的现象是「67% 回波在 0.6 m 以内，成因未定（外部环境 vs 雷达看到自身结构）」。
关键是想清楚**这两种可能在观测上有什么区别** ——

> **自身结构与雷达固连：车挪到哪儿，它都在同样的角度上。
> 环境回波则随摆位而变。**

所以判据**不是"距离多近"**，而是「**换一个摆位再测一次，看回波跟不跟着车走**」。
这条判据的好处是**不要求空旷场地**，只要求"两次摆位不同"——
因此即便现场空间不大，只要两次剖面差异显著，就能定性。

先前的做法（"把车挪到开阔处或吊起来再看"）把"换摆位"和"足够开阔"混在一起了，
其实只需要前者。这一点已写进 `DEV_NOTES.md` §1.4。

### 测试结果

| 项 | 2026-10-06（原地） | **2026-10-07（另一摆位）** |
|---|---|---|
| 近场占比（< 0.6 m） | **67%** | **3.6%** |
| 贴身回波（中位 < 0.35 m） | 有，198°~359° 一整圈 0.10~0.28 m | **完全消失** |
| 前方 ±30° 每帧最近回波（跨帧中位） | 0.244 m | **0.537 m** |
| 前方 ±60° `d·cosθ` | 像 0.25 m 处一个平整面 | std **0.28~0.52 m**（随分格宽度而变），不像单一平整面 |
| `/scan` 速率（独立核对） | 10.00 Hz | **9.998 Hz**（`ros2 topic hz` 同为 10.000） |
| 有效回波比例 / 点数每帧 | 93.5~97.0% / 502~505 | 92.4% / 503（502~504） |

→ **两块近场回波都没跟着车走 ⇒ 判为外部环境。不需要做自身结构回波掩膜。**

⚠️ **但 `path_clear(±30°, 1 m)` 现在仍是 `false`，而且这是正确答案**
—— 车前方 0.54 m 处确实有东西（本次**未清场**，且空间小）。
⚠️ **更严的判别法（原地转 90°，与场地大小无关）本次未做** —— 结论建立在两次摆位对比上。

### 遇到的问题

**新工装第一版把 `/scan` 报成 16.85 Hz。** 同一时刻 `ros2 topic hz /scan` 是 `10.000`，
且它显示的帧间隔 `min 0.096s max 0.104s` 高度均匀 —— **两个读数不可能同时为真，先怀疑自己的工装**。

根因不是雷达，是**墙上钟**：工装用 `time.time()` 算首末帧时间差，而本机**每次开机时钟都会被
timesyncd 恢复、再被 NTP 前拨**（正是已记录在案的 **#24**）→ 墙上钟**不是单调的**，
采集窗口里一次步进就足以把时长算错（帧数是对的，于是速率被算成一个不存在的值）。
改用 `time.monotonic()`，并**直接报帧间隔中位数**。

**教训**：#24 那条坑**不是「`usb_cam` 的毛病」，而是本机时钟的普遍性质** ——
凡是量时间的地方都要先问一句"这钟会不会跳"。本项目已因同一性质踩了两次
（第一次是厂商节点冻结换算基准，这次是我们自己的工装）。

### 最终结果

- D-028 的环境观察**关闭**（判为外部环境），原「自身结构回波剔除」遗留项**据此关闭**。
- 产出一条**比原观察更强**的后续约束：**避障阈值必须在真实部署环境实测标定**
  —— 同一台车两次摆位，近场占比 **3.6% ↔ 67%**，任何拍出来的固定阈值都会被场地否决。
- `DEV_NOTES.md` 新增方法论 §1.4（"跟着走 = 自身的，留在原地 = 环境的"）与坑 13（墙上钟）。
- Phase 0 软件侧仍只剩**语音唤醒（#25）**；硬件侧只剩**急停链路（#22，用户已暂缓）**。

## 2026-10-06（第五轮）— 收相机 Driver 的时间戳尾巴：`pipeline_latency` 标定为 110 ms，并查清「厂商戳陈旧 0.72 s」其实不恒定

### 做了什么

1. **实测标定 `pipeline_latency`**：45 ms（估计值） → **110 ms**，验证残差 ≈ −9 ms。
2. **扩展验收工装 `tools/camera_latency_probe.py`**（三处，都是它本身的缺陷/局限）：
   - `--topic`：原来只测两条写死的话题，无法测**我们自己的输出话题**，也就无法标定；
   - `compressed_brightness()`：原来对 `image_compressed` 是**拿 JPEG 字节流稀疏采样当亮度**，
     那是熵编码数据，与画面亮度没有稳定关系（本轮实测直接得到"亮度几乎没变"的假结论）——
     改为先用 `cv2` 解码；
   - `--repeat` + `--jitter` + 汇总统计：单次事件判读不了（见「遇到的问题」）。
3. **推翻 D-022 的一条推断**：⛔「raw 比 compressed 多出的约 90 ms 是订阅端解析 614 KB 的开销」
   —— 本轮 30 KB 的 compressed 与 614 KB 的 raw **到达时刻只差 8~20 ms**。
4. **把 D-022 里「被排除」的『启动时冻结的时钟换算基准』重新坐实**（见 #24）：
   厂商 `usb_cam` 的 `header.stamp` 陈旧量**不是恒定的 0.72 s**，本轮实测 **338.6 s**。
5. **查清影响面**：只有 `usb_cam` 一个节点受影响（`/scan` −12 ms、`/odom` −12~15 ms、
   `/tf` −57 ms 全部正常）。

### 为什么这么做（思路）

**先问「这个数凭什么可信」，再问「它等于多少」。** `pipeline_latency = 45 ms` 当初的来历是
「≈22.6 Hz 下的一帧」—— 那是个**量纲估计**，不是测量。要标定它，就必须有一个**独立于相机
自己的世界端基准**，于是仍然用 `v4l2` 的 `brightness`（ISP 数字偏移、逐帧立即生效）
当"传感器端打光"。这条方法论在 `DEV_NOTES.md` §1 已经写过，本轮是它的第二次应用。

**标定对象必须是"我们自己的输出"**，不是厂商的原话题 —— 所以工装必须先能测任意话题。
这也是为什么"给工具加个 `--topic`"不是顺手，而是**前提**。

### 测试结果

| 项 | 实测（2026-10-06） |
|---|---|
| 帧周期 T | 44 ms（输出 19 Hz） |
| 内容端到端延迟（compressed 参照 / 我们的 614 KB 输出） | +118 ms / +138 ms（14 次事件均值） |
| 输出戳 − 世界事件（标定前 P=45 / 标定后 P=110） | **+88 ms** / **+13 ms** |
| 厂商戳陈旧量 | **338 565 ms**（抖动 12~17 ms，raw 与 compressed 一致） |
| `/scan`、`/odom`、`/tf` 的戳 − 实时 | −12 ms、−12~15 ms、−57 ms（**全部正常**） |

标定式：`新值 = 原值 + 「戳−下发」均值 − T/2` = 45 + 88 − 22 = 111 → 取 **110 ms**。

### 遇到的问题

**1. 单次事件的判读值稳定得"太好"，反而说明它不可信。**

一开始按固定间隔重复 14 次，每次读到「戳 − 下发」几乎**挤在同一个数上**（+61 / +59 / +60 …）。
原因不是精度高，而是**事件相对帧栅格的相位被锁住了**：这类测量天生带 ±T/2 的量化误差，
而量化误差**只有在相位随机时才服从均匀分布**；相位固定时它退化成一个固定偏置，
与真正的传输延迟混在一起分不开。修法是给事件间隔加**随机抖动**，加完之后标准差
涨到 **14 ms**，正落在 `U(0,44)` 的理论值 `T/√12` = 12.7 ms 上 —— 这才是相位被打散的证据。
（已记为 `DEV_NOTES.md` **坑 7**。）

**2. 厂商戳的陈旧量在两次会话之间从 0.72 s 变成了 338.6 s。**

顺着这条线查到本机**没有可用 RTC**：**每次开机** timesyncd 先按「上次记录的陈旧时间」恢复
时钟（本次 `17:26:02`），随后 NTP 再**前拨约 339 s**；而 `usb_cam` 恰在这两者之间启动，
并冻结了一个 `(实时−单调)` 换算基准 → 它发出的一切时间戳永久落后。多组独立数字吻合：
陈旧量 338.6 s ≈ 本次开机时钟前拨量 ≈339 s；`who -b` 的 17:25 与 `(实时−单调)` 推出的
17:31:29 差 6.5 min。

⚠️ 这也意味着 **D-022 当年对这条假设的"排除"是错的**，而错因很具体：当时的否证是
「服务启动至今 `(实时−单调)` 仅变化约 0.04 s」—— 那个测量**只在"本次会话之内"成立**，
**结构上看不见两次会话之间发生的跳变**。已在 D-022 表格里显式撤回，并记入 #24。

### 最终结果

- `pipeline_latency` 由估计值变为**标定值 110 ms**（`config/camera_driver.yaml` 与代码默认值同改），
  已验证：标定后「输出戳 − 世界事件」均值 +13 ms，相对估计曝光时刻的残差 ≈ −9 ms。
- 工装具备**可复现的重标能力**；`pipeline_latency` 随负载变化这一性质已明确写进 D-023 / #23 / DEV_NOTES §4。
- `corrected` 策略（只用自己的实时钟）被本轮全部证据**进一步支持** —— 它既不依赖那个
  0.72 s / 338.6 s 的偏移，也不依赖偏移的机制。
- ⚠️ 当轮仍未闭合：TF 朝向实机目视校验（场地画面失焦，需重新布置）—— **同日第六轮已闭合，见下一条**。

## 2026-10-06（第十三轮）— LiDAR Primitive：做查询原语而不是收口；顺带发现一个环境条件

（用户不在场，要求"后面一直继续我不在场可以进行的开发"。）

### 做了什么

1. 新建包 `embodied_lidar_driver`，在厂商 `/scan` 之上提供**查询原语**：
   `/embodied/lidar/front`（每帧更新的前方扇区最近回波）、
   `~/sector_min_range`、`~/path_clear`。
2. 接口包 `embodied_skills_interfaces` 增加 `SectorMinRange` / `PathClear` 两个 `.srv`。
3. 几何逻辑抽到纯 Python 的 `scan_query.py`，配 **30 项离线单测**。
4. **对真实雷达做"独立重算"交叉验证**。
5. 顺带**查出一个环境条件**（见下），它会影响将来所有避障阈值。

### 为什么这么做（思路）

**先判断这个包该做什么，而不是先写代码。** 前两个 Driver（相机 D-023、电机 D-025）做的都是
"**收口**"—— 厂商给的东西不可信，我们在自己这层修好。所以动手前先问了一句：
厂商的 `/scan` 可信吗？查下来是**可信的**（10 Hz、360°、`frame_id` 与 TF 都对）。
**那就没有"收口"可做。** 如果照着前两个的样子硬做一个"LiDAR Driver"，
只会多一层没有理由存在的转发。

**于是换了个问题：上层到底要问什么？** 不是"这一圈点云长什么样"，而是
「**我这个方向、这个距离内，有没有东西**」。这才是原语。而且一件事只有做成原语
才能被共用 —— 下面那个坑就是证据。

**躲开一个"不单测几乎必然会写错"的坑。** LD19 的 `/scan` 是 `angle_min=0` 起、逆时针、
`angle_max=2π`。所以「正前方 ±30°」在数据里**不是一个连续的下标区间**，
而是 **330°~360°** 加 **0°~30°** 两段。任何"按角度找到起点、切一段数组"的写法都会
**静默漏掉一半扇区**，而且漏掉的恰好是最该看见的那一半。所以实现一律按**最短有符号角差**
判定，并为它专门写了单测（把最近回波放在接缝另一侧，验证确实被算进来）。
**如果让每个上层各自去切数组，这个错会被重复犯很多次。**

**把"不知道"和"安全"分开。** `path_clear` 有两种"没有东西"的情况，
它们的可信度完全不同：扫描新鲜但扇区内无回波（**假设**空旷，返回 `range=-1` 如实标注），
以及**扫描根本没有**（**什么都不知道**）。后者绝不能报 `clear=true` ——
那等于在"传感器挂了"的时候告诉上层"前面没东西"。这条单列进了决策。

### 测试结果

**单测 30 项全过。**

**对真实雷达的独立重算交叉验证**（自己订阅 `/scan`、自己算一遍再比）：

| 检查 | 结果 |
|---|---|
| `/embodied/lidar/front` 速率 | **9.999 Hz**（与 `/scan` 一致） |
| 流式输出 vs 独立重算 | **32/32 帧**对得上 |
| `sector_min_range` | **逐位一致**：`valid=True, 0.244 m, 83 点` |
| 宽扇区（120°，**跨接缝**） | **逐位一致**：`0.129 m / 167 点` |
| 无扫描数据时 `path_clear` | ✅ `clear=False`（不知道 ≠ 安全） |
| 无扫描数据时 `sector_min_range` | ✅ `valid=False` |

### 遇到的问题

**验证脚本第一次报"29 帧里 27 帧一致"，看起来像有 bug。** 我没有直接放过，也没有直接
把阈值放宽，而是先想清楚可能是**话题配对错开一帧**（前端消息与服务不同步），
再改成"允许与最近几帧的重算之一对上"。改完 32/32 全对。
**这一步值得写下来**：如果把"放宽判据直到它过"当成解法，就会把一个真实 bug 一起放过去；
正确做法是**先给不一致一个可证伪的解释，再据此改判据**。

**顺带查出一个环境条件（不是缺陷，但重要）：** 当前 504 个点里 **340 个（67%）在 0.6 m 以内**，
距离随角度**平滑变化**（0° 时 0.251 m、30° 时 0.294、60° 时 0.544 —— 呈 `d/cos θ`，
像是正前方约 0.25 m 处有一个平整面），另有 198°~359° 一圈 0.10~0.28 m。
**后果：`path_clear(±30°, 1 m)` 恒为 false**，这个原语在当前摆位下给不出有意义的"通畅"。
**成因未定**（外部环境 vs 雷达看到机器人自身结构），我用现有手段**分不出来**，
需要人到场（挪到开阔处或吊起来再看这几段在不在）。**这条会影响将来所有避障阈值的选择**，
所以没有含糊过去，如实记进了 D-028 与 §7。

### 最终结果

- Phase 1 的三个 Driver（相机 / 电机 / LiDAR）**至此齐了**。
- 决策 **D-028**；接口包多了两个可复用的 `.srv`。
- 遗留：环境条件待人工确认；未做自身结构回波剔除；未接闭环。

## 2026-10-06（第十二轮）— Safety Runtime 补上最后一道：**Motor Driver 挂了自动接管**

（承接第十一轮。用户要求"后面一直继续我不在场可以进行的开发"。）

### 做了什么

1. 新增停更看门狗（纯逻辑 `watchdog.py`，配 8 项单测）。
2. Safety Runtime 监视 Motor Driver 的状态话题：**停更 > 2 s 即自动急停并接管发零**。
3. **Motor Driver 未恢复时拒绝 `~/release`**。

### 为什么这么做（思路）

**上一轮只解决了"已经知道要停"，还有一种更隐蔽的没解决。** 第十一轮做完，
我以为"急停"这件事已经闭环了。但顺着失效模式往下捋，还剩最后一个**没有任何防线**的：

    如果 Motor Driver 进程**自己死了**呢？

它死了不会报错、不会发事件、没人转告。而"持续发零"这件事**只在它里面** ——
于是底盘会保持最后一条速度一直跑下去。本机没有物理急停（#22），
**没有任何东西能拦住它**。这不是"再补一个功能"，这是把最坏情况补上。

**看门狗和"零速通道"是一对，缺一不可**：通道解决"知道要停时怎么停"，
看门狗解决"根本没人知道要停"。

**`~/release` 的行为是这一轮里我最想清楚的一个决定。** 一开始写的是"直接解除"，
但推一遍后果会发现：Motor Driver 还死着的时候解除，等于本节点停止发零 ——
而那时**没有别人在发零**，底盘立刻跑飞。所以必须**拒绝**。
而且不能靠"解除后又被看门狗立刻重新锁存"来兜底：那在现象上就是一个
"点了没反应"的按钮，人只会以为坏了。**明确拒绝 + 说清原因**才是可用的设计。

### 测试结果

**单测 45 项全过**（`estop` 37 + `watchdog` 8）。

**端到端 12/12 通过**（用假状态话题模拟"Motor Driver 进程死掉"）：

| 场景 | 实测 |
|---|---|
| **从未见过** Motor Driver | ✅ **不报失联**（假警报会淹掉真警报） |
| 在线（喂 20 Hz 状态） | ✅ 不报警，且**没向 `/cmd_vel` 发过任何东西** |
| **状态停更 3.5 s**（阈值 2.0 s） | ✅ **自动锁存** + 事件 `motor_driver_lost` + 发零（**非零帧数 0**） |
| 未恢复时调 `~/release` | ✅ **被拒绝**，理由写明 |
| 恢复后调 `~/release` | ✅ 成功；解除后 1 s 内 0 帧 |

### 遇到的问题

本轮没有再踩新坑。前几轮的教训（坑 9 launch 参数、坑 10/11 并发）已经变成写法习惯了：
**launch 参数先声明再传、纯逻辑先写单测再接线**。
值得记一笔的是 —— **收益是复利的**：把坑写成检查项，后面每一轮都在省时间。

### 最终结果

- Safety Runtime 现在覆盖**三条**：本地安全指令、独立零速通道、**对上游死亡的自动接管**。
- 加上前一轮，本机**没有物理急停**（#22）这个最要命的约束，终于有了三层软件防线：
  Motor Driver 的锁存（D-025）→ Control Skill 的中止（D-026）→ **Safety Runtime 的独立通道 + 看门狗（D-027）**，
  且后两者**不依赖于前者的存活**。
- 遗留：本版不含避障 / 限速 / Agent 侧 Skill 网关；真机未验证。

## 2026-10-06（第十一轮）— Safety Runtime 第一版：安全指令本地化 + **独立零速通道**

（用户不在场，要求"后面一直继续我不在场可以进行的开发"。）

### 做了什么

1. 新建包 `embodied_safety_runtime`，落地项目的核心主张
   **`Safety > Control > Skill > Agent`** 的第一个**落点**。
2. **本地安全指令通路**（D-006 / D-024 决策 3）：订阅厂商**离线** ASR 的文本，
   **在本节点内**匹配安全词，**不经过 LLM、不经过厂商 `voice_control_*` 节点**。
3. **独立零速通道**：锁存期间自己直接向 `/cmd_vel` @10 Hz 发零，
   **不依赖 Motor Driver 存活**。
4. 判定逻辑抽到纯 Python 的 `estop.py`，配 **37 项离线单测**。

### 为什么这么做（思路）

**先把"散着的安全"收成一处。** 此前"停"这件事分在三处：Motor Driver 有锁存停车、
Control Skill 有 `~/stop`、厂商有它自己那条（还漏着，见 #26）。**没有一处能回答
"最终由谁说了算"。** 项目的核心主张写了这么久，该有个落点了。

**关键在于"独立"两个字，而它的依据是已有的实测。** 我本来想的是"急停就调 Motor Driver 的
`~/stop` 就行了"，但顺着 D-020/D-025 的证据链推下去会发现一个洞：底盘没有指令超时保护，
所以"停止发布 ≠ 停车"；而**"持续发零"这件事目前只在 Motor Driver 里** ——
**它自己挂了就没人发零了**，底盘会保持最后一条速度一直跑。
所以急停通道**必须不依赖它**。这不是"多写一个 publisher"，而是把最坏情况补上。

**顺带得到了一个很强的性质**：本节点**唯一的发布语句就是 `publish(Twist())`** ——
它在**结构上**不可能发出非零速度。这比"我们保证只发零"强得多，因为它是代码形状决定的。

**做取舍的地方要留痕。** 安全词用**整句匹配**而不是子串匹配，这是本次唯一一个
"两种做法都会错、只是错法不同"的决定：子串匹配会让厂商词表里的 `停止追踪` / `stop tracking`
**全部误触发整机急停**，把安全通路变成一个不可信的按钮；整句匹配则可能漏掉没想到的说法。
我把这个取舍连同**两种错法各自的后果**一起写进了 `estop.py` 的 docstring 和 D-027 ——
因为后人重看这段代码时，第一反应很可能是"为什么不用 `in`？"。

### 测试结果

**单测 37 项全过**（含"功能词不该触发整机急停"那一组）。

**端到端实测 14/14 通过 —— 且全程 Motor Driver 未启动**（这正是要验的）：

| 检查 | 结果 |
|---|---|
| `go forward` / **`停止追踪`** / `唤醒成功(wake-up-success)` | ✅ 都不触发，且**没向 `/cmd_vel` 发过任何东西** |
| 本地识别到 `停下`（走真实解析路径，不是直接调服务） | ✅ 立刻锁存，事件 `estop_triggered:voice:停下` |
| 独立零速通道 | ✅ 约 **10 Hz** 持续发零；**非零帧数 = 0** |
| 锁存期间说别的 | ✅ 不解除 |
| `~/release` | ✅ 显式解除后才停发零；解除后 1 s 内 **0 帧** |
| `~/estop` 服务 | ✅ 也能触发 |

### 遇到的问题

本轮没有踩到新坑 —— 因为前两轮（坑 9 `ros2 launch` 未声明参数被静默忽略、
坑 10/11 回调组与共享状态）的教训直接用在写法上了：launch 参数**先声明再传**，
安全词判定**先写单测再接线**。
**这本身是个正反馈**：把坑写成可复用的检查项，下一轮就会少踩一次。

### 最终结果

- 项目的 Safety 主张第一次有了**代码落点**；决策 **D-027**。
- **独立零速通道**这一条补上了此前没人负责的最坏情况（Motor Driver 自己挂了）。
- 遗留：本版**不含**避障 / 限速 / **对 Motor Driver 存活性的监视**（"它挂了就自动接管"
  是这条通道的自然延伸，目前只做到"锁存时才发零"）；真机未验证
  （本节点只会发零，风险为零，但"发零真能让底盘停下"只有真机运动测试能确认）。

## 2026-10-06（第十轮）— Phase 2 首个 Control Skill：`move_relative` / `rotate` / `stop`，并用**速度积分**验证

（用户不在场，要求"后面一直继续我不在场可以进行的开发"。）

### 做了什么

1. 新建接口包 `embodied_skills_interfaces`（ament_cmake + rosidl），定义**项目自己的** `.srv`。
2. 新建 Control Skill 包 `embodied_control_skills`：`~/move_relative` / `~/rotate` / `~/stop`。
3. 运动规划逻辑抽到纯 Python 的 `motion_plan.py`，配 **19 项离线单测**。
4. **用"速度积分"做端到端验证**：车不动，但"该走 0.5 m 到底发出多少米"可以被量出来。
5. 顺带**回答了 D-011 里"跨语言 IPC 具体形式待定"**那一项（**D-026**）。

### 为什么这么做（思路）

**先解决"怎么验证"。** Phase 2 的动作原语天生要动底盘，而底盘一动就需要人在场。
但这个项目已经有两个可以复用的条件了：Motor Driver 有 `dry_run`，而 Skill 只**发布速度**。
于是把两者接起来 —— Skill 发速度 → Motor Driver 干跑 → 干跑话题 → **把速度对时间积分**。
**"发出去多少米"就变成了一个可测的数**，而车一步没动、人一个也不用在。
这条路径把"需要看护"的验证压缩成了"只需要在最后做一次真机确认"。

**接口形式的选择不是风格问题，是需求问题。** 项目里一直挂着"topic / service / action 待定"
（D-011）。这次的判断依据是：action 的两大价值是**过程反馈**和**可取消**，
而当前阶段这两样**都不成立** —— 开环没有真实进度可报，取消了也没意义因为本来就没闭环；
而"停"已经由独立的 `~/stop` 提供，且更贴合安全层的用法。
所以选 service，并把**升级路径**（有了闭环就换 action）写进决策，
免得后人以为 action 是被漏掉的。

**"开环"这件事必须写在接口上，不能只写在脑子里。** 第一版只做纯平移 / 纯旋转，
不做"平移+旋转一次完成"——因为对全向底盘，机体速度恒定 **≠** 世界系走直线。
更重要的是：**`success` 的含义是"速度按时长发完了"，不是"真的走到位了"**。
这句话写进了 `.srv`、launch 文件和 `motion_plan.py` 三处，因为上层的每个后续设计都以它为前提。

### 测试结果

**单测 19 项全过**（钉住"恒定速度 × 时长 == 请求位移"这条积分性质）。

**端到端干跑验证 16/16 项通过**：

| 用例 | 期望 | 实测 |
|---|---|---|
| `move_relative(0.5, 0)` | ∫vx ≈ 0.500 m | **+0.495 m**；侧向 ∫vy=0.0000、∫wz=0.0000 |
| `rotate(π/2)` | ∫wz ≈ 1.5708 rad | **+1.560 rad** |
| `move_relative(0.3, 0.4)` | (0.300, 0.400) | **+0.297 / +0.396** |
| `move_relative(2.0, 0)` 超上限 | 拒绝 | ✅ 返回失败，**积分 0.0000** |
| 运动中再来请求 | 拒绝、不排队 | ✅ `正有一个动作在执行，拒绝新请求` |
| 运动中 `~/stop` | 立即中止 | ✅ 只走 **+0.045 m**（0.35 s 内停住 1 m 的请求） |
| Motor Driver 不在跑 | 拒绝运动 | ✅ `状态已陈旧 14.8s —— 拒绝运动` |

### 遇到的问题

1. **节点在第一次运动请求后直接崩了**（`TypeError: 'NoneType' object is not subscriptable`）。
   控制循环收尾时把 `self._goal` 置 `None`，而服务回调还在用 `self._goal['success']` 读结果。
   修法：**启动动作时就把那条 goal 的引用抓在手里**。已记为 **坑 11**。
2. **"一次只跑一个动作、不排队"这条设计根本没生效。** 实测发现运动中的第二个请求
   **没被拒绝，而是等第一个跑完又照做了**；`~/stop` 更是直接超时 ——
   它的回调排在那个阻塞到运动结束的回调后面。根因是三个服务都用
   `MutuallyExclusiveCallbackGroup`。改用 `ReentrantCallbackGroup` 后才真正成立。
   已记为 **坑 10**。
   → **两个坑的共同点：代码里那行 `if self._goal is not None: return busy` 写得好好的，
   光看代码完全看不出问题，必须实测。**
3. **写在注释里的意图和代码实际行为不一致。** 模块注释里我写着"`~/stop` 走单独的 callback group"，
   而代码把三个服务放进了同一个组。**注释比代码先写出了意图，却没被核对** ——
   这也是坑 10 能溜过眼的原因。

### 最终结果

- Phase 2 首个 Control Skill 落地并**干跑验证通过**；决策 **D-026**（同时定下 D-011 悬置的 IPC 形式）。
- **验证方法本身是个可复用资产**：以后每个控制类原语都能先用"积分量位移"离线验证，
  只在最后做一次真机确认。
- 遗留：**真机运动未测**；**闭环未做**（`success` 不代表到位）；
  `move_forward` 作为 `move_relative(x=d, y=0)` 的特例未单列服务。

## 2026-10-06（第九轮）— Motor Driver 的链路失联处理：补上 D-021 的安全窗口

### 做了什么

1. 在 `safety_gate.py` 里加**链路状态机**（`startup` / `alive` / `lost`）与
   **「失联后需重新使能」**（`needs_rearm`）。
2. 节点新增 `/embodied/motor/events`（**只在变化时发**）与状态码 4 = `rearm_required`。
3. 单测 14 → **21 项**。
4. **用假遥测制造一次真实的链路失联与恢复**，把整条路径验证掉。

### 为什么这么做（思路）

**先把"自恢复"这个词拆开，再决定能做什么。** D-021 说"断线重连要本项目自己实现"，
但实测是「重新 bind **不自恢复**，必须重启厂商服务」—— 而**重启系统服务需要 root**。
所以"Driver 自己恢复"这件事**物理上做不到**。硬要假装做了，只会写出一个看起来在恢复、
实际没恢复的东西。**诚实的做法是把能做的和不能做的分开**：
能做的是**策略侧**（检测、归零、告警、不静默复动），不能做的是**重启那一步**，明确留给人工。

**再想清楚"危险"到底在哪。** 我一开始以为危险是"旧指令被重放"，所以在失联时作废了存指令。
但真正危险的是另一件事：**上层可能一直在以 20 Hz 发同一条指令**。
链路一恢复，那条指令立刻生效 → 机器人**毫无预兆地接着跑**，
而操作者此刻正以为它是停着的、甚至可能正在搬它。**这是"恢复"时刻特有的危险**，
作废旧指令完全挡不住。所以要的是**恢复后必须显式确认一次**。

**但又不能一律要求确认**：失联前本来就静止的话，恢复后多要一次确认没有道理 ——
而这种"没必要的确认"会被无脑点掉，反而削弱了真正需要它的那次。
所以只在**失联那一刻底盘"可能还在动"**（存在未超时且非零的指令）时才置位。

**验证方式也要设计。** 要测这条路径，最直接的办法是拔 USB —— 但那会真的让底盘失联、
可能有真实风险，而且要人在场。**把存活判据话题参数化之后，就可以用假遥测制造失联**：
车不动、人不在场，路径却是真的走了一遍。

### 测试结果

**单测：21 项全过**（新增 7 项覆盖链路状态机）。

**假遥测实测（零硬件风险）**：

| 时刻 | 观测 | 判定 |
|---|---|---|
| 0.0 / 0.4 s | 输出 0.000 → **+0.200** | ✅ |
| 6.0 s | 切断假遥测 | — |
| **8.5 s** | 输出 → **0.000**，事件 `chassis_link_lost` | ✅ 检出延迟**恰好 = +2.5 s**，与 `telemetry_timeout` 精确吻合 |

## 2026-10-06（第八轮）— Phase 1 第二个 Driver：`embodied_motor_driver`，把四条安全硬约束封进代码

（用户不在场，要求"进行不需要人工看护的开发"。）

### 做了什么

1. 新建 Overlay 包 `embodied_motor_driver`（Driver 层）。
2. **把四条安全硬约束从"文档里靠人记着"变成"代码里必然执行"**：
   主动持续发零（D-020）、存活判据只用 `imu_raw`/`battery`（D-021）、发布前自己再限幅（#19）、
   锁存停车（#22 无物理急停）。
3. 判断逻辑抽到纯 Python 的 `safety_gate.py`，配 **14 项离线单测**。
4. **默认 `dry_run=true`**：不向 `/cmd_vel` 发布任何东西。

### 为什么这么做（思路）

**选这个方向，是因为它同时满足"不需要人工看护"和"是项目真正需要的下一步"。**
Phase 1 的 Driver 层里，相机已收口；LiDAR 的 `/scan` 数据本来就对（`frame_id`、TF、10 Hz 全正常），
没有待收口项；**只有底盘这一层堆着四条硬约束没地方落**。而且它是 D-024 决策 3
（"安全停车要落在本项目自己的 Driver 层"）的落点。

**"不需要人工看护"是设计出来的，不是碰巧的。** 本机没有物理急停，所以任何可能让车动的代码
默认都必须是**不能动**的：`dry_run=true` 时节点向 `/embodied/motor/cmd_vel_dryrun` 发，
**`/cmd_vel` 的发布者数保持 0** —— 于是"逻辑对不对"可以离线验证，"车会不会动"则是一个
可被直接测量的断言（数发布者），而不是靠承诺。这样即使我在无人时段反复起停节点，风险也是零。

**安全逻辑必须能离线证伪。** 本机没有物理急停，这些判断是**唯一的安全依据**；
把它们散在 ROS 回调里、靠"跑起来看着像对的"是不能接受的。抽成纯 Python 后，
"超时会归零""锁存后必须 resume""存活恢复不得重放旧指令"这些都能被单测钉死。

### 测试结果

**离线单测（不需要 ROS、不需要底盘）：14 项全过。**

**实机干跑（车未动）**：

| 项 | 结果 |
|---|---|
| **`/cmd_vel` 发布者数** | **0** —— 直接证明车动不了 |
| 持续发布 | 干跑话题 **19.998 Hz** 连续发布，空闲时全零 |
| 限幅 | `(+0.9, −0.5, +3.0)` → 日志 `-> (+0.200, -0.200, +0.500)`，干跑话题上无任何超限值 |
| 指令超时 | 停发 0.5 s → `状态 -> no_cmd` 并归零 |
| 锁存停车 | `~/stop` → `状态 -> stopped`；`~/resume` → `状态 -> ok` |
| 遥测失联 | 启动时（遥测未到）即 `状态 -> telemetry_lost` |

### 遇到的问题

1. **两处单测失败，但错的是测试不是逻辑。** 我在 1.2 s 处求值，而测试里遥测时间戳停在 0.0 ——
   超过了 1.0 s 的遥测超时，安全门**正确地**判成了 `telemetry_lost`。
   修法是把这几个断言**隔离**到被测的那一条上（放大 `telemetry_timeout`）。
   **教训：测"指令超时"时，别让"遥测超时"同时在生效。**
2. **实测速率暴露了一个拍脑袋的参数。** 我先按经验把 `telemetry_timeout` 定成 1.0 s；
   实测发现 **`imu_raw` 46.9 Hz，但 `battery` 只有 0.95 Hz（周期 1.05 s）** ——
   **1.0 s 比 battery 的周期还短**。一旦 imu 单独失效、只剩 battery，阈值会跟着
   battery 的节拍上下反复抖动。改为 **2.5 s**（给最慢那一路留 2 倍余量）。
   **教训：超时阈值必须按最慢的那一路信号定，而不是按最快的、也不是按"感觉"。**
3. 后台记录脚本卡住（子进程占着 stdout 管道），与我自己的进程管理有关，见 `DEV_NOTES` 坑 3 的复发记录。

### 最终结果

- `embodied_motor_driver` 落地并**干跑验证通过**；决策见 **D-025**。
- 四条硬约束**从文档搬进了代码**，并且有回归测试守着（含"本类不得出现 `/odom` 存活入口"这条）。
- ⚠️ **真机运动未测**：需人工看护 + 能直接断电 + 显式 `dry_run:=false`。

## 2026-10-06（第六轮）— 相机 TF 朝向实机校验通过：D-023 的两项收口全部闭合

### 做了什么

把物体放在**机器人前方偏右、低于镜头**处来回晃动，对 `/embodied/camera/image` 相邻帧做差分，

### 为什么这么做（思路）

「相机装没装反」听起来只能靠人看，但**左/右与上/下的判据本来就是可以量化的**：
光心在 `camera_info` 里是已知的，物体的图像位置相对光心就是它的方位。
用**运动差分取质心**、而不是靠人指着画面说「我觉得在右边」，好处是**不依赖主观判断**，
而且连拍几百次能给出一个统计上很硬的结论。

### 测试结果

| 判据 | 实测 | 期望 | 判定 |
|---|---|---|---|
| 水平 | **513 次检出：右 513、左 0**；`du` 中位数 **+214 px**（+120 ~ +267） | 机器人右侧 → 图像右半 | ✅ |
| 垂直 | `dv` 在 **−134 ~ +108** 摆动（上下都晃到了）；静止场景**地面在光心下方** | 机器人下方 → 图像下方 | ✅ |

### 遇到的问题

1. **第一次取到的画面严重失焦/过曝**（一团亮斑）。用厂商 JPEG 话题交叉验证后确认
   **不是我们转发的问题，是现场画面本身**。相机在 `v4l2` 里**没有任何对焦控制项**
   （只有 brightness / contrast / saturation / hue / 白平衡 / gamma / 工频 / sharpness /
   背光补偿 / 自动曝光）→ 是**定焦镜头**，糊来自「物体离得太近」或镜头脏/有膜。
2. **先按"静止物体 + 连拍差分"测，测不到任何运动**（物体已经放稳了）。

3. **原先写在 launch 注释里的"校验方法"本身是错的**：那条写的是
   `ros2 run tf2_ros tf2_echo camera_link0 camera` 然后"目视判断物体坐标"——
   但 `tf2_echo` 只是**把我们自己发布的静态变换原样打印出来**，无论物理上装没装反，
   打出来的都是同一组数，**证明不了任何事**。已把注释改成上面这套真正用过的判据。

## 2026-10-05（第四轮）— 建 Overlay 工作区，落地第一个 Driver：把相机欠账 #16 / #23 一起收口

### 做了什么

承接用户「建完我顺手把相机 Driver 那件事（时间戳重打 #23 与 TF 帧补发 #16）在同一个节点里起步」。

   能成立的前提——工作区在仓库外，代码就进不了 Git，也不出现在 `git status` 里。
2. **修一个静默的 .gitignore 陷阱**：仓库根原有的厂商源码副本 `src/src/`，
   迫使 `.gitignore` 里有一条**裸的 `src/`** 规则，它会匹配任意层级，
   把我们自己的工作区源码一并忽略（`git status` 看着干净、代码却进不了库）。
   按用户授权把副本改名为 `vendor_reference/`，规则改为锚定形式，三条语义均验证。
3. **落地 `embodied_camera_driver`**（Driver 层）：同一节点内做两件事——
   重新打时间戳（#23）+ 补发 TF `camera_link0 → camera`（#16）。决策见 **D-023**。
4. **新增 `docs/DEV_NOTES.md`**：用户要求把「遇到的困难、怎么解决的、开发思路」单独成篇。
   与本文（按日期记做了什么）分工：DEV_NOTES 记**为什么这么想、在哪摔了跤**。

### 为什么这么做（思路）

**把 #16 和 #23 放进同一个节点，不是凑数，是因为它们本来就是同一件事的两面。**
两者都源于「厂商相机输出的元数据不可信」：一个说错时间（`header.stamp` 早 0.72 s），
一个说错空间（`frame_id=camera` 不在 TF 树）。这两样都是**元数据整形**，
都属于 Driver 层的职责，都不该让上层 Skill 各自去绕。合成一个节点，
就只有一个地方需要验证、一个地方需要维护。

**为什么 TF 不照抄厂商的四元数。** 厂商那条例子里用的是
`(-0.7071, 0, -0.7071, 0)`，对应 x=上/y=右/z=前，**不是**相机光学坐标系的 REP-103 约定。
照抄它在当下不会报错（因为没人查这个帧），但会在实现 D-007 的 `get_target_position()`
时以一个"结果总是错的、却看不出哪里错"的形式爆发。所以取 REP-103（z 前/x 右/y 下），
并把姿态做成参数。

**为什么时间戳给三档而不是直接写死一个修正值。** 因为我们**不知道**精确的修正量——
只知道量级（约一帧）。与其硬编码一个假装精确的常数，不如：把修正量做成参数、
默认取保守估计，并让诊断话题持续报出「原始戳陈旧量 / 实测帧率 / 施加的修正量」，
让这个数将来可以被实测校准。**不发明无法验证的修正量。**

## 2026-10-05（第三轮）— 相机与语音盒验收：把「图像时间戳可信吗」用亮度探针问出一个确定答案

### 做了什么

承接用户「还有什么硬件要测试的，比如相机和语音盒，确认没有问题我们要开始功能开发了」，把 Phase 0 剩下的两块硬件收掉，并把过程中发现的一个**感知层缺陷**量化到毫秒级。

1. **相机**：确认硬件可用，量化端到端延迟与时间戳偏移，定位 `frame_id=camera` 不在 TF 树的根因。
2. **语音盒**：确认控制串口 / 录音 / 播放，修正一条过期 udev 规则，验证厂商 ASR 栈能起来。
3. 系统层改动：`/etc/udev/rules.d/xf_mic.rules`（备份后修正）。**没有改动厂商仓库。**

### 为什么这么做

**为什么不能只看「有没有图」。** 相机早已出图（D-019），但两个数字一直悬着：话题速率只有设备协商值的三分之一左右（#15），以及图像 `frame_id` 不在 TF 树里（#16）。这两个都不是"能不能出图"的问题，而是"**这个图能不能拿来做闭环控制**"的问题。而在我实际排查时又冒出一个更严重的：**图像的 `header.stamp` 与本地时钟差了一大截**。

**难点在于：延迟与时间戳是两件不同的事，必须分开测。** 「图像比真实世界晚 0.72 秒」和「图像很新、但它的时间戳写早了 0.72 秒」对控制的影响完全不同 —— 前者要调管线，后者只要重新打时间戳。只测「收到的时刻 − `header.stamp`」是分辨不出来的，因为它俩在这个测量里是同一个数。

**破局点：找一个"世界端"的时间基准。** 需要一个能被我精确触发、且相机必定看得见的变化。`v4l2` 的 `brightness` 正好符合：它是 **ISP 的数字偏移、逐帧立即生效**，不依赖自动曝光的收敛。于是：在 `t_cmd` 改变亮度 → 世界在 `t_cmd` 变了 → 含新内容的那一帧**真实曝光时刻 ≈ `t_cmd`**。再分别读它的「收到时刻」和「`header.stamp`」，两个问题一次分开。

**为什么用两条话题。** `image_compressed` 比 `image_raw` 小 20 倍（~30 KB vs 614 KB）。如果延迟是订阅端解析慢造成的，两者会拉开明显差距 —— 果然拉开了约 90 ms，于是可以断定那 90 ms 是**我自己的**开销，不是相机的。

### 实测结果

**相机端到端延迟与时间戳（三档亮度跳变，结果一致）**

| 订阅 | 收到的时刻 − 下发时刻 | 该帧 `header.stamp` − 下发时刻 |
|---|---|---|
| `image_raw`（614 KB） | +111 ~ +135 ms | −604 ~ −628 ms |
| `image_compressed`（~30 KB） | **+19 ~ +44 ms** | −692 ~ −716 ms |

稳态偏移：raw **−741.2 ms**（抖动 12.4 ms / 306 帧）、compressed **−737.8 ms**（抖动 21.9 ms / 340 帧）。

→ **内容是一帧的延迟（很健康），时间戳早了约 0.72 秒。**

**六种解释逐一排除**

| 假设 | 否证 |
|---|---|
| 订阅队列积压 | 全新 `depth=1 + BEST_EFFORT` 订阅者的**第一条消息**就已 −738 ms，且不收敛 |
| 仿真时钟 | `use_sim_time: false`，全系统无 `/clock` |
| 启动时冻结的"单调→实时"换算基准 | 服务启动至今 `(实时−单调)` 仅变 **0.04 s**（开机时时钟曾被 NTP 跳过约 31 分钟，但那是 55 分钟前的事）；该假设只能预测 0.04 s 或 ~1878 s |
| 同一话题两个发布者交错 | `ros2 topic info -v`：**Publisher count = 1**（`/usb_cam`；`/yolo` 是订阅者） |
| USB 带宽不足 | dmesg 无任何 UVC 带宽/等时错误；单进程独占 `/dev/video0` |
| 设备只支持低速档 | `--list-formats-ext` 只有 **30/25/20/15/10/5**；`--get-parm` 协商 **30.000 fps** |

**22.6 Hz 的来源**：设备只有 6 个离散档、协商 30 fps，而实测 22.6 Hz 不在任何档位上 → **主机侧丢帧**（`uvcvideo.nodrop=0`，缓冲区不够时整帧丢弃），不是设备能力，也不是订阅端慢（间隔 43.77~48.03 ms 高度均匀，0/453 >50 ms）。⚠️ 但 2026-09-28 同话题四次实测是 9.8~11.5 Hz，**速率随负载变化**。

**相机 TF（#16 根因）**：`ascamera.xacro` **只定义 `camera_link0`**；URDF 里**不存在** `camera` / `ascamera_camera_link_0` / `depth_cam_color_frame`。厂商 `depth_camera.launch.py` 里那个名为 `depth_cam_base_link` 的 static_transform_publisher **发布的正是这两个都不存在的帧**（复制粘贴残留，丢了 `ascamera.launch.py` 参数的前半段）。**当前无影响**：全厂商代码里没有任何地方对 `camera` 帧做 TF 变换，`image_raw` 唯一订阅者是 `/yolo`。

**语音盒**

| 项 | 结果 |
|---|---|
| 控制串口 | `/dev/ttyCH341USB1`（USB 路径 **`1-2.4.1`**）可正常打开、无人占用 |
| `/dev/ring_mic` | ❌→✅：udev 规则写 `1-2.3.1:1.0`（该口现在是相机），实际 `1-2.4.1:1.0` |

### 遇到的问题

1. **差点把延迟和时间戳混为一谈。** 最初的测量只有「收到时刻 − `header.stamp`」这一个数，它同时包含了两个未知量。想到用 `brightness` 造一个"世界端"基准之后才分得开。
2. **`brightness` 的控制项列表一开始没细看。** 事后确认 `auto_exposure` 其实是 `value=3`（Aperture Priority，即自动曝光），与参数文件写的 `autoexposure: false` 不一致 —— 这也是画面亮度长时间钉在 143.6 的原因。选 `brightness`（数字偏移、立即生效）而不是去关自动曝光，恰好绕开了这个坑。
3. **误开了麦克风直通，录到满量程削顶。** `amixer -c 0 sset 'Mic' 80% unmute` 这条命令**同时设置了 playback 与 capture 两侧** —— 这台机器的 `Mic` 是一个双向简单控件。playback 侧被打开 = 麦克风直通扬声器 = 啸叫环路，于是录到峰值 32768 / RMS 31588。发现后 `sset 'Mic' playback mute` 复原，重新做增益扫描才拿到干净数据（496 档：峰值 7565 / 削顶 0%）。**教训：改本机 `Mic` 控件前必须看清是 `capture` 还是 `playback`。**
4. **`pkill -f` 打死过自己的 shell。** 清理语音残留进程时，`pkill -f 'awake_node.py|asr_node.py|voice_control'` 匹配到了我自己那条命令行（命令里包含这些字符串），返回 144。改用 `ps | grep | awk` 取 PID 再逐个 kill。
5. **两次"证据不一致"是同一个原因：速率随负载变。** #15 里记的「`camera_info` 曾出现 37 Hz，与 11 Hz 矛盾」，和本轮测到的 22.6 Hz，都是同一个量在不同负载下的取值。**结论不是"速率是多少"，而是"速率不可假设"。**
6. **`uvcvideo.quirks = 4294967295` 一度被怀疑。** 查下来是主线的**正常默认**（`uvc_quirks_param = -1` = 不强制任何 quirk），`/proc/cmdline` 与 `/etc/modprobe.d` 里都没有相关设置。**撤回该怀疑。**
7. **时间戳的机制没能定死。** `usb_cam` 在本机只有 stripped 二进制（`/opt/ros/humble/lib/usb_cam/usb_cam_node_exe`，35 KB）+ `libusb_cam*.so`，没有源码；`uvcvideo.clock = CLOCK_MONOTONIC` 说明驱动给的是单调时钟，但从外部无法确定是在哪一步换算错的。**没有为了"给个说法"而编一个机制** —— 记录为未定，并给出与机制无关的处置。

### 最终结果

- **相机硬件判定可用**：真实图像、单发布者、CPU 4%、无 USB 错误、**端到端延迟 ≈ 一帧（20~45 ms）**。
- **🔴 新立安全/设计前提**：图像 `header.stamp` **比真实采集时刻早 0.72 s**，且**不能靠调缓冲或换 `io_method` 修好**（问题不在管线深度）。→ **须在自建 Driver 层重新打时间戳**（#23 / **D-022**）。
- **#15 / #16 从"未定"变为"已定性"**：速率是主机侧丢帧且随负载变化；TF 帧缺失的根因是厂商 launch 里的复制粘贴残留，**补救变换必须落在 Overlay**（CLAUDE.md §2/§8 禁止改厂商文件）。
- **语音盒硬件判定可用**：控制串口 / 录音 / 播放三项全通过；`/dev/ring_mic` 缺失**只是一条过期 udev 路径**，修正后厂商 ASR 栈正常启动。
- **Phase 0 只剩两项**：**急停链路**（唯一剩下的硬件项，需物理操作）与**相机 TF 帧收口**（需先建 Overlay Workspace）。

## 2026-10-05（续）— 通信中断模拟：把「必须显式发 0」从推断变成读数

### 做了什么

承接同日底盘运动验收留下的开放问题「通信中断时底盘会不会停车」，做了两阶段模拟，并把测量手段固化成一个新工装。

1. **S2 — 冻结桥节点**（`SIGSTOP ros_robot_controller`，等价于「指令发不进板子」），机器人原地旋转中执行。
2. **S3 — 真断线**（`unbind` 底盘 USB 口 `1-2.2`，**零速、不动电机**），观察遥测与恢复行为。
3. 新增 `tools/lidar_rotation_probe.py` —— 用 LiDAR 测原地旋转角速度的验收工装。

### 为什么这么做

**为什么要换仪器。** 第一轮只能用 IMU 振荡幅度间接推断「电机还在转」（±0.067 vs ±0.0015）。但 IMU 与桥节点**同生共死** —— 想测「桥节点被冻结后板子还转不转」，IMU 恰好在那一刻消失。目视轮子也不行：旋转中的麦轮看不出转没转，实测问了两次都是「没看清楚」。

**破局点**：**LiDAR 走独立的 USB 口（`1-2.1`）与独立进程，桥节点死了它照常出数据。** LiDAR 固连在机器人上，机器人原地转 θ，扫描图就整体平移 θ —— 对两帧 `ranges` 做互相关即可读出转角。于是「板子还转不转」从一个需要目视判断的问题，变成了一台**独立仪器上的读数**。

**为什么 S3 只在零速下做。** 真正该问的安全问题是「运动中拔线是否停车」，但**这个测试按构造就是不安全的**：S2 已证明指令中断不停车，而断线后**也无法再发 0**（发不进板子），机器人会一直转到厂商栈重启成功；而厂商栈的重启是整栈级的、可能失败，本机又**没有物理急停**，场地「不是很开阔」。一个失败模式是「停不下来的旋转机器人」的测试，违反 CLAUDE.md §8「任何运动测试必须保留急停」。**故刻意不做，并写进文档**。S2 已足以回答该问题 —— 底盘固件在两种场景下看到的都是「没有新指令到达」。

### 实测结果

**S2 — LiDAR 转速计（`tools/lidar_rotation_probe.py`）**

| 相位 | 总转角（直接法 / 链式法） | 转速 |
|---|---|---|
| 静止 | +0.0000 / +0.0000 | **0.0000 rad/s** |
| 发 `wz=+0.15` | +0.5121 / +0.4997 | **+0.1298 rad/s** |
| 静止 | +0.0375 / +0.0500 | +0.0149 rad/s |
| 冻结前发 `wz=+0.15` | +0.3623 / +0.3747 | **+0.1308 rad/s** |
| **★冻结 7 s（SIGSTOP）** | **+0.9493 / +0.9244** | **+0.1373 rad/s（冻结前的 105%）** |
| 发 0（显式停车） | +0.0125 / +0.0250 | **+0.0064 rad/s** |
| finally 停车 | −0.0125 / +0.0000 | −0.0028 rad/s |

冻结期间共转 **0.9369 rad ≈ 53.7°**。两法在每一相位吻合到 **2~3%**。

**S3 — 真断线（USB unbind `1-2.2`）**

| 信号 | 断线前 | 断线中 |
|---|---|---|
| `/odom` | 30.002 Hz | **28.529 Hz（照常）** |
| `/scan` | 10.000 Hz | 9.906 Hz |
| `imu_raw` / `battery` | 有消息 | **❌ 无消息** |
| 桥节点进程 | PID 26198 | 仍存活（三轮实测三种行为：苟活 / 退出 / 静默存活） |

恢复：仅 `bind` **不自恢复** → `sudo systemctl restart start_app_node.service` 后新 PID 28244、`/odom` 30.000 Hz、遥测恢复（约 6~18 s）。`/dev/rrc` 重新枚举在 `ttyACM1` / `ttyACM2` 间跳变。

**其它确认**：`~/wifi_manager/button_scan.py`（PID 697）的 `os.system('sudo halt')` **被注释掉** → **本机没有物理急停**。

**恢复后状态**（已确认）：`/odom` 30.000 Hz、`/scan` 9.9 Hz、电量 12457、两个 `cmd_vel` 静默、LiDAR 转速计读 **0.0000 rad/s（静止）**。

### 遇到的问题

1. **v1 转速计被丢帧悄悄缩放**：v1 用「相邻帧位移 ÷ 固定 `scan_time`」，但订阅端 6 s 只收到 24 帧（≈4 Hz，而 `/scan` 是 10 Hz），`prev` 一旦不是真正的相邻帧，速率就被缩放。修法不是"加快循环"而是**换算法**：改用「首帧 vs 末帧互相关」求总转角再除时长，**完全不依赖相邻帧**；并加「~1 s 步长链式累加」做交叉自检。顺带查清丢帧根因是控制循环里 `publish + sleep` 拖慢了 `spin_once` 消费速度（纯 spin 循环下收到 59 帧/5.7 s ≈ 10.4 Hz）。
2. **LiDAR 每帧点数浮动（503/504/505）**：互相关要求两帧等长，v2 一开始要求「首末帧形状相同」，结果**旋转段经常整段返回 `nan`**（冻结段碰巧等长才测到）。改为只使用**出现次数最多的帧长**的帧。
3. **静止时"两法差值偏大"误报**：判据只看相对差，两值都 ≈0 时 1 个索引点（0.0125 rad）的相对差被放大成 100%。修法是**绝对下限 + 相对阈值同时超标**才告警。
4. **`sed 's/^/  /odom /'` 把表达式写坏**：替换串里的 `/` 与分隔符冲突，导致关键速率没打出来，白跑一轮断线。改为写脚本文件、用 `printf` 输出。
5. **argparse help 里的 `%` 必须写 `%%`**：自作主张把 `%%` 改成 `%`，`--help` 直接抛 `ValueError: unsupported format character`。已改回。
6. **桥节点进程状态三轮三种行为**（苟活 / 退出 / 静默存活）：这不是噪声，而是**结论本身** —— 进程是否在列表里**不能**作为健康判据。
7. **`/odom` 在断线后照常发布 28.5 Hz**：这是最危险的一条 —— 拿 `/odom` 做 watchdog 输入等于 watchdog 监视自己。

### 最终结果

1. **验收工装自身先踩了两个坑**，均与「测量工具骗人」同类：

   - 拿通用的 `_avg(seq, i)`（期望元素是三元组）去算 IMU 的 float 列表 → `TypeError`。**修**：加 `_mean(seq)`。
2. **`ros2 topic echo --field` 会夹带 `---` 分隔行**，被 awk 的 `$1` 当成数字 0 → 一度算出「IMU 一半样本是 0」。**修**：`grep -E '^-?[0-9]'` 过滤后再统计。**教训同 09-28 的 `ros2 topic echo` 省略长数组：统计前必须确认工具输出的真实形状。**
3. **T8 早先一次读数（IMU 均值 −0.227 rad/s）与后续复现（+0.003）矛盾**，一度以为「无指令时底盘在自转」。加做同轮三阶段探针（发 0 / 主动发 / 停止发布 / 再发 0）后定位：**判据应是振荡幅度而非均值** —— 电机振动让瞬时值在 ±0.06 内摆动，取均值会随机落在任意值上。改判据后两轮复现一致。**这是本轮最值得记的一条方法论：用振动幅度判"转没转"，不要用均值。**
4. **实际测试条件与计划不符**：原计划「车轮悬空」，实际是**车轮着地**。用户确认后据此定性 —— 反而获得了更真实的**地面运动**证据；但也意味着本次**没有**验证到悬空工况，且运动是在地面而非架空下完成的。

### 最终结果

### 遇到的问题

1. **`/dev/lidar` 被 udev 指向了底盘串口**（🔴 本次最重要发现，也是已知问题 #4 的真正根因）

   ```text
   /etc/udev/rules.d/lidar.rules 中启用的规则:   KERNELS=="1-2.2:1.0"  → SYMLINK+="lidar"
   而 1-2.2 是底盘 CH9102 → ttyACM0 (=/dev/rrc)
   真正的雷达在 1-2.1  → ttyCH341USB0
   ```

   链条：雷达健康但 `ldlidar` 节点要打开 `/dev/lidar`（=`ttyACM0`，已被底盘进程独占）→ **节点起不来** → ROS 图中无 `/scan`。这解释了 2026-09-23 基线里「无 `/scan`」与 syslog 里 `wait device insert...` 的全部现象，**根因不在硬件**。

   另注：厂商自带的 `usb_ch341` 驱动把 CH340 命名为 `/dev/ttyCH341USB*`（而非内核标准的 `ttyUSB*`），这也是「按 `ttyUSB0` 找不到雷达」的表面原因。

   **处置**：改 `lidar.rules` 为 `KERNELS=="1-2.1:1.0"`（旧行保留为注释并写明原因），备份为 `lidar.rules.bak-20260928`。`udevadm test` **dry-run 先验证**（雷达设备 → `LINK 'lidar'`；底盘设备 → `Removing/updating old device symlink '/dev/lidar', which is no longer belonging to this device`），再**只对雷达那一个设备**触发 uevent（该口无人占用）。

   ```text
   修正前: /dev/lidar -> ttyACM0        (底盘串口，错)
   修正后: /dev/lidar -> ttyCH341USB0   (LD19 雷达)
   /dev/rrc -> ttyACM0 未变；底盘进程 PID 689 / 2884 未受影响
   ```

2. **Aurora930 是深度相机，不是 LiDAR** —— 此前基线把 `aurora930_node` 当成雷达驱动来排查（已知问题 #8），方向错了。它是 Deptrum 的**深度相机**（VID `3251`）驱动，本机无此设备，故节点 `21:12:20` 报 `No deptrum device connected! It's going to quit...` 后退出。

3. **`.typerc` 机型配置与实机不符** —— `DEPTH_CAMERA_TYPE=aurora` 期望深相机，实机是单目。旁证：厂商 `usb_cam` 分支的 `usb_cam_param.yaml`（`/dev/video0` + `yuyv` + 640×480）**与实机摄像头完全吻合**，且 `usb_cam` 包**已随系统安装在 `/opt/ros/humble`** —— 说明本机本该走 `usb_cam` 分支，`.typerc` 的机型填错了。**未改动**（属厂商配置，D-009）。

4. **`ttyCH341USB1` 身份未确认** —— 口 4 副 Hub 下有一个静默 CH340。`xf_mic.rules` 期望的 `/dev/ring_mic`（口 `1-2.3.1`）在本机**不存在**，故疑其为讯飞环形麦的串口控制口（与同处 `1-2.4` 的 USB 声卡构成一个复合设备），也可能属云台/舵机控制器。**待实测**（新记已知问题 #14）。

5. **两个 CH340 均无序列号** —— `1a86:7523` 的 `serial` 字段为空，无法按 ID 区分雷达与另一路 CH340，**只能按物理路径匹配**。这意味着 `/dev/lidar` 规则绑定 `1-2.1:1.0`，**更换 USB 插口即失效**，是已知的脆弱点（已写入 D-018）。

### 最终结果

## 2026-09-23（续）— 解除磁盘阻塞：根分区在线扩容 65G → 116G

### 做了什么

1. **分区布局侦察**（只读，不修改任何分区）
2. **零风险缓存清理** ~2.35G
3. **在线扩容**根分区与文件系统：65G → 116G，可用 2.9G → 55G
4. 两项"看似可删"的资产经核查后**主动放弃删除**（见下"遇到的问题"）
5. GPT 备份留档：`/root/gpt-nvme0n1-2026-09-23.bin` + `.txt`

### 为什么这么做

磁盘是 Phase 0~7 全部部署（PyTorch / 模型权重 / engine / rosbag / Docker）的硬前提。

侦察发现关键事实：**这块 256GB NVMe 只用了 65G，后面 185G 空闲从未被使用** —— 所以"清理 3G"只是权宜，**扩容才是根本解法**：

```text
nvme0n1 = 256GB (500118192 扇区)，GPT 声明的 last-lba = 250069646（≈119 GiB）
├─ p2~p13   A/B 内核槽 + recovery + ESP       0.64 GiB
├─ p14/p15  UDA / reserved                    0.92 GiB
├─ p1  APP  ext4 = /  扇区 3050048→139405311  65 GiB（已用 57.9G）
├─ 空闲    扇区 139405312→250069646           52.8 GiB  ← 可直接用
└─ GPT 之外 扇区 250069647→500118192          119 GiB   ← 被 GPT last-lba 挡住，未解锁
```

p1 是磁盘上**最后一个分区**，空闲空间紧邻其后 → 可在线扩容，无需重启、无需迁移数据。

### 测试结果

**清理（2.35G，逐项可查）**

| 项 | 回收 | 验证 |
|---|---|---|
| `/var/log/syslog` 391M + `kern.log` 75M | 466M | 截断后均为 4.0K |
| snap 旧版本 4 个（gnome-42-2204 rev245 / gnome-46-2404 rev147 / mesa-2404 rev1166 / cups rev1208） | 1.34G | `snap list --all` 已无这些 revision，`.snap` 文件消失 |
| `~/.cache/pip` | 373M | 目录已删除 |
| `~/.ros/log` | 169M | 目录已删除（`rtabmap.db` 保留） |

**扩容（关键校验，全部通过）**

```bash
sudo sfdisk --no-reread /dev/nvme0n1 < /tmp/gpt-new.txt   # 只改 p1 size，uuid 原样保留
sudo partx -u /dev/nvme0n1p1                              # 内核分区表更新

```

| 校验项 | 结果 |
|---|---|
| `sfdisk -d` 中 p1 | `size 136355264 → 247019599`，`uuid=7E601F05-…` **未变** |

1. **`snap remove <name> --revision=<rev>` 才是正确语法** —— 写成 `--revision=<rev> <name>` 会报 `snap "cups 1208" is not installed`。
2. **`/usr/src/linux-headers-5.15.0-168{,-generic}`（137M）放弃删除** —— 原以为是 x86 头文件，实为 Ubuntu **arm64 generic** 内核头（对 tegra 内核同样无用）。但 `apt-get purge --dry-run` 显示会**连带安装 `linux-headers-5.15.0-194` 新包并升级 `linux-headers-generic` 元包**（系统有 1008 个待升级包）。为 137M 在 96% 分区上触发 apt 事务不划算。

4. **磁盘仍有 ~119G 未纳入 GPT** —— 本次按"不碰 GPT 几何"执行，`last-lba` 保持 250069646。需要时再单独执行（改 `last-lba` + p1 size 回灌即可），当前 55G 充足。
