# DECISIONS.md — 重要技术决策记录

> 记录**为什么**这样设计，防止后续忘记设计原因而做出冲突的改动。
>
> 格式：决策 → 原因 → 影响 / 约束。新增决策请追加，不要删除历史决策；若决策被推翻，标注"已废弃 + 替代决策"。

---

## D-001：机器人整体是 Agent，而不是"Agent 控制机器人"

**决策**：把整台机器人抽象为一个具备 Perception / Reasoning / Action / Environment Feedback 的完整 Agent。Jetson 提供认知与计算能力，LLM 提供高层推理，Skill Runtime 与 Linux 负责把决策变成真实动作。

**原因**：
- "Jetson 上跑一个 Agent 去控制小车"会把智能局限在一个 Python 进程里，而真实的感知、执行、反馈分散在整个系统。
- Agent 的完整定义要求闭环（感知 → 推理 → 动作 → 环境反馈），只有整机才能构成这个闭环。

**影响 / 约束**：
- 不能用"Agent 进程"的视角去划分模块边界。
- 编写文档与代码时，"Agent" 指整机；指进程时明确写 `agent_service` / `agent_runtime`。

---

## D-002：LLM 不参与实时控制

**决策**：LLM 只负责自然语言理解、任务拆解、多步骤规划、Skill 选择、条件判断、失败重规划、结果总结。**禁止** LLM 参与电机 / PID / 急停 / 避障等实时控制。

**原因**：
- LLM 推理延迟（秒级）与控制环要求（20~100 Hz）相差数个数量级。
- LLM 输出不确定，无法提供实时控制的确定性与可验证性。
- 断网时控制能力必须仍然可用。

**影响 / 约束**：
- LLM 只输出 `navigate_to("desk")` 这类语义调用，**绝不输出** `左轮 100 RPM / 右轮 90 RPM / 向左偏 2°`。
- 任何进入控制环的代码不得依赖大模型。
- 这是**架构红线**，不接受为"方便"而打破。

## D-003：采用分层 Skill 架构（6 层）

**决策**：`Hardware → Driver → Primitive → Control Skill → Autonomous Skill → Semantic Skill → Agent Task`。

**原因**：
- 让复杂智能建立在确定性的底层能力之上：越往下越确定、越实时、越不依赖 LLM；越往上语义越强、时间尺度越慢。
- 每层可独立测试与验收，避免"整机联调才能发现问题"。

**影响 / 约束**：
- Agent **只能**调用 Semantic Skill，不直接访问 Motor / GPIO / PWM / ROS Topic。
- 新增能力时必须明确它属于哪一层。
- 只有验收通过的能力才允许向上封装（见 D-009）。

## D-004：采用 Event-driven Agent，而非 Real-time LLM Controller

**决策**：Agent 发起 Skill 后进入 `WAIT`，由本地运行时执行；只有任务级事件（`ARRIVED` / `BLOCKED` / `FAILED` / `CANCELLED` / `TARGET_LOST` 等）才唤醒 Agent。

**原因**：
- 让 LLM 持续轮询状态会浪费算力且引入延迟。
- 导航 / 跟随等过程需要几十秒本地闭环，期间 LLM 无事可做。
- 事件粒度让 Agent 的重规划时机明确、可测试。

**影响 / 约束**：
- Skill 必须有明确的状态机与事件上报机制。
- Skill Manager 负责 Cancel / Timeout / Event 上报。

---

## D-005：Safety Runtime 独立于 LLM，且拥有最终否决权

**决策**：Safety Runtime 独立运行，包含急停、避障停止、限速、Watchdog、命令超时、电机超时、低电量保护。优先级 `Safety > Control > Skill > Agent`。

**原因**：
- 安全不能依赖一个可能超时、断网、幻觉的组件。
- 断网 / LLM 故障时安全能力必须绝对可用。

**影响 / 约束**：
- Safety 路径**不经过 LLM**。
- Tool / Skill 请求必须经过 Safety Gateway（Schema 校验 / 权限 / 范围检查 / 超时 / 取消 / 结果校验）。
- 例如 `move_relative(100m)` 必须被 `REJECTED: distance exceeds safety limit`。

---

## D-006：安全指令走本地解析，绕过 LLM

**决策**：`停 / 急停 / 取消任务 / 别动` 等安全指令走 `Voice → Local Parser → Safety Runtime → Motor Stop`，不经过 LLM。确定性指令（"向前走 0.5 米"）同理走本地解析 → Control Skill。

**原因**：
- 安全指令要求**最低延迟**与**最高可靠性**，走 LLM 会引入秒级延迟与失败风险。
- 大部分日常指令其实是确定性的，本地解析即可完成，无需消耗 LLM。

**影响 / 约束**：
- 必须维护一份本地关键词/规则表，且能被 ASR 直接触发。
- 只有真正的复杂任务（条件、多步、模糊语义）才进入 Agent Runtime。

## D-007：视觉推理使用 TensorRT

**决策**：视觉链路为 `Camera → GStreamer → CUDA → TensorRT → YOLO → Tracker`，对上层暴露 `detect_object()` / `detect_person()` / `capture_image()` / `get_target_position()` / `describe_scene()`。

**原因**：
- Jetson Orin 上 TensorRT 能充分利用 GPU/NVDLA，显著降低推理延迟，满足跟随、寻迹等 10~30 Hz 的实时要求。
- 目标是本地实时闭环，不能依赖云端推理。

**影响 / 约束**：
- `*.engine` / `*.plan` 是**平台相关的大二进制产物**，必须由构建脚本从 ONNX 生成，**不进 Git**（见 D-010）。
- 需记录 TensorRT / CUDA / JetPack 版本，因为 engine 与版本强绑定。

---

## D-008：C++ 与 Python 分工

**决策**：

| 语言 | 模块 | 理由 |
|---|---|---|
| C++ | `robot_service` / `navigation_service` / `safety` / 部分 vision runtime | 实时性、确定性、靠近硬件 |
| Python | `voice_service` / `agent_service` / LLM orchestration | 生态、LLM SDK、迭代速度 |

**原因**：
- 控制与安全环对延迟和确定性敏感，适合 C++。
- LLM / ASR 生态以 Python 为主，且迭代频繁，适合 Python。
- 强行统一语言会在某一侧付出明显代价。

**影响 / 约束**：跨语言接口需要明确的 IPC / ROS2 接口约定（见 D-011）。

## D-009：厂商 ROS2 栈作为系统 SDK，项目代码放 Overlay Workspace

**决策**：保持厂商 `~/ros2_ws` 与 `~/third_party` 不变，作为系统 SDK 使用；本项目代码放在独立的 Overlay Workspace（计划名 `embodied_agent_ws`）。

**原因**：
- 厂商栈包含大量已验证的驱动与配置（`ros_robot_controller` / `kinematics` / `orbbec_camera` / `xf_mic_asr_offline` 等），直接修改风险高、难以回滚。
- Overlay 方式可以随时丢弃本项目代码而不影响底层能力。

**影响 / 约束**：
- **不修改厂商包**；确需修补时以 Overlay 覆盖的方式实现，并在此记录。
- 环境加载沿用厂商既有 source 顺序，改动顺序需记录原因。

## D-010：模型权重与 engine 不进 Git，暂不引入 Git LFS

**决策**：`.gitignore` 排除 `*.engine` / `*.plan` / `*.onnx` / `*.pt` / `*.pth` 等模型产物。**暂不使用 Git LFS。**

**原因**：
- 这些文件体积大且是**可重新生成**的构建产物（ONNX → engine）。
- 当前根分区仅剩 3.0G，LFS 会增加管理复杂度与存储压力。
- 尚无必须版本化的模型资产。

**影响 / 约束**：
- 模型通过**构建脚本 + 版本化配置**复现，而不是提交二进制。
- 若未来确有必须版本化的权重，**先与用户讨论 Git LFS**，不要直接提交大文件。

---

## D-011：Agent 与底层的接口走 Skill Manager + ROS2，不用直连

**决策**：Agent → Skill Manager → ROS2（topic / service / action）→ Driver。Agent 不直接发布 `cmd_vel` 或访问 `/dev/*`。

**原因**：
- Skill Manager 统一承担注册、参数校验、执行、状态管理、Cancel、Timeout、事件上报。
- 集中一处做校验与安全拦截，避免每个调用点各自实现。

**影响 / 约束**：
- 新增底层能力时，先在 Skill Manager 注册，而不是让 Agent 直接调用 ROS2。
- 具体 IPC 形式（topic / service / action）在实现对应 Skill 时确定，并在此追加决策。

## D-012：第一版明确不做机械臂 / 多机器人 / 强化学习导航 / 复杂 RAG / 大型本地 VLM / 自动充电

**决策**：为保证主线清晰，第一版不包含上述功能。

**原因**：这些功能会显著分散精力，且都依赖尚未完成的底层能力。

**影响 / 约束**：评审新需求时，若属于上述范围，默认推迟到第一版之后。

## D-013：文档与代码在同一个 commit 内更新

**决策**：架构、进度、开发日志、决策记录的更新与对应代码改动放在同一个 commit。

**原因**：文档滞后会直接导致下一次会话基于过时信息做决策，破坏"可恢复的长期开发闭环"。

**影响 / 约束**：文档同步视为任务完成的一部分，不是可选收尾。

## D-014：磁盘不足时，优先"扩容 + 只回收可再生缓存"，不删引导链与固件资产

**决策**：根分区空间不足的解法顺序为 ① 先侦察分区布局 ② 扩容 ③ 只回收**可再生**缓存（日志、pip cache、ROS 日志、snap 旧 revision）。以下资产**默认不删**：

| 资产 | 保留原因 |
|---|---|
| `/opt/ota_package`（238M） | `TEGRA_BL_*.Cap` / `BOOTAA64.efi` 是 **A/B 引导链 OTA capsule 载荷**，删除会丢失固件 capsule 更新能力，离线难以重建 |
| `/usr/src/linux-headers-5.15.0-168*`（137M） | 需 `apt purge`，会连带安装新头文件包并升级元包；在接近满的分区上触发 apt 事务风险大于 137M 收益 |
| `~/.ollama/models`（3.6G） | Phase 7 本地小模型的候选资产，删后需重新 pull（依赖网络） |
| `~/.vscode-server`（3.9G） | 连上即按需重新下载，由用户按需清理更合适 |
| `/swapfile`（8G） | 内存仅 7.4Gi，这是实际的安全余量 |

**原因**：
- 这台机器是**嵌入式设备**，引导链 / 固件 / 离线安装资产一旦删除，恢复成本远高于其占用空间。
- "看起来像残留"的目录（`ota_package`、内核头）实际承担功能职责，**必须先核查内容再判断**，不能按名字归类为垃圾。
- 清理上限只有几个 G，而扩容一次可得 52.8G —— 性价比与风险都更优。

**影响 / 约束**：
- 清理前必须逐项核对内容与归属（`du` / `dpkg -S` / `apt-get --dry-run`），并说明"为什么可以删"。
- 本机可安全清理的路径：`/var/log/{syslog,kern.log}`（截断）、`~/.cache/pip`、`~/.ros/log`、`snap remove --revision=<旧 rev>`。注意 `~/.ros/rtabmap.db` 是 SLAM 数据库，**不在清理范围**。

## D-015：分区扩容必须保留 PARTUUID，用 sfdisk 回灌而非重新创建分区

**决策**：扩容操作固定为 `sgdisk -b` + `sfdisk -d` 备份 → 只改 p1 的 `size` → `sfdisk --no-reread` 回灌 → `partx -u <part>` → `resize2fs`。

**明确不用的做法**：
- `growpart`：本机（Ubuntu 22.04 aarch64）未安装，需额外装 `cloud-guest-utils`。
- `sgdisk -d 1` + `sgdisk -n 1:…`：**会重新生成分区 GUID**，除非额外指定 `-u`。

**原因**：
- 根分区以 **PARTUUID** 引用：`/boot/extlinux/extlinux.conf` 中 `root=PARTUUID=7e601f05-7305-42c0-afad-85b790a82e91`（由 cbootargs 传入）。分区 GUID 一变，系统无法启动。
- `sfdisk -d` 的 dump 含每个分区的 `uuid=`，原样回灌可完整保留所有 GUID 与分区属性（类型、名称、ESP 标志）。
- 在线扩容对**最后一个分区**成立：ext4 支持在线增长，`partx -u` 通过 `BLKPG_RESIZE_PARTITION` ioctl 更新内核，无需重启。

**影响 / 约束**：
- 任何分区操作前必须备份（`sgdisk -b <bin>` + `sfdisk -d > <txt>`），并留档到 `/root`。
- 操作后**强制复核**：`lsblk -no PARTUUID` 与 `extlinux.conf` 中的 `root=PARTUUID` 必须逐字符一致；`sgdisk -v` 无错误。
- 回滚：`sgdisk -l <bin>` 恢复分区表；文件系统回缩需离线 `e2fsck` + `resize2fs`（正常不应发生）。
- 涉及磁盘 / 分区的操作**必须先经用户确认**，不与其它改动混在同一个 commit。

## D-016：Control Skill 接入点为 `/cmd_vel`，不与厂商 app 争 `/controller/cmd_vel`

**决策**：本项目的控制类 Skill 通过发布 `geometry_msgs/msg/Twist` 到 **`/cmd_vel`** 驱动底盘。**不**发布到 `/controller/cmd_vel`，**更不**直接发布 `/ros_robot_controller/set_motor`。

**实测依据**（2026-09-23 Phase 0 基线）：

| 话题 | 发布者 | 订阅者 | 结论 |
|---|---|---|---|
| `/cmd_vel` | **0** | 1（`odom_publisher`） | ✅ 干净，专用外部入口 |
| `/controller/cmd_vel` | **5**（`lidar_app` / `line_following` / `object_tracking` / `self_driving` / … 厂商 app） | 1（`odom_publisher`） | ❌ 多方争用，不可作为接入点 |
| `/ros_robot_controller/set_motor` | 1（`odom_publisher`） | 1（`ros_robot_controller`） | Primitive 层，Control Skill 不得直接调用 |

**原因**：
- 厂商的 4~5 个 app 都挂在 `/controller/cmd_vel` 上，且各自带 `enter` / `heartbeat` 服务，**被激活即开始发运动指令**。项目若也接这一条，等于与 app 抢方向盘，且无法解释"车为什么动了"。
- `/cmd_vel` 是 ROS 生态公认的底盘入口（nav2 / teleop 同约定），发布者当前为 0 —— 独占且可预期。
- `/ros_robot_controller` 是硬件桥（`set_motor` / servo / buzzer / led / oled），属于 Primitive 层。直接调用它会绕过运动学层与 Safety，违反 D-003 / D-005。

**影响 / 约束**：
- 运动测试前必须确认厂商 app 未激活；这是 Phase 0 底盘验收的**前置条件**。
- 麦轮运动学约定、单位、速度上限、命令超时由 `odom_publisher` 决定，需在实测中记录后补充进接口清单。
- 若将来必须与某个厂商 app 共存，需先明确**互斥与优先级**，不得默认并行发布。

## D-017：视觉基线为单目 RGB，本项目不假设深度输入

**决策**：本项目的视觉输入定义为**单目 USB 摄像头**，**不存在深度相机**。任何 Driver / Primitive / Skill / Agent 设计**不得假设**可获得深度图、点云或相机内参对齐后的 3D 坐标。

**实测依据**（2026-09-28，全系统 USB 与视频节点枚举）：

| 项 | 实测 |
|---|---|
| 摄像头 | **全系统仅一个**：UVC `32e6:9005`「icspring camera」@ `1-2.3` |
| 设备节点 | `/dev/video0`（Video Capture，YUYV 640×480@30）/ `/dev/video1`（**Metadata Capture**，非深度流） |
| 支持格式 | UVC 描述符中**仅 1 种格式**（`guidFormat 32595559…` = YUYV），无任何深度 / IR 的 GUID，控制项中无 ToF / IR 相关项 |
| 深度相机 | ❌ 全总线无 Deptrum（`3251`）、无 Orbbec（`2bc5`）；CSI 侧（`tegra-camrtc`）亦无 sensor 注册 |
| 厂商配置 | `~/ros2_ws/.typerc:9` 中 `DEPTH_CAMERA_TYPE=aurora`（期望 Deptrum Aurora930）→ 与实际硬件**不符**，`aurora930_node` 已于 21:12:20 报 `No deptrum device connected!` 后退出 |

**原因**：
- 硬件事实如此：这台车上装的就是单目摄像头。文档此前记录为「Orbbec 深度相机 + 深度对齐方案」属于**沿用厂商软件包名的误记**，必须先纠正，否则后续会基于不存在的能力做设计。
- 深度能力的有无会直接改变上层的实现路线（见下），必须作为**架构前提**固定下来，而不是当作待办事项悬置。

**影响 / 约束**：
- **测距与避障一律依赖 LiDAR**（详见 D-018 的 LD19）。不得为避障设计依赖深度的方案。
- **不能做 RGBD SLAM**；建图只能走 2D LiDAR SLAM（`slam_gmapping` / `rtabmap` 的 2D 模式）。
- D-007 所列 `get_target_position()` / `describe_scene()` 需要改为**单目方案**（基于像素几何 + 已知目标尺寸 / 标定 + LiDAR 辅助），实现时需追加决策记录，不得沿用"深度对齐"的原始设想。
- `~/ros2_ws/.typerc` 是厂商的**机型配置文件**（按机型切换 `LIDAR_TYPE` / `DEPTH_CAMERA_TYPE` / `MIC_TYPE` 等，注释中即列有备选机型），填的机型与实际硬件不符属**配置项写错**，不是代码缺陷。但修改它仍是改动厂商配置（D-009），需先记录再动 —— **2026-09-28 已按用户决策改为 `usb_cam` 并重启实测出图，见 D-019**；相机 Driver 的最终归属（复用厂商 `usb_cam` 还是在 Overlay 自建）改由 D-019 决定。
- 若未来加装深度相机，本决策**需显式推翻并记录替代决策**，不得默默启用。

## D-018：LiDAR 型号确定为 LD19，通过 `/dev/lidar` 统一接入

**决策**：本项目 LiDAR 使用 **LDROBOT LD19**（`ldlidar_stl_ros2` 驱动，230400 波特率），设备入口统一为 `/dev/lidar`（与厂商 5 个 LiDAR launch 的既有约定一致）。

**实测依据**（2026-09-28）：

| 项 | 实测 |
|---|---|
| 物理位置 | Hub 第 1 口 `1-2.1`，CH340 `1a86:7523` → `/dev/ttyCH341USB0` |
| 协议 | `0x54 0x2C` 帧头，**包长恒为 47 字节**，CRC8 多项式 `0x4D` |
| 校验 | **1248/1249 包通过 CRC（99.9%）** |
| 数据质量 | 14976 个测距点**全部有效**（166~2453 mm，中位 262 mm），无无效点 |
| 速率 | 416.5 包/秒 × 47 B = 19576 B/s，与端口实测 19579 B/s **偏差 0.01%**（字节守恒） |
| 点频 / 覆盖 | 4992 点/秒（规格 4500）；起始角覆盖 2.5°→356.3°，**完整 360°** |

**原因**：

## D-020：底盘速度上限与「无指令超时」——停车必须靠显式发 0

**决策**：Control Skill / 任何控制路径在结束运动、异常、取消、超时时，**必须显式向 `/cmd_vel` 发布零速度**，并**不得**假设底盘会因「没有新指令」而自行停车。Safety Runtime 的停车动作也必须落到「持续发 0」上，而不是「停止发布」。

**实测依据**（2026-10-05 底盘运动验收，完整数据见 `DEVELOPMENT_LOG.md` 与 `PROJECT_STATUS.md` §7）：

| 发现 | 实测 |
|---|---|
| `/cmd_vel` 入口限幅 | ✅ 指令 `vx=+0.30` → 电机实际 `rps=0.7958` = **0.20 m/s**（`app_cmd_vel_callback` 钳到 ±0.2 / ±0.5） |
| `/controller/cmd_vel` 入口 | ❌ **无任何限幅**（`cmd_vel_callback` 直通），且 5 个厂商 app 挂在其上 |
| **指令超时保护** | ❌ **不存在**。停止发布后 `set_motor` 无新消息，但 IMU 振荡幅度仍为 ±0.067 rad/s（对比发 0 时仅 ±0.0015）→ **电机保持最后一条速度指令继续转** |
| 源码佐证 | `ros_robot_controller_sdk.set_motor_speed()` 的报文**不带 duration**；`ros_robot_controller_node` 无 `create_timer` 看门狗、无 `cmd` 超时逻辑 |
| IMU 零偏基线 | +0.00898 rad/s，std 0.00081（`angular_velocity.z`），加速度 z = 9.47 m/s² → 该 IMU 可作运动验证的独立物理量 |

**原因**：
- 底盘控制板是「设置并保持」语义：一次 `set_motor` 报文写入后，固件不会自行归零。这与常见底盘「心跳超时自动停车」的约定**不同**，必须显式记录，否则上层很容易写出「停止发布即停车」的错误安全逻辑。
- `/cmd_vel` 与 `/controller/cmd_vel` 的限幅差异是**隐藏的安全边界**：前者有厂商限幅可当第二道防线，后者没有。这进一步坐实 D-016 选 `/cmd_vel` 的正确性。

**影响 / 约束**：
- ⚠️ **Safety Runtime 的急停必须是「主动持续发 0」**，且要有独立的发布通道 —— 不能依赖「上游不再发指令」。
- 所有 Control Skill 的 `stop()`、异常 `except`、超时 `finally` 路径都必须发 0（本仓库验收工装 `tools/phase0_chassis_motion_acceptance.py` 即按此实现，可作范例）。
- 速度上限由 `odom_publisher` 决定：**`/cmd_vel` 上 linear ±0.2 m/s、angular ±0.5 rad/s**。此上限是**厂商 app 通道的上限**，不等于底盘机械上限；本项目若要更高速度，必须另建入口并自行承担限幅责任（并重做 Safety 论证）。
- **「通信中断是否停车」已用仪器回答**（2026-10-05 第二轮，S2）：详见下节与 **D-021**。
- ⛔ **「运动中拔掉底盘串口」更极端的场景【刻意未测】**：已知指令中断不停车，而断线后也**无法再发 0**（发不进板子），机器人会持续旋转直到厂商栈重启成功；本机**没有物理急停**（D-021）。一个失败模式是「停不下来的旋转机器人」的测试，违反 CLAUDE.md §8「任何运动测试必须保留急停」。**该测试按构造不安全，故不做**。S2 已足以回答这个问题 —— 底盘固件看到的都是「没有新指令到达」。

### D-020 补充实测（2026-10-05 第二轮 · S2，仪器为 LiDAR）

第一轮只能靠 IMU 振荡幅度间接推断「电机还在转」；第二轮改用**独立于桥节点的 LiDAR 转速计**（见 `tools/lidar_rotation_probe.py`），把「指令断裂时板子是否停车」变成了可直接读数的物理量：

| 相位 | 总转角 | 转速 |
|---|---|---|
| 静止 | 0.0000 rad / 2.82 s | **0.0000 rad/s** |
| 发 `wz=+0.15` | +0.5059 rad / 3.90 s | **+0.1298 rad/s** |
| 冻结前发 `wz=+0.15` | +0.3685 rad / 2.82 s | **+0.1308 rad/s** |
| **★冻结桥节点 7 s（指令发不进板子）** | **+0.9369 rad / 6.82 s** | **+0.1373 rad/s（= 冻结前的 105%）** |
| 发 0（显式停车） | +0.0187 rad / 2.93 s | **+0.0064 rad/s** |

> 冻结期间机器人转了 **0.94 rad ≈ 53.7°**，速率与正常指令**无统计差异**。停止发布 = 板子收到零条新指令 = 板子照转。而 4 秒后显式发 0，读数立刻落回 0.0064 → **停车 100% 依赖上层主动发零**。
>
> 方法论：转速用「首帧 vs 末帧互相关」与「~1 s 步长链式累加」两种独立算法求总转角再除以时长，两法在每一相位都吻合到 2~3%，且**不依赖「相邻帧」**（订阅端丢帧时按相邻帧算的速率会被悄悄缩放 —— 实测踩过此坑）。

## D-021：底盘「存活判据」只能是 `imu_raw` / `battery`；断线不自恢复；本机无物理急停

**决策**：

1. **任何「底盘是否在线 / 是否在动」的判断，不得使用 `/odom`，也不得使用桥节点进程状态。**只允许用 `/ros_robot_controller/imu_raw` 与 `/ros_robot_controller/battery`。
2. **本项目必须自己实现串口断开后的重连**，不得假设厂商栈会自恢复。
3. Safety Runtime 的设计前提是**本机不存在物理急停**，因此「停下来」这件事必须完全由软件保证，且必须拥有**独立于 Control Skill 的发布通道**。

**实测依据**（2026-10-05 第二轮 · S3，USB `unbind` 底盘口 `1-2.2`；全程零速，**不动电机**）：

| 信号 | 断线前 | **断线中** | 能否当「底盘在线」判据 |
|---|---|---|---|
| `/odom` | 30.002 Hz | **28.529 Hz（照常发布）** | ❌ **不能** —— 纯死推算，串口断了它照样跑 |
| `/scan` | 10.000 Hz | 9.906 Hz（照常） | ❌ 与底盘无关（LiDAR 在另一个 USB 口） |
| `/ros_robot_controller/imu_raw` | 有消息 | **❌ 无消息** | ✅ 能 |
| `/ros_robot_controller/battery` | 有消息 | **❌ 无消息** | ✅ 能 |
| 桥节点进程 | PID 26198 | **仍存活**（三轮实测三种行为：带死 fd 苟活 / **退出** / 静默存活） | ❌ **不能** —— 三次实测三种行为 |

**断线后仅重新 `bind` 不会自恢复**：桥节点 PID 不变、`imu_raw` / `battery` 仍旧无消息；必须 `sudo systemctl restart start_app_node.service`，重启后新 PID 28244、`/odom` 回到 30.000 Hz、遥测恢复（观察值约 6~18 s 内恢复）。重连后设备会**重新枚举**（`/dev/rrc` 实测在 `ttyACM1` / `ttyACM2` 之间跳变，udev 会正确重建符号链接，但**持有旧 fd 的进程不会自己换过去**）。

**本机没有物理急停**（源码实证）：`~/wifi_manager/button_scan.py`（PID 697，开机自启，同样打开底盘串口）读取 Jetson GPIO 25 / GPIO 4，但 `os.system('sudo halt')` 一行**被注释掉**；KEY2 长按只调 `board.set_buzzer()`。`/ros_robot_controller/button` 话题存在但**行为未验证**。→ **唯一的停车手段是软件持续发 0，或直接断电。**

**原因**：
- `/odom` 的 twist 是 `odom_publisher.cal_odom_fun()` 对**订阅到的指令值**积分而来（D-020 已记录），它反映的是「我们发了什么」，不是「板子是否还活着」。拿它做 watchdog 的输入，等于 watchdog 监视自己。
- 桥节点 `ros_robot_controller` 对串口断开**没有重连逻辑**：无论进程是退出还是带死 fd 苟活，都不会重新 `open()`。把它「还在进程列表里」当成健康信号会得到**假阳性**。
- 厂商栈是 systemd `Restart=always` 的整栈服务，**没有单节点重连能力** —— 恢复粒度是「重启整个厂商栈」，代价是几秒到十几秒的全栈中断。

**影响 / 约束**：
- ⚠️ **Safety Runtime 的底盘存活探测必须订阅 `imu_raw` / `battery`（或直接自持串口）**，**绝不能**订阅 `/odom` 或轮询 `pgrep ros_robot_controller`。这是**本项目必须自己实现 Watchdog 的具体形态**（ARCHITECTURE.md §6.2）。
- ⚠️ **断线后的恢复要靠本项目自己的重连逻辑**；在 Phase 1 自建 Driver 之前，只能靠重启厂商栈，且**重启期间底盘不可控** —— 这段时间必须按「底盘不可控」处理，而不是按「底盘已停」处理。
- ⚠️ 「检测到断线」到「重新可控」之间存在**秒级窗口**，而 D-020 已证明这期间底盘会保持最后速度。→ 这构成了一个**必须写进 Safety Runtime 设计的安全窗口**：理想方案是**让底盘自己会停**（例如后续评估更底层的固件/硬件级改造），而不是靠上层追赶。
- 「物理急停」与「遥控优先级」**仍未验证**，列为 `PROJECT_STATUS.md` §6 待办；在补齐之前，任何运动测试都必须有人在场并**能直接断电**。

## D-022：相机「内容延迟」仅约一帧，但 `header.stamp` 比真实采集时刻早 0.72 s；语音盒卡在一条过期 udev 规则

**决策**：

1. **相机硬件判定为「可用」**，Phase 4 视觉功能按 **端到端延迟 ≈ 一帧（20~45 ms）** 做预算。
2. **但图像 `header.stamp` 不可信** —— 比真实采集时刻早约 **0.72 s**（稳态 −741 ms、抖动仅 12 ms）。**任何用到图像时间戳的融合（TF 查询、与 `/odom` 对齐、目标位置计算）都必须先在自己的 Driver 层重新打时间戳**，不得直接使用厂商 `usb_cam` 的 `header.stamp`。
3. **相机话题速率 22.6 Hz 是主机侧丢帧**，既不是设备能力，也不是订阅端解析慢。
4. **语音盒音频硬件判定为「可用」**：控制串口 / 录音 / 播放三项全部实测通过；`/dev/ring_mic` 缺失**只是 udev 规则路径过期**，已修正。
   > ⚠️ **2026-10-06 更正口径**：这里通过的是**音频硬件三项**，**不含唤醒**。当时把"厂商 ASR 栈正常启动"当成了"语音可用" —— **那验证的是节点起得来，不是能唤醒**。**第七轮实测：唤醒不通**（人声 + 四个本地 TTS 合成的候选唤醒词全部零事件，见 **#25**）。**"语音盒硬件通过"应读作"麦克风与扬声器可用"，不是"语音链路可用"。**

**实测依据**（2026-10-05，人工在场）：

### 相机端到端延迟 —— 用「传感器端打光」当探针

`v4l2` 的 `brightness` 是 ISP 数字偏移、**逐帧立即生效**。在 `t_cmd` 时刻改变亮度，看画面变化出现在哪一帧：

| 订阅 | 收到的时刻 − 下发时刻 | 该帧 `header.stamp` − 下发时刻 |
|---|---|---|
| `/depth_cam/rgb0/image_raw`（614 KB） | **+111 ~ +135 ms** | −604 ~ −628 ms |
| `/depth_cam/rgb0/image_compressed`（~30 KB） | **+19 ~ +44 ms** | −692 ~ −716 ms |

- 只有 `image_compressed` 那条 19~44 ms 是相机管线的真实贡献（约一帧）；raw 多出的约 90 ms 是**订阅端在 Python 里解析 614 KB 的开销**，不是相机的。
- 内容在 `t_cmd` 就变了，**携带该内容的帧的时间戳却落在 `t_cmd − 0.6~0.7 s`** → **内容新鲜、时间戳陈旧**。
- 稳态偏移：raw **−741.2 ms**（抖动 12.4 ms，306 帧）、compressed **−737.8 ms**（抖动 21.9 ms，340 帧）。两条话题一致。

### 被排除的解释

| 假设 | 否证 |
|---|---|
| 订阅队列积压 | 全新 `depth=1 + BEST_EFFORT` 订阅者的**第一条消息**就已 −738 ms，且此后不收敛 |
| 仿真时钟 | `use_sim_time: false`，全系统无 `/clock` 话题 |
| ~~启动时冻结的「单调→实时」换算基准~~ ⚠️ **这一条 2026-10-06 已撤回** | 当时的否证是「服务启动至今 `(实时−单调)` 仅变化约 **0.04 s**」——那个测量**只在"本次会话之内"成立**，**看不见两次会话之间发生的时钟跳变**。2026-10-06 实测陈旧量为 **338.6 s**，与该次开机的时钟前拨量（≈339 s）吻合，该假设被**重新坐实**。详见 **#24** 与 D-023 的 2026-10-06 补充 |
| 同一话题有两个发布者交错 | `ros2 topic info -v` 实测 **Publisher count = 1**（`/usb_cam`；`/yolo` 是订阅者） |
| USB 带宽不足 | dmesg 无任何 UVC 带宽/等时错误；相机独占 `Port2→Port3` 的 480M 链路，单进程持有 `/dev/video0` |

## D-023：自建相机 Driver（Overlay）——时间戳三档策略 + TF 用 REP-103 光学约定

**背景（2026-10-05 第四轮）**：D-019 当时决定"先沿用厂商 `usb_cam` 分支，**暂不自建 Driver**"，
以便尽快拿到图像。现在图像已稳定，而第二/三轮的两项实测结论要求必须有一层自己的
Driver 来收口：**#23 时间戳不可信**（早 0.72 s）与 **#16 `camera` 帧不在 TF 树**。
故建 Overlay 工作区并落地 `embodied_camera_driver`（架构分层中的 **Driver 层**）。
本决策**取代 D-019 中"暂不自建 Driver"的表述**，其余（先走厂商 `usb_cam`、单目基线）不变。

**决策 1：时间戳策略给出三档，默认 `corrected`。**

| `stamp_source` | 输出时间戳 | 用途 / 误差 |
|---|---|---|
| `original` | 原样透传厂商 `header.stamp` | 复现问题 / 对照实验；误差 −0.72 s |
| `receipt` | 本节点收到该帧的时刻 | 恒为正值（图像只会"晚"不会"早"）；误差 = 传输延迟，几十 ms |
| `corrected`（默认） | `receipt − pipeline_latency` | 最接近真实曝光时刻；`pipeline_latency` 默认 **110 ms**（2026-10-06 实测标定，见下） |

理由是**不发明无法验证的修正量**：`pipeline_latency` 是**参数**而非硬编码常数，
且 Driver 的诊断话题会**同时报出**「原始时间戳的陈旧量 / 实测帧率 / 施加的修正量」，
便于日后实测校准。选 `corrected` 而非 `receipt`，是因为我们知道传输延迟的量级
（约一帧），减掉它严格优于不减。

> ⚠️ **2026-10-06 修正**：`pipeline_latency` **不是物理常数，而是随负载变化的量**
> （2026-10-05 该管线约 30 ms，2026-10-06 为 110 ms）。默认值取最近一次实测值，
> **换负载或重启厂商栈后应重标**。

**决策 2：TF `camera_link0 → camera` 用 REP-103 光学约定（rpy = −π/2, 0, −π/2）。**

- 即 **z 前 / x 右 / y 下**（相机光学坐标系标准）。这样把相机图像与 3D 目标投影
  （D-007）接起来时，坐标约定与 ROS 生态一致。
- ⚠️ **明确不沿用**厂商那条例子的四元数 `(-0.7071, 0, -0.7071, 0)`（那是 x=上/y=右/z=前，
  见 #16 的分析）。
- ✅ **2026-10-06 已实机校验通过**：把物体放在**机器人前方偏右、低于镜头**处来回晃动，
  对 `/embodied/camera/image` 相邻帧做差分并取变化象素质心，与 `camera_info` 的光心
  (323.6, 238.6) 比较 —— **513 次检出全部落在画面右侧、左侧 0 次**（`du` 中位数 +214 px）；
  静止场景中**地面位于光心下方**。→ **无镜像、无滚转，左右与上下方向正确，参数不需要修正**。
- ⚠️ **校验的边界**：它**没有精确测定 pitch（俯仰）**。相机若相对机身微微仰/俯，这组判据
  看不出来。pitch 的最终依据仍是**厂商 URDF 的 `rpy=0`**（`base_link → camera_link0`），
  本项目未改动它。已记入 `PROJECT_STATUS.md` §7 与 `DEV_NOTES.md` §4。

**决策 3：订阅/发布都用 BEST_EFFORT + depth=1。**

- 与厂商发布端兼容（BEST_EFFORT 是最低要求，稳妥）；
- `depth=1` **只留最新帧**，避免队列积压把延迟算进时间戳——这与 #23 的教训直接相关。

**决策 4：Driver 层职责边界——只做确定性整形，不含任何语义/规划。**

- 本节点只做「重新打时间戳」和「补 TF」两件可验证的事；
- 不订阅 LLM、不做目标识别、不控制任何执行器（CLAUDE.md §0「LLM 绝不参与实时控制」）。

**实测验证（2026-10-05，Overlay 实跑）**：

| 项 | 结果 |
|---|---|
| 编译 | `colcon build` 通过 |
| 独立复核时间戳陈旧量 | **均值 736 ms / 最大 747 ms**（与 D-022 的 −737.8 / −741.2 ms 相互印证，代码路径完全不同） |

### D-023 补充实测（2026-10-06 第五、六轮）—— 标定 `pipeline_latency`，查清厂商戳陈旧量不恒定，并实机校验 TF 朝向

**一、`pipeline_latency` 实测标定为 110 ms（原估计 45 ms）。**

工装仍是 `tools/camera_latency_probe.py`（本轮扩展：`--topic` 测任意话题、`--repeat` 多事件、
`--jitter` 相位抖动、汇总统计；并修掉「把 JPEG 字节流当亮度均值」的缺陷 ——
对 `image_compressed` 必须先解码）。

| 项 | 实测（2026-10-06） |
|---|---|
| 帧周期 T | **44 ms**（输出 19 Hz） |
| 内容端到端延迟（compressed 低开销参照 / 我们的 614 KB 输出） | **+118 ms** / **+138 ms**（14 次事件均值） |
| 输出戳 − 世界事件（标定前 P=45 / 标定后 P=110） | **+88 ms** / **+13 ms** |

标定式：`新值 = 原值 + 「戳−下发」均值 − T/2` = 45 + 88 − 22 ≈ **110 ms**；验证残差 **≈ −9 ms**。

> ⚠️ **方法上的硬要求**：单次事件判读带有 **±T/2** 的帧栅格量化抖动，**必须多事件取均值**；
> 而且**事件间隔必须加随机抖动** —— 相位固定时量化误差退化成固定偏置，均值会跟着偏
> （本轮实测：不加抖动时 14 次事件几乎挤在同一个数上）。这条已写入 `DEV_NOTES.md`。

**二、厂商戳的陈旧量不是常数，而是随开机时钟跳变（见 #24）。**

- 2026-10-06 实测 **338 565 ms**（抖动 12~17 ms，raw 与 compressed 一致），
  与 2026-10-05 的 736~741 ms 相差 460 倍。
- 成因：本机**无可用 RTC**，**每次开机** timesyncd 先按「上次记录的陈旧时间」恢复时钟
  （本次 `17:26:02`），随后 NTP 再**前拨约 339 s**；`usb_cam` 恰在这两者之间启动并
  **冻结了一个 `(实时−单调)` 换算基准**，于是它的 `header.stamp` 永久落后。
  多组独立数字吻合：陈旧量 **338.6 s** ≈ 开机时钟前拨量 **≈339 s**；
  `who -b` 的 17:25 与 `(实时−单调)` 推出的 17:31:29 差 **6.5 min**。
- **影响面只有 `usb_cam` 一个节点**：`/scan` −12 ms、`/odom` −12~15 ms、
  `/tf`（`odom→base_footprint`）−57 ms，全部正常。
- ⚠️ **未做源码级确认**（`usb_cam` 只有 stripped 二进制），也**未逐个验证其它开机自启节点**。

**三、一条被推翻的旧推断。**

⛔ D-022 说「raw 比 compressed 多出的约 90 ms 是**订阅端解析 614 KB 的开销**」——
本轮 30 KB 的 compressed 与 614 KB 的 raw **到达时刻只差 8~20 ms**，该解释**不成立**；
当时那 90 ms 更可能是**该会话里管线本身就慢**（管线延迟随负载在 30~140 ms 间变化）。

**结论**：`corrected` 策略（只用自己的实时钟）**被本轮全部证据进一步支持** ——
它既不依赖那 0.72 s/338.6 s 的厂商偏移，也不依赖偏移的机制。

**四、TF 朝向实机校验通过（决策 2 收口）。**

方法：物体放在**机器人前方偏右、低于镜头**处来回晃动；对 `/embodied/camera/image`
相邻帧做差分（灰度阈值 12、忽略 <300 px 噪声），取变化象素质心，与光心 (323.6, 238.6) 比较。

| 判据 | 实测 | 期望 | 判定 |
|---|---|---|---|
| 水平 | **513 次检出：右 513、左 0**；`du` 中位数 **+214 px**（+120 ~ +267） | 机器人右侧 → 图像右半 | ✅ |
| 垂直 | `dv` 在 −134 ~ +108 摆动（上下都晃过）；静止场景**地面在光心下方** | 机器人下方 → 图像下方 | ✅ |

→ **`tf_roll/tf_pitch/tf_yaw = (−π/2, 0, −π/2)` 确认无误，参数无需修正。**

⚠️ **边界**：本次确证的是**无镜像、无滚转、左右与上下方向正确**（即「相机装反/装歪 90°」
这类会毁掉 3D 投影的错误已排除），但**没有精确测定 pitch**。pitch 的最终依据仍是厂商
URDF 的 `rpy=0`，本项目未改动它。

## D-024：语音安全指令链路——识别侧可复用厂商离线栈，**执行侧必须本项目自己实现**

**背景（2026-10-06 第七轮，语音软件侧验收）**：摸清厂商语音链路后发现，它的**识别侧**恰好满足
D-006 的结构要求，但**执行侧**有一处**沉默的安全缺陷**，不能沿用。

**厂商链路的实际结构（源码级，`vendor_reference/xf_mic_asr_offline`）**：

```text
唤醒词 ──→ 环形麦硬件自己判（/dev/ring_mic 串口，本地）+ 声源角度
              ↓ /awake_node/awake_flag
asr_node ──→ /voice_control/get_offline_result（讯飞【离线】SDK + 本地 BNF 语法）
              ↓ /asr_node/voice_words（std_msgs/String）
voice_control_move ──→ /controller/cmd_vel
```

**决策 1：识别侧（唤醒 + ASR 文本）可以复用。**
整条链路**不经云端、不经 LLM**（`ASR_MODE` 与它无关，该变量只被厂商 `large_models` 读取，#27），
且 `config/call.bnf` 里**本来就有安全词**（中文 `停下`、英文 `stop`），
`GRM_FILE` 的注释明写它是"**用户自修改文件**" → **词表可扩展**。
⚠️ 前提是**唤醒得先修好**（#25，卡点未定位）。

**决策 2：执行侧必须本项目自己重做，理由有二。**

- **① 厂商的「停下」是碰巧成立的，不是设计出来的。** 命令词表里有 `停下` / `stop`，
  但 `voice_control_move.py` 的 `main()` **只处理 前进 / 后退 / 左转 / 右转 / 过来 / 休眠**，
  **没有 stop 分支** —— 它现在之所以能停，**纯粹是掉进了 `twist` 保持初始全零并被 publish 的默认分支**。
  **失效表现是「说了停、车不停」，而且不报错。** D-006 把安全指令的可靠性建立在这种东西上，不可接受。
- **② 它发布到 `/controller/cmd_vel`** —— 即 #19 里那条**完全无限幅**的话题，
  **不是** D-016 规定的 `/cmd_vel`；且角速度写死 **0.8 rad/s**，**超过** `/cmd_vel` 的 ±0.5 rad/s 限幅。

**决策 3：安全指令的停车动作落在本项目自己的 Driver 层，且必须"主动持续发 0"。**
与 D-020 一致 —— 底盘**没有指令超时保护**，停止发布 ≠ 停车。
「识别到 `停下`」→ 本项目自己的 Safety 入口 → **持续发零**，**不经过厂商 app、不经过 LLM**。

## D-025：Motor Driver（Overlay）—— 把四条安全硬约束**封进代码**；默认 `dry_run=true`

**背景（2026-10-06）**：Phase 1 的第二个 Driver。相机 Driver（D-023）收口的是
"**元数据不可信**"；这边收口的是"**执行器不安全**" —— 底盘无指令超时保护（D-020 / #18）、
断线不自恢复且 `/odom` 会撒谎（D-021 / #21）、`/controller/cmd_vel` 完全无限幅（#19）、
**本机没有物理急停**（#22）。这些以前只写在文档里靠人记着，**现在封进代码，上层不必各自记得**。
（也正是 D-024 决策 3 说的"安全停车要落在本项目自己的 Driver 层"的落点。）

**决策 1：话题方向 = 「上层 → 本项目话题 → 本节点 → `/cmd_vel` → 厂商」。**

```text
上层 Skill ──→ /embodied/motor/cmd_vel ──→[本节点]──→ /cmd_vel ──→ 厂商 odom_publisher ──→ 电机
```

这是 **D-016 的细化**：`/cmd_vel` 仍是**厂商侧唯一的令入点**，但**不再直接暴露给上层** ——
"加不加限速、停不停车"不再由每个 Skill 各自保证，只由这一层保证。
方向与相机 Driver 相反（那边是厂商话题进、本项目话题出），但**收口模式是同一种**。

**决策 2：四条硬约束的落点。**

| 约束 | 出处 | 在本节点怎么落地 |
|---|---|---|
| 停止发布 ≠ 停车 | D-020 / #18 | **以固定频率持续发布**（默认 20 Hz），**空闲时发零**；指令超时 `cmd_timeout`（0.5 s）后归零 |
| 存活判据只能是 `imu_raw` / `battery` | D-021 / #21 | 只订阅这两个；遥测超时 `telemetry_timeout` 即判失联并归零。**绝不订阅 `/odom`、绝不用 `pgrep`**（有回归测试守着） |
| `/controller/cmd_vel` 无限幅 | #19 | 发布前**自己再钳一次**（纵深防御，不依赖厂商实现） |
| 停车要能"锁住" | #22（无物理急停） | `~/stop` 服务**锁存**，必须显式 `~/resume` 才能再动 |

**决策 3：默认 `dry_run=true`。**
默认**不向 `/cmd_vel` 发布任何东西**，只把同样的速度发到
`/embodied/motor/cmd_vel_dryrun`。理由：本机没有物理急停，"能真动"必须是**显式打开**的。
代价是"直接 `ros2 launch` 车不动" —— 这是**刻意的**，节点启动时会用 `WARN` 明确说明。

**决策 4：安全相关的时间一律用单调钟（`time.monotonic()`），不用 ROS 时间。**
#24 已实测这台机器的系统实时钟会被 NTP 跳跃（本次 338.6 s）—— 拿它算超时，一跳就失效。

**决策 5：判断逻辑抽到 `safety_gate.py`（纯 Python，不依赖 ROS），便于离线单测。**
本机没有物理急停，这些判断是**唯一的安全依据**，不能让它们散在 ROS 回调里靠"跑起来看着像对"。

**决策 6（2026-10-06 追加）：失联恢复后**不静默复动**，必须显式重新使能。**

D-021 实测的安全窗口是：USB 断线 → `/odom` 照发而 `imu_raw`/`battery` 停发 →
**重新 bind 不自恢复** → 这段窗口里**底盘保持着最后一条速度**（D-020）。
「停不下来」是真实风险。

⚠️ **先划清权限边界**：真正的恢复动作是 `sudo systemctl restart start_app_node.service`，
**需要 root，Driver 自己做不到**。所以本节点只负责窗口的**策略侧**：

| 阶段 | 本节点行为 |
|---|---|
| 遥测超时 | 判 `link = lost`，**持续发零**，发事件 `chassis_link_lost` |
| 恢复 | 判 `link = alive`，发 `chassis_link_recovered` |
| **是否需要重新使能** | **仅当失联那一刻底盘"可能还在动"**（存在**未超时且非零**的指令）→ 置位 `needs_rearm`，发事件 `rearm_required` |
| 重新使能前 | **即使上层继续以 20 Hz 发指令，也一律输出零**（状态码 4 = `rearm_required`） |
| `~/resume` | 清除 `needs_rearm`（与清除停车锁存合为同一个动作），发事件 `rearmed` |

**为什么危险的不是"旧指令被重放"而是"上层一直在发"：** 存指令在失联时已被作废，
所以重放不是问题。真正的问题是**上层可能一直在发同一条指令** —— 链路一恢复，那条指令
**立刻生效**，机器人会在链路回来的一瞬间**毫无预兆地继续跑**，
而操作者此刻正以为它是停着的，甚至可能正在搬它。**这是"恢复"时刻特有的危险**，
所以必须由人（或上层）显式确认一次。

**为什么只在"当时可能还在动"时才要求：** 失联前本来就是静止/零指令，恢复后没有理由多要一次确认
（否则每次瞬断都要人工点一次，久而久之就会被无脑点掉）。

⚠️ 启动阶段（从未收到过遥测）**不算失联**，不报事件 —— 否则每次开机都先来一次假警报。

**实测验证（2026-10-06，干跑模式，车未动）**：

| 项 | 结果 |
|---|---|
| 编译 / 单测 | `colcon build` 通过；**14 项单测全过**（`pytest test/test_safety_gate.py`） |
| **`/cmd_vel` 发布者数** | **0**（干跑期间也必须是 0 —— 这是"车动不了"的直接证据） |
| 持续发布 | 干跑话题 **19.998 Hz** 连续发布，空闲时 `Twist` 全零 |
| 限幅 | 发 `(+0.9, −0.5, +3.0)` → 日志 `指令被限幅 ... -> (+0.200, -0.200, +0.500)`，干跑话题上未出现任何超限值 |
| 指令超时 | 停发指令 0.5 s 后 `状态 -> no_cmd` 并归零 |
| 锁存停车 | `~/stop` → `状态 -> stopped`；`~/resume` → `状态 -> ok` |
| 遥测失联 | 启动时（遥测未到）即 `状态 -> telemetry_lost` 且输出零 |

**顺带实测到的两个速率**（用来定 `telemetry_timeout`）：`imu_raw` **46.9 Hz**、
`battery` **0.95 Hz（周期 1.05 s）**。⚠️ 所以超时阈值必须按**最慢**那一路留余量 ——
按 imu 的周期去定，imu 单独失效时会跟着 battery 的节拍在阈值上下反复抖动。取 **2.5 s**。

**实测验证 · 失联与恢复（2026-10-06，用**假遥测**制造，零硬件风险）**

方法：把 `imu_topic` / `battery_topic` 指向两个测试话题，由脚本以 47 Hz / 1 Hz 喂假遥测；
上层**全程以 20 Hz 发 0.2 m/s**（这正是危险场景）。

| 时刻 | 观测 | 判定 |
|---|---|---|
| 0.0 s | 输出 0.000（遥测未到） | ✅ |
| 0.4 s | 输出 **+0.200** | ✅ |
| 6.0 s | 切断假遥测 | — |
| **8.5 s** | 输出 → **0.000**，事件 `chassis_link_lost` | ✅ 检出延迟**恰好 = +2.5 s**，与 `telemetry_timeout` 精确吻合 |
| **12.0 s** | 事件 `chassis_link_recovered` + **`rearm_required`** | ✅ |
| **12.0–18.0 s** | **上层一直在发 0.2 m/s，输出始终为 0** | ✅ **核心：不静默复动** |
| **18.0 s** | 调 `~/resume` → 输出 **+0.200**，事件 `rearmed` | ✅ 显式确认后才恢复 |

**遗留**：
- 🔴 **真机运动未测**：需要人工看护 + 能直接断电（本机无物理急停），且必须显式 `dry_run:=false`。
- ⬜ **真恢复仍须人工**：重启厂商服务需要 root，本节点做不到。
  若要自动化，需要一个**有权限的辅助程序**（如只允许重启那一个服务的 polkit 规则）——
  那是**系统级改动，须用户单独决策**，本轮未做。
- ⬜ 未接 `odom_publisher` 的往返验证（真机运动时一并做）。

## D-026：Control Skill 层——接口形式用 **service**（不是 action）；第一版**开环**；一次只跑一个动作

**背景（2026-10-06）**：Phase 2 的第一个落地（`embodied_control_skills` +
`embodied_skills_interfaces`）。本决策同时**回答 D-011 里"跨语言 IPC 具体形式待定"**那一项
—— 至少对 Control Skill 这一层给出答案。

**决策 1：Control Skill 的 IPC 用 service，不用 action，也不裸用 topic。**

- 这些原语是**确定性、有界、短时**的（≤ 1 m / ≤ 180°，开环 7 s 内结束），
  请求-响应语义天然贴合"走到这儿，告诉我成了没有"。
- **action 的价值是「过程反馈」+「可取消」，这两样在当前阶段都不成立：**
  - **反馈**：开环没有可靠的进度可报，报一个假进度只会误导上层；
  - **可取消**：已经由**独立的 `~/stop` 服务**提供，而且它比 action 的 cancel 更贴近
    安全层的用法 —— 安全层要的是"**停**"，不是"取消某个 goal id"的流程。
- **升级路径写在这里，免得后人以为 action 是被忽略的**：一旦有了闭环反馈
  （里程计 / 激光 / 视觉），"进度"才有真实含义，那时再换成 action。

**决策 2：一次只跑一个动作；运动中再来请求 → 直接拒绝（busy），不排队。**
排队会让"车现在到底在不在动"变得不可预测，而安全层**必须**能回答这个问题。

**决策 3：服务回调必须用 `ReentrantCallbackGroup`（配合 `MultiThreadedExecutor`）。**
服务回调会**阻塞到运动结束**。用 `MutuallyExclusiveCallbackGroup` 时，
"运动中来的第二个请求"不会被拒绝，而是**排在后面等**——变成一个隐藏队列，
而且 `~/stop` 会**排在最需要它的那一刻之后**。**这是实测踩出来的**（见 `DEV_NOTES` 坑 10）。

**决策 4：第一版只做开环，且只做**纯平移 / 纯旋转**。**
不做"平移 + 旋转一次完成"：对全向底盘，**机体速度恒定 ≠ 世界系走直线**，
同时旋转时终点位置会随朝向弯曲。要正确做"走到某相对位姿"必须先解算
「转到目标朝向 → 平移 → 转回目标朝向」，而且**必须有反馈**才能闭合。
开环硬凑出来的东西会"看起来动了、位置是错的"——所以**明确不做**，而不是做得似是而非。

> ⚠️ **因此 `success` 的含义是"速度按时长发完了"，不是"真的走到位了"。**
> 这句话写进了 `.srv` 注释、launch 文件与 `motion_plan.py` 顶部，**不是可有可无的免责声明**——
> 上层的每个后续设计都要以它为前提。

**决策 5：护栏分两层，互不替代。**

| 层 | 管什么 |
|---|---|
| Motor Driver（D-025） | **速度**：±0.2 m/s / ±0.5 rad/s |
| Control Skill（本决策） | **单次位移 / 转角上限**：1 m / π rad —— 这是 Driver 管不到的维度 |

且本层**断言**规划出的速度不超限：超了就**拒绝运动**，而不是让它被 Motor Driver 静默钳掉
——被钳掉意味着**实际位移与时长都对不上，而调用方拿到的却还是 success**。

**决策 6：前置条件——底盘未确认在线就拒绝运动。**
订阅 Motor Driver 的 `/embodied/motor/status`（D-025）。状态**陈旧**、或为
`telemetry_lost` / `stopped` / `rearm_required` 时，一律拒绝。

**实测验证（2026-10-06，干跑，车未动）**

方法：Skill 只发速度，Motor Driver 在 dry-run 下把速度原样发到干跑话题，
于是**把速度序列对时间积分**就得到"实际被命令走过"的位移/转角 ——
**车不动，"该走 0.5 m 到底发出多少米"却是可以量出来的**。

| 用例 | 期望 | 实测 |
|---|---|---|
| `move_relative(0.5, 0)` | ∫vx ≈ 0.500 m | **+0.495 m**（误差 −0.005）；侧向 ∫vy=0.0000、∫wz=0.0000 |
| `rotate(π/2)` | ∫wz ≈ 1.5708 rad | **+1.560 rad**（误差 −0.011） |
| `move_relative(0.3, 0.4)` | ∫ ≈ (0.300, 0.400) | **+0.297 / +0.396** |
| `move_relative(2.0, 0)` 超上限 | 拒绝 | ✅ 返回失败，且**积分 0.0000**（确实没发出任何速度） |
| 运动中再来一个请求 | 拒绝（不排队） | ✅ `正有一个动作在执行，拒绝新请求` |
| 运动中 `~/stop` | 立即中止 | ✅ `stop 立即返回成功`；只走了 **+0.045 m**（0.35 s 内停下）；被中止的请求返回失败 |
| **Motor Driver 不在跑** | 拒绝运动 | ✅ `Motor Driver 状态已陈旧 14.8s —— 拒绝运动` |

单测：`motion_plan` **19 项全过**（钉住"恒定速度 × 时长 == 请求位移"这条积分性质）。

**遗留**：
- 🔴 **真机运动未测**（需人工看护 + 能直接断电）。
- ⬜ **闭环未做**：现在没有里程计/激光反馈，"走没走对"无从校验（`success` 不代表到位）。
- ⬜ `move_forward(d)` 是 `move_relative(x=d, y=0)` 的特例，**未单列服务** —— 需要时再加。

## D-027：Safety Runtime 第一版——本地安全指令通路 + **独立零速通道**

**背景（2026-10-06）**：项目的核心主张是 **`Safety > Control > Skill > Agent`，Safety 具有最终否决权**。
但此前"停"这件事是**散着**的：Motor Driver 有锁存停车（D-025）、Control Skill 有 `~/stop`（D-026），
**没有一个"最终否决权"的落点**。而 D-006 明确要求安全指令**本地解析、绕过 LLM**，
D-024 决策 3 又明确**执行侧必须本项目自己做**。本决策是这条线的第一个落点。

> ⚠️ 按 `plan.md` 的相位划分，Safety Gateway 属 **Phase 6**；本版是**提前开始**
> —— 因为 D-006 的要求**在当下就成立**（"没有物理急停"这条约束今天就压着，
> 见 #22 / D-021），而不是等 Agent 层建好才需要。

**决策 1：安全指令的「识别侧」复用厂商离线 ASR 文本，「执行侧」完全自建。**

订阅厂家 ASR 的文本话题；**匹配在本节点内完成**（纯 Python，可离线单测）。

⚠️ **一个字都不经过 LLM，也不经过厂商的 `voice_control_*` 节点** ——
后者正是 **#26** 里「`停下` 在词表里、却**没有对应处理分支**、靠掉进默认零 Twist 碰巧成立」
的那条路，**绝不能复用**。

**决策 2：必须有一条独立的零速通道 —— 本节点自己直接向 `/cmd_vel` 发零。**

理由链是完整的：底盘**没有指令超时保护**（D-020），所以"停止发布 ≠ 停车"；
而"持续发零"这件事目前**只在 Motor Driver 里**（D-025）——
**它自己挂了就没人发零了**，底盘会一直保持最后一条速度跑下去。

所以急停通道必须**不依赖 Motor Driver 存活、也不依赖 Control Skill 存活**。
另两个 `~/stop` 服务照发（best-effort），但**急停不靠它们成立**。

> 🔒 **本节点唯一的发布语句是 `zero_pub.publish(Twist())`** —— 它在**结构上**不可能发出
> 任何非零速度。这是代码保证，不是约定；验收里也把"非零帧数必须为 0"当成一条断言。

**决策 3：急停锁存，必须显式 `~/release`；且三道锁互相独立。**

解除急停这个动作本身必须是一次明确的、有人（或上层）负责的决定。
本节点的锁、Motor Driver 的停车锁存、Control Skill 的动作中止**各有各的恢复入口**，
解除一处**不会**自动解除另一处 —— 这是刻意的。

**决策 4：安全词用「整句匹配」，不用子串匹配。**

这是本决策里**最需要留痕**的一条：它是一个**取舍**，不是一个"更好的做法"。两种错法都想过：

| 方案 | 会怎么错 |
|---|---|
| **子串匹配** | 安全词表里只要有个 `停`，厂商词表里的 `停止追踪` / `停止分拣` / `stop tracking` **全部会误触发整机急停**。用户说"停止追踪"机器人停住，再说一次还是停住 —— 安全通路迅速变成"一个动不动就整机停住的按钮"，**很快会被当成故障而不是保护** |
| **整句匹配**（本实现） | **可能漏掉没想到的说法**。缓解：① 词表可配置，可加现场常用说法；② 厂商 BNF 语法本来就**把可识别词限制在固定集合**里，ASR 不会产出任意句子，所以"没想到的说法"实际很有限 |

**决策 5：对 Motor Driver 的停更看门狗 —— 它挂了就**自动接管**。**

决策 2 只解决了"**已经**知道要停"的情况。还有一种更隐蔽的：**根本没人知道要停** ——
Motor Driver 进程自己死了。它既不报错、也没人转告，而底盘会保持最后速度一直跑。
（本机没有物理急停，#22；这一条是**最后一个没有防线**的失效模式。）

所以本节点监视 Motor Driver 的状态话题：**停更超过 `motor_watchdog`（默认 2 s）即自动急停**，
由本节点接管发零。

⚠️ **首次见到之前永不判失联**（`watchdog.py`）—— 与 D-025 链路状态机"startup 不算 lost"同一条原则：
假警报会把真警报淹掉。

⚠️ **Motor Driver 仍未恢复时，拒绝 `~/release`。** 解除就等于本节点停止发零，
而那时**没有别人在发零**，底盘会跑下去。与其"解除了又立刻重新锁存"（看起来像 bug），
不如明确拒绝并说清原因。

**实测验证（2026-10-06，全程 **Motor Driver 未启动** —— 这正是要验的）**

| 检查 | 结果 |
|---|---|
| `go forward` / **`停止追踪`** / `唤醒成功(wake-up-success)` | ✅ **都不触发**，且**没向 `/cmd_vel` 发过任何东西** |
| 本地识别到 `停下`（走真实解析路径，非直接调服务） | ✅ 立刻锁存，事件 `estop_triggered:voice:停下` |
| 独立零速通道 | ✅ 约 **10 Hz** 持续发零，**非零帧数 = 0** |
| 锁存期间说别的 | ✅ **不解除** |
| `~/release` | ✅ 显式解除后才停发零；解除后 1 s 内 **0 帧** |
| `~/estop` 服务 | ✅ 也能触发（给未来的上层留入口） |

**看门狗单独验（用假状态话题模拟"Motor Driver 进程死掉"）**：

| 检查 | 实测 |
|---|---|
| **从未见过** Motor Driver | ✅ **不报失联**（假警报会淹掉真警报）；status 里 motor 龄为 −1 |
| Motor Driver 在线（喂 20 Hz 状态） | ✅ 不报警，且**没向 `/cmd_vel` 发过任何东西** |
| **状态停更 3.5 s**（看门狗 2.0 s） | ✅ **自动锁存**，事件 `estop_triggered:motor_driver_lost`，开始发零且**非零帧数 = 0** |
| 仍未恢复时调 `~/release` | ✅ **被拒绝**：`拒绝解除：Motor Driver 状态仍停更 3.5s —— 解除会让底盘无人发零（D-020）` |
| 恢复后再调 `~/release` | ✅ 成功解除，且解除后 1 s 内 **0 帧** |

单测：`estop` + `watchdog` 共 **45 项全过**。

**遗留**：
- ⬜ **本版不含**：避障、速度/区域限制、Agent 侧 Skill 网关。
- ⬜ **真机未验证**（本节点只会发零，所以风险为零；但"发零真的能让底盘停下"这条
  只有真机运动测试才能确认）。

## D-028：LiDAR Primitive——不做"收口"，做**查询原语**；且"不知道"绝不等于"安全"

**背景（2026-10-06）**：Phase 1 的第三个 Driver/Primitive。
⚠️ 与相机（D-023）、电机（D-025）**不同**：厂商的 `/scan` 本身**是对的**
（实测 10.00 Hz、360°、`frame_id=lidar_frame`、TF `base_link→lidar_frame` 已就位，
见 PROJECT_STATUS §7），**没有可收口的元数据问题**。所以本包的定位不是"修"，是"**加**"。

**决策 1：本包提供的是查询原语，不是转发。**

上层真正要问的不是"这一圈点云长什么样"，而是「**我这个方向、这个距离内有没有东西**」。
提供三层：

| 接口 | 语义 |
|---|---|
| `/embodied/lidar/front`（话题，每帧更新） | 前方扇区（默认 ±30°、≤3 m）的最近回波 |
| `~/sector_min_range`（服务） | 任意扇区的最近回波 + 点数 |
| `~/path_clear`（服务） | 某方向在给定距离内是否通畅 |

让它成为原语而不是各写各的，理由是下面这个坑 —— 它**不单测几乎必然会写错**。

**决策 2：扇区查询必须按角度差算，不能按下标切片。**

⚠️ LD19 的 `/scan` 是 `angle_min=0`、逆时针增大、`angle_max=2π`。
所以「**正前方 ±30°**」在数据里**不是一个连续的下标区间**，而是
**330°~360°（下标靠后）** 加上 **0°~30°（下标靠前）**两段。
任何"找到起点角度、然后切一段数组"的写法都会**静默漏掉一半扇区** ——
而且漏掉的恰好是最该看见的那一半（接缝两侧）。

本实现一律用**最短有符号角差**（`scan_query.angular_diff`）判定，并有专门的单测
（`test_min_range_across_the_seam`：把最近回波放在接缝另一侧，验证它确实被算进来）。

**决策 3：「不知道」绝不报成「安全」。**

这是本决策里最需要留痕的一条，两种情况必须分清：

| 情况 | `path_clear` | 为什么 |
|---|---|---|
| 扫描**新鲜**、扇区内无回波 | `clear=true, range=-1` | 空旷时本来就该通畅 —— 但 `range=-1` 让调用方**看得出这是假设而不是证据** |
| 扫描**陈旧/从未收到** | **`clear=false`, range=-1`** | **不知道 ≠ 安全。** 把这种情况报成 true，等于在"传感器挂了"的时候告诉上层"前面没东西" |

**决策 4：接口注释里写清 `clear=true` 的边界。**
它只说明**这个扇形、这个距离内没有回波**，**不保证路径整体安全** ——
旁边可能有东西、地上可能有坑、回波可能被吸音材质吃掉。
把语义边界写进 `.srv`，上层才不会把 `clear` 当成"可以放心走"。

**实测验证（2026-10-06，对**真实雷达**）**

手法是**独立重算**：脚本自己订阅 `/scan`、自己按角度差算一遍，再与节点的答案比。
只看"节点有没有输出"是证明不了它算得对的。

| 检查 | 结果 |
|---|---|
| `/embodied/lidar/front` 速率 | **9.999 Hz**（与 `/scan` 的 10 Hz 一致） |
| 流式输出 vs 独立重算 | **32/32 帧**都能对上（对齐最近几帧之一，容忍话题配对错开） |
| `sector_min_range` vs 独立重算 | **逐位一致**：节点 `valid=True, 0.244 m, 83 点` = 重算 相同 |
| 宽扇区（120°，跨接缝）vs 独立重算 | **逐位一致**：`0.129 m / 167 点` |
| 无扫描数据时 `path_clear` | ✅ `clear=False, range=-1`（不知道 ≠ 安全） |
| 无扫描数据时 `sector_min_range` | ✅ `valid=False` |

单测 `scan_query` **30 项全过**。

⚠️ **同轮观察到一个环境条件（不是缺陷，但会影响后续）**：当前 504 个点里
**340 个（67%）在 0.6 m 以内**，且距离随角度平滑变化（0° 时 0.251 m、30° 时 0.294、
60° 时 0.544 —— 呈 `d/cos θ` 形态，像是正前方约 0.25 m 处有一个**平整面**），
另有 198°~359° 的一圈 0.10~0.28 m。**后果：`path_clear(±30°, 1 m)` 恒为 false**，
这个原语在当前摆位下无法给出有意义的"通畅"。
**成因未定**（外部环境 vs 雷达看到机器人自身结构），**需要人到场确认**
（把车挪到开阔处或吊起来再看这几段回波在不在）。这也提醒：**将来定避障阈值
必须基于真实环境实测**，不能拍一个数。

**补充（2026-10-07）：上面那条「环境条件」已判明 —— 是外部环境，不是自身结构。**

判别法不是看"距离多近"，而是看**回波跟不跟着车走**：自身结构与雷达固连，
换个地方还在同样的角度上；环境回波随摆位而变。工装 `tools/lidar_environment_probe.py`
（本次新增）把剖面量化下来，两次摆位对比：

| 项 | 2026-10-06（原地、局促） | 2026-10-07（挪到另一处） |
|---|---|---|
| 近场占比（< 0.6 m） | **67%** | **3.6%** |
| 贴身回波（中位 < 0.35 m） | 有，198°~359° 一整圈 0.10~0.28 m | **完全消失** |
| 前方 ±30° 每帧最近回波 | 0.244 m | 0.537 m |
| 前方 ±60° 的 `d·cosθ` | 像 0.25 m 处一个平整面 | std **0.28~0.52 m**（随分格宽度而变），不像单一平整面 |

→ 两块近场回波**都没跟着车走** → **外部环境**。
⇒ **不需要做"自身结构回波剔除"掩膜**（原「遗留」第 2 条据此关闭）。

⚠️ **两条边界，不要夸大**：
1. 本次场地**并不大**（用户说明"空间比较小"）。判据要的是"**两次摆位不同**"，
   不是"某一次足够开阔"，所以这个结论成立；但**"转车 90°"那条更严的判别法没做**。
2. **`path_clear(±30°, 1 m)` 现在仍然是 `false`** —— 此时它是**正确答案**
   （车前方 0.54 m 处确实有东西），不是原语失效。**换个场地它就是另一个值。**

**遗留**：
- ✅ ~~上述环境条件待人工确认~~ → 2026-10-07 判明为外部环境（见上）。
- ✅ ~~未做"自身结构回波剔除"~~ → 不需要做（见上）。
- ⬜ **避障阈值必须在真实部署环境实测标定**：近场占比在两次摆位间从 3.6% 变到 67%，
  **任何拍出来的固定阈值都会被场地否决**（这条比原观察更强）。
- ⬜ 未接闭环（这是 Control Skill 从开环走向闭环的候选反馈源之一，但需要一个决策：
  用什么当"走了多远"的反馈，以及如何与 D-021「`/odom` 不能当存活判据」共存）。

## D-029：上层控制流三方对齐 —— **Registry 是数据、Gateway 是唯一准入点、Skill Manager 是执行器**

**背景（2026-10-07）**：`plan.md` §19、`ARCHITECTURE.md` §5.1、D-003 三处对"Agent 怎么到达 Skill"说法不一致：

| 出处 | 说法 |
|---|---|
| `plan.md` §19 | `Agent → Safety Gateway → Skill Manager` |
| `ARCHITECTURE.md` §5.1 | `Agent → Tool/Skill Registry → Skill Manager`（**Gateway 没出现**） |
| D-003 | 「Agent **只能**调用 Semantic Skill」 |

三者**看起来**是三条不同的路，其实是在描述同一跳里的三个职责。

**决策 1：统一为一条控制流。**

```text
Agent（agent_runtime）
   ↓  ~/invoke（SkillInvoke 信封，D-031）
Skill Gateway          ← 唯一准入点：六项检查（D-005）+ 任务生命周期
   ├─ 查 Skill Registry（**数据**：有哪些技能、参数与策略边界、权限、超时）
   └─ 派发到技能           ← 这一部分即"Skill Manager"的职责
   ↓  强类型 .srv（复用既有接口）
Control / Autonomous / Semantic Skill
```

`ARCHITECTURE.md` §5.1 那一行改写为
`Agent → Skill Gateway（查 Registry）→ Skill Manager → ...`，
并在 §6.1 的 Gateway 框图里注明 **Registry 是 Gateway 查的数据，不是一个并列的跳**。

**决策 2：D-003 的「Semantic Skill」修正为「task-tier（Autonomous + Semantic）」。**
D-003 写"Agent 只能调 Semantic Skill"，但 `ARCHITECTURE.md` §3/§8 又让 Agent 调
`navigate_to` —— 那是 **Autonomous** Skill。两处矛盾。统一表述为**task-tier**：
Autonomous 与 Semantic 同属"Agent 可以命名"的那一层，Control 及以下不属于。

**决策 3：D-003 靠 **Permission 检查**执行，不靠"物理上没有别的入口"。**
注册表里每个技能声明 `allowed_principals`；`control.*` 一律**不含** `agent.planner`。
Gateway 的 Permission 检查是**唯一**能真正执行这条架构红线的地方 ——
也正因如此它不能是空的。

> 顺带纠正一个可能的误解：D-003 说的"ROS Topic"指**执行器/感知话题**（`cmd_vel`、GPIO…），
> **不是** D-011 认可的 Skill IPC 通道。Agent 调 Gateway 的 service 不违反 D-003，
> 正如 Agent 调 Skill Manager 不违反它。

**决策 4：第一版 `Skill Manager` 不拆成独立进程。**
`registry` / `checks` / `task_table` / `dispatch` 是同一个包里的**模块**。
边界体现在模块与测试上，不体现在进程数上 —— 进程越少、失效模式越少。
文档注明"**可拆**，接口不变"。

**实现**：`embodied_agent_ws/src/embodied_skill_gateway/`。

## D-030：**Agent ↔ Skill Manager 的 IPC 形式**（填掉本文件原来的"待定"格）

**背景**：本文件「待补充的决策」表里，**唯一被点名"仍待定"**的就是这一格；
D-011 也写着"具体 IPC 形式在实现对应 Skill 时确定，并在此追加决策"。

**决策：三件套，全部 service / topic，**不用 action**。**

| 件 | 形式 | 作用 |
|---|---|---|
| `~/invoke`（`SkillInvoke`） | **service** | 准入 + **立即返回** `task_id`（异步受理） |
| `/embodied/skill/events`（`SkillEvent`） | **topic** | 任务级事件；`WAIT` 的唤醒载体 |
| `~/cancel` / `~/get_result` / `~/list` | **service** | 取消 / 查询 / 注册表只读投影 |

**理由：**

1. **事件用 topic 而不是 service 响应或 action feedback**：D-004 要的是"Agent 发起后进入
   WAIT，只有任务级事件唤醒"—— 这是**一对多、异步、可被多方订阅**（Agent、日志、
   将来的 TTS）的东西，天然是 topic。
2. **WAIT 不阻塞**：受理后把 `task_id` 记下来**立刻返回事件循环**，Event Manager 按
   `task_id` 匹配唤醒。**用阻塞等待实现 WAIT，会把 Agent 变成不可取消、不可超时的单线程**，
   与 D-004 的意图正好相反。
3. **超时 = 取消 + 终态事件**，不是"悄悄不再等"。deadline 用 **`time.monotonic()`**
   （本机墙上钟会被 NTP 步进，#24 / DEV_NOTES 坑 13）。
4. **取消必须落到技能的 stop**，不能只把本地等待标记为放弃 ——
   否则"车还在动，上层以为任务结束了"，接着就会把下一个规划建立在假前提上。
   停车的**最终手段**始终是 Safety Runtime 的独立零速通道（D-027）；
   本机制是工艺流程上的取消，不是安全兜底。
5. **不用 action**：本层要的是**离散任务事件**，不是连续进度；且 rclpy 的
   goal-handle / cancel 回调 / result future 是最难离线单测、最容易藏"未验证"bug 的
   三处。**升级路径**见下。

**升级路径（写在这里，免得后人以为 action 是被忽略的）**：
当 task-tier 技能具备**真实的过程反馈**（里程计闭环 / SLAM / 视觉跟踪）时，
把 `invoke` + 事件换成 `ExecuteSkill.action`：`feedback` 携带 `progress`
（**那时它才有真实含义**，不再是 -1），`result` 携带终态。
`SkillInvoke` 的字段形状（`task_id` / `state` / `message`）刻意与之对齐，使调用方改动最小。
**事件话题保留**作为跨订阅者的任务级广播。

**其它约束**：
- **每技能同时只允许一个在途任务**（沿用 D-026 决策 2 的"不排队"原则）——
  不排队是为了让"车现在到底在不在动"永远可回答。
- 任务表**有界**（默认 200）：满了先淘汰**最老的终态**记录；一个终态都没有时
  **拒绝受理新任务**，而不是丢掉还在跑的任务、也不是无界增长（内存只有 7.4 GiB，#7）。

**实现**：`embodied_skills_interfaces/srv/SkillInvoke|SkillResult|SkillCancel|SkillList.srv`
+ `msg/SkillEvent.msg`；`embodied_skill_gateway/skill_gateway.py` + `task_table.py`。

## D-031：Skill 网关对外用**通用信封**，不用逐技能强类型服务

**背景**：Gateway 是对外唯一入口，它长什么样是一个必须现在定的选择。

**决策：`SkillInvoke { principal, skill, args_json, request_id }` 通用信封；
不提供 `/skill_gateway/move_relative` 这类逐技能强类型服务。**

**理由：**

1. **强类型会让六项检查里的「Schema Validation」变成空检查。**
   ROS 的反序列化已经替我们校验了 schema —— 那么这一项就没有任何事可做。
   D-005 的六项是硬约束，**不该有一项在设计上就是空的**。信封把它变成**显式策略**：
   字段缺失 / 多余 / 类型错 / NaN / inf / 跨字段约束，全在 `checks.py` 里，可离线单测。
2. **"注册表是数据"这个要求与强类型自相矛盾。** 若 Gateway 暴露强类型服务，
   "加一个技能"就变成"改接口包 + 重编译"，注册表就不再是数据驱动。
3. **将来 LLM tool calling 天然是动态的**（Phase 7）。信封与 tool-call 同构；
   `~/list` 的投影可直接当 tool schema 用。
4. **语义并没有因此丢失**，只是换了地方写：
   | 语义 | 写在哪 |
   |---|---|
   | 参数含义 / 单位 / 范围 / 权限 / 超时 | **注册表**（`config/skill_registry.yaml`，数据） |
   | 坐标系 / 正方向 / 有效性边界 | **底层强类型 `.srv`**（`MoveRelative` / `Rotate` …） |
   **无类型只被限制在"分发层"，没有渗进语义边界。** 这与本项目讨厌
   `Float64MultiArray` 的理由不冲突 —— 那是讨厌**语义没被写下来**。

**代价与缓解**：

| 代价 | 缓解 |
|---|---|
| 失去 ROS 反序列化层的类型安全，错误推迟到运行时校验 | 校验在 `checks.py` 穷举单测；信封是**唯一**入口，爆炸半径被限制在准入点 |
| `ros2 service call` 手工调试不如强类型直观 | `~/list` 可读投影 + 中文拒绝原因（指明是哪个字段、期望什么） |

**升级路径**：若有非 Agent 的 **C++ 客户端**需要编译期类型，在 Gateway 上**追加**
强类型 façade（如 `~/move_relative`），实现为**同一个注册表 / 校验 / 任务表的薄适配器**，
不新增策略 —— 即 **typed façade / generic core**。
若某技能需要**流式**参数（图像、点云），单独开 typed 通道并在注册表标记 `transport: custom`。

**实现**：`embodied_skill_gateway/checks.py`（`validate_schema`）+ `registry.py`。

## D-032：8 状态机只服务 **task-tier** 技能；**Control Skill 不进状态机**

**背景**：`plan.md` §21 定了 8 个状态
（`STARTED / RUNNING / ARRIVED / TARGET_FOUND / TARGET_LOST / BLOCKED / FAILED / CANCELLED`）。

**问题**：Control Skill 的 `success` 含义是「**速度按时长发完了**」，不是「走到位了」（D-026）。
那 8 个状态里**没有任何一个能诚实表达它**：

- 映射成 `ARRIVED` → **撒谎**。Agent 会以为到位了，**后续规划建立在假前提上**。
- 映射成 `TARGET_FOUND` → 更离谱。
- 其余终态都是失败语义 → 也不对。

硬塞只能编造。而这是一个**安静的、会连锁的**错误 —— 本项目最该避免的那一类。

**决策：两个词汇表，只在 `FINISHED` 这一处分叉。**

| 层级 | 状态 |
|---|---|
| task-tier（Autonomous / Semantic） | 上面 8 个；后 6 个是终态，**也是唯一会唤醒 Agent 的状态**（D-004） |
| control-tier（Control Skill） | `RUNNING / FINISHED / FAILED / CANCELLED` |

> ⚠️ **`FINISHED` 不是那 8 个任务状态之一**，它的含义**只有**「技能返回了」，
> 绝不表示"到位了 / 达成目标了"。

⚠️ **别把"control-tier 不唤醒"误推广**：`FAILED` / `CANCELLED` 是两个词汇表**共用**的
（它们本来就是任务终态），所以它们**仍然会唤醒 Agent**。只有 `FINISHED` 不唤醒。

**配套**：所有结果与事件一律带 **`verified: false`** —— 当前**没有任何独立反馈**
（里程计闭环 / 视觉）能确认目标达成，所以"验证通过"这件事**今天在物理上无法成立**。
上层**不得**把 `verified=false` 读成"已经到位"。
（`checks.validate_result` 里写死了这一点，并有单测钉住。）

**实现**：`embodied_skill_gateway/task_state.py`（纯逻辑，含迁移表与不变式）。

## D-033：未验证代码的三层闸门与**三级验证清单**

**背景**：用户要求"轮不到真机验证的代码可以写，但必须明确标注未验证"。
但真正危险的不是"代码没测过"，而是**默认值把未验证逻辑接进了运动路径**。

**决策 1：三层互相独立的闸门，默认全关。**

| # | 闸门 | 默认 | 拦住什么 |
|---|---|---|---|
| ① | 上层节点的 `allow_motion`（命令路由器、Skill 网关） | **false** | 上层**派发**会动的技能 |
| ② | Motor Driver 的 `dry_run` | **true** | 发到厂商 `/cmd_vel` |
| ③ | Control Skill 的底盘前置条件 | — | 底盘状态不新鲜 / 未确认在线时拒绝运动 |

任意一层没打开，车都动不了。**打开①不等于车会动** —— 这正是"独立"的意思。

**决策 2：三级验证清单，只有第三级才算"未验证"。**

| 级别 | 含义 |
|---|---|
| (a) 离线单测通过 | 纯逻辑可证伪 |
| (b) dry-run 集成通过 | 链路跑通、数值对得上，但**车没动** |
| (c) **真机未验证** | 只有这一级进"未验证清单" |

**标注约定**：源码里写 `# UNVERIFIED(real-motion): ...`；
`PROJECT_STATUS.md` 单列「未经验证的代码」一节。

**决策 3：绝不为任何理由新增对 `/cmd_vel` 的发布者。**
最危险的接线**不是**网关，而是 Safety Runtime 已经占用的那条 `/cmd_vel` 通道 ——
它绕过一切默认值直接发布（D-027 用"唯一发布语句就是 `publish(Twist())`"保证结构上只发零）。
上层**只有**经由 Motor Driver 这一条执行路径。

**决策 4：本机时钟不当时间基准。** 超时 / 时限一律 `time.monotonic()`
（#24 / DEV_NOTES 坑 13：墙上钟会被 NTP 步进，实测已把一个 10.000 Hz 读数算成 16.85 Hz）。

## D-034：**Skill 组合**的边界 —— 铁律管的是"Agent 侧不得绕过准入"，不是"技能之间不许互相调用"

**背景（2026-10-07）**：D-029 定了一条铁律：

> 🔒 **除网关外，任何人不得直接调用技能服务。**

但第一个 Autonomous Skill（`advance_until_blocked`）的实现**必然**要调下层 ——
它就是一个"看（`/lidar_driver/path_clear`）+ 动（`/control_skills/move_relative`）"的循环。
按字面理解，它违反了那条铁律。

**决策：把铁律的适用范围说准 —— 它管的是 Agent / 命令侧，不管技能**内部**的组合。**

> **真正要守住的不变式是**：**没有任何东西能不经过一次受检的入口就到达执行器。**

这条不变式**仍然成立**：

| 环节 | 谁来保证 |
|---|---|
| Agent 不能直接碰执行器 | 网关的 Permission（`agent.planner` 不在 `control.*` 的 `allowed_principals` 里） |
| 命令路由器不能越权 | 同上（它只能调 `control.*` 的窄集合，且受策略上限约束） |
| **组合技能本身** | **它是注册在册、过了六项检查才被派发的**；它的参数（`max_distance` 等）在网关那边受策略上限约束 |
| 组合技能调的下层 | Control Skill 自己还有一层底盘前置条件与限幅断言（D-025 / D-026） |

**为什么不能反过来"让技能也走网关"**：每加一个组合技能都要在网关里开一条新路径，
网关会退化成一个大 switch —— 而它的价值恰恰在于**只做准入、不做事**。

**代价与边界**（诚实写下来）：
- 组合技能**内部的**子调用**不受网关的策略上限约束**。
  例如 `advance_until_blocked` 每步调 `move_relative(0.1)`，这一步**不过**网关的
  0.5 m 策略检查。缓解手段是：组合技能自己的参数在网关受检，且它的**实现**里
  用 `advance_plan.validate` 做自校验（有单测）。
- 所以新增组合技能时，**它的参数上限就是新的安全边界**，必须认真定、并写进注册表。

**实现**：`embodied_autonomous_skills/autonomous_skills.py` 顶部注释。

## D-035：Planner 的**架构红线要在代码里执行**；Agent Task 归属 Agent 层而非路由器

**背景**：`plan.md` §11 的 `agent_runtime` 有一个 Planner。第一版没有 LLM，那它做什么？

**决策 1：Planner 第一版是**规则表**（Phase 7 那张 Rule Engine 的占位），且**默认空表**。**

> 规则表为空 ⟹ **任何自然语言任务都被明确拒绝**，理由写明「需要 LLM 规划，当前未实现（Phase 7）」。
> **这是刻意的默认值，不是缺陷。**

它的价值在于：让"查表 → 网关 → task-tier 技能 → 事件 → 唤醒 Agent"这条**链路**
今天就能被端到端跑通与验证，而不必先有一个 LLM。接 LLM 时替换的是**表的内容**，
不是这条链路。

**决策 2：D-003「Agent 只能命名 task-tier 技能」在 Planner 里是**代码级校验**。**

规则表写了 `control.*` → **拒绝**，并说明是架构红线。理由：

> 这张表将来是 **LLM 填的**。如果这一层不校验，一条"顺手"的规则就能让 Agent
> 绕过 D-003，而且**没有任何地方会报错** —— 它只会安静地工作，直到出事。

规则表里的技能名还要**对着网关的注册表**校验（同一份数据，不另抄一份）——
名字写错时**报错**，而不是表现为"技能调不通"（那会让排查方向跑偏）。

**决策 3：复杂任务（C 类）归属 **Agent 层**，路由器只负责分类。**

路由器识别出"这是 Agent Task"后，**转给 Agent Runtime**，由它回答"能不能做"。
在路由器里替 Agent 下结论，等于把 Agent 的职责抄一份到路由器里 —— 两份迟早不一致。

> 今天的实际效果：复杂任务**仍然会被拒绝**，但拒绝是**从 Agent 层发出的**，
> 理由写清了是 Phase 7 未到。

**决策 4：规则表是**文件**不是命令行字符串。**
`ros2 launch ... rules_json:='{...}'` 会被 launch 当成 **YAML** 解析成 dict，
参数系统直接拒收（`Allowed value types are ... Got <class 'dict'>`）。
规则表本来就是数据 —— 放文件里，与注册表一致。

**实现**：`embodied_agent_runtime/planner.py`（纯逻辑）、`config/rules_example.yaml`。

## D-036：避障接入 Safety Runtime —— 停车**锁存**、阈值按**时间**不按距离、新鲜度**另取心跳**

**背景**：D-027 把"避障"明确列为本版不做；D-005 / `ARCHITECTURE.md` §6.2 只写了
"Emergency Stop / **Obstacle Stop** / Speed Limit"这一行，**没有策略、没有阈值**；
`plan.md` §24.4 给的验收判据也只有一句"放置静态障碍物，验证能触发**减速/停止**"。
本条把这个空格填上，且只填"**停**"这一半 —— 绕行属 Phase 3 的局部规划器
（`ARCHITECTURE.md` §9.1 那条 `LiDAR → Costmap → Detection → Planner → Velocity`）。

**决策 1：避障触发后**锁存**，必须显式 `~/release`；不做自动解除。**

这不是偏好，是被 D-020 / 坑 23 逼出来的唯一可行解：

> `/cmd_vel` 上有**两个并列发布者**（Motor Driver 20 Hz、Safety Runtime 10 Hz），
> 厂商 `odom_publisher` 收到一条转一条，**没有任何仲裁**。所以"Safety 发零"顶多让底盘
> 收到 `0.2/0/0.2/0` 的交替指令 —— 那是抖着走，**不是停车**。
> 现在急停之所以有效，靠的是顺带调下游 `/motor_driver/stop`，让 **Motor Driver 自己**锁存发零。

于是"自动解除"就必须**同时自动解除 Motor Driver 的锁存** —— 那正是 D-025 决策 6
明确拒绝过的「**静默复动**」。何况"障碍移开了"并不等于"可以走了"（人可能正站在那儿）。
⇒ **停是一次决定，"继续走"是另一次决定。**

**决策 2：判据用 `速度 × 预留时间`（TTC 式），**不用固定距离**。**

D-028 留了一句硬话：**任何拍出来的固定阈值都会被场地否决** —— 实测近场回波占比
在两次摆位之间从 **3.6% 变到 67%**（同一个雷达、同一台车）。
用时间当阈值就把这个问题绕开了：**"这车需要多远刹住"是车的属性，与场地无关**，
标定一次即可；场地变的是"前面恰好有没有东西"。

- 阈值 = `clamp(速度 × obstacle_lookahead, 下限, 上限)`；静止时阈值为 0，
  **不触发** —— 所以"停在墙边"不会被反复锁存（这条是必须的，否则功能会被关掉，等于没有）。
- ⚠️ 三个默认值（`lookahead` 1.5 s / `min_range` 0.20 m / `width` ±30°）是**临时值**，
  启动时会**打出警告**说它们尚未标定。`lookahead` 的标定方法见 `DEV_NOTES.md`。

**决策 3：方向取自「**被命令的运动**」，不是「哪边是前方」。**

速度取 `Motor Driver 状态里的 vx/vy`（那是它的**输出**，锁存/超时时自己就是 0），
扇区中心取 `atan2(vy, vx)`。麦轮会侧移、后退，若一律查"前方"，
就会出现"右移撞墙不报、前方墙边空转"这种既危险又难解释的行为。
实测：命令左移时事件写的是 `obstacle:0.18m@+90deg`。

**决策 4：雷达数据复用 `~/sector_min_range`；但**新鲜度另取一路心跳**。**

复用原语是为了那份已验收的跨 0/2π 接缝几何（D-028），不重写第二份。

但**新鲜度不能问它**：`sector_min_range` 把「扫描陈旧」与「扇区真的空」返回成
**逐字段完全相同**的值（`valid=false, range=-1, angle=0, points=0`，见坑 24）。
直接信它，就会在**传感器挂了**的时候读出"前面没东西"。
⇒ 新鲜度取自 `/embodied/lidar/front`（原语每收到一帧扫描发一次）的**到达时刻**，
**只看心跳、不看内容**。心跳停了即判"不知道"，此时若正被命令运动 → 停。

> 顺带一条判据：`path_clear` **没有**这个问题（陈旧 `clear=false`、新鲜空 `clear=true`），
> 同一份数据、两个接口，一个能分辨一个不能 —— 所以这不是"数据的性质"，是**接口的责任**。

**决策 5：给「还没等到第一份回答」一条**有界宽限**（`scan_pending`）。**

真雷达第一次验证就撞上了：判定与发问在**同一拍**，`_reply` 还是 `None`，
于是被判成"不知道"而锁存 —— **每段运动的头一拍都会这样**（坑 25）。
⇒ `_reply is None` 且"开始问"至今不超过一个回答超时（0.5 s）时，视为「**还没看**」，
不判停；超时后仍无回答才照「不知道」停。
宽限是有界的，且只覆盖刚起步的 <0.5 s（最坏走出 10 cm）。

**决策 6：默认**开启**；但关闭 `watch_motor` 时**显式禁用并报 ERROR**，不静默退化。**

守卫只会停车、不会动车，失效方向也是停，所以默认开。
但它的**方向来源**是 Motor Driver 的状态 —— `watch_motor=false` 会让它拿不到方向。
此时**不能**安静地变成"不避障"：启动时打 ERROR 说明"它无法工作"，
状态里 `守卫使能` 字段报 0。（静默失效正是 #26 被记为重大缺陷的原因。）

**决策 7：边界（明确不做，写在这里免得被当成已做）。**

- **不绕行**：只会停。绕行属 Phase 3。
- **不判原地转身的机体扫掠**：`speed < min_speed` 一律不判 —— 转角时会不会蹭到旁边，
  本版不管。
- **阈值未标定**（见决策 2）。
- ⚠️ **`/cmd_vel` 的双发布者仲裁从未实测**（坑 23）：本功能因此选了"锁存"这条
  **已被验证**的路。但"Motor Driver 活着并被命令运动时，停不站得住"这一档仍是空白，
  需在**架空 + 人看护**条件下补测。

**实现**：`embodied_safety_runtime/obstacle_guard.py`（纯逻辑，37 项单测）；
`embodied_safety_runtime.py` 只管接线（订阅心跳、异步问服务、复用 `EStopLatch`）。
状态话题**追加** 5 个字段（前 4 个位置不变）；事件仍走 `estop_triggered:<原因>`，
原因为 `obstacle:<距离>m<方位>deg` 或 `obstacle:unknown_scan`。
验收工装 `tools/obstacle_guard_acceptance.py`（三路输入全部造假，**车不动、雷达不接**）。
