## 1. 方法论：测不准的量，先给它造一个独立基准

这是本项目到目前为止**最有用的一条思路**，值得放在最前面。

### 1.1 相机：为什么「延迟」和「时间戳」必须先分开

`PROJECT_STATUS.md` #16 / D-022 的核心问题一开始是这样被问的：

> 「相机比真实世界晚多少？」

但真正去测的时候，唯一能拿到的量是：

```text
（我们收到图像的时刻） − （图像自带的 header.stamp）
```

问题在于，**这个差值同时包含两个未知量**：

```text
收到时刻 − header.stamp  =  真实传输/处理延迟  +  时间戳本身的误差
                            └─ 我们想要的 ─┘   └─ 我们没意识到的 ─┘
```

只测这一个数，永远分不清「图像来得慢」还是「图像来得快、但戳写早了」。
这两件事的**修法完全不同**：

| 若是 | 修法 |
|---|---|
| 真实延迟大 | 调管线：缓冲、`io_method`、QoS、驱动 |
| 时间戳陈旧 | 什么都不用调，**重新打时间戳**即可 |

**解法：造一个「世界端」的时间基准，它独立于被测系统。**

我们选的是 `v4l2` 的 `brightness` 控制项：

- 它是 ISP 的**数字偏移**，**逐帧立即生效**（不像自动曝光要收敛几帧）；
- 因此在 `t_cmd` 时刻改亮度 → **世界在 `t_cmd` 变了**；
- 含新内容的那一帧，其**真实曝光时刻 ≈ `t_cmd`**。

于是同一个 `t_cmd` 给出**两个互不混淆**的读数：

```text
端到端延迟   = 含新内容的帧被收到的时刻 − t_cmd     ← 控制真正关心的量
时间戳偏移   = 该帧 header.stamp        − t_cmd     ← ≈0 则时间戳诚实
```

实测结果（D-022）：延迟只有约一帧（20~45 ms），而时间戳**早了约 0.72 s**。
结论直接反转了最初的假设——**问题不在管线，在时间戳**。

### 1.2 同一个思路，之前已经用过一次

测底盘原地旋转角速度时，里程计自己说自己转了多少，是**自证**，不可信。
当时引入 **LiDAR** 作独立仪器：让机器人原地旋转，看周围点云转了多少度，
就得到一个不依赖底盘自述的角速度（`tools/lidar_rotation_probe.py`）。
LiDAR 丢帧免疫，且与电机控制回路完全独立。

### 1.3 一般化

> **当一个量同时耦合了「你要测的」和「你不知道的」，不要硬测它。
> 造一个独立的时间/物理基准，把它拆成两个可分别读出的量。**

本项目里已经建立的独立基准：

| 被测对象 | 独立基准 | 工装 |
|---|---|---|
| 底盘旋转角速度 | LiDAR 点云 | `tools/lidar_rotation_probe.py` |
| 相机内容延迟 / 时间戳误差 | `v4l2` 亮度（ISP 数字偏移） | `tools/camera_latency_probe.py` |
| 底盘是否真的停了 | LiDAR 点云（不靠 `/odom` 自述） | 同上 |

## 2. 本项目「哪些量可信、哪些不可信」的当前结论

这条清单是被坑出来的，Phase 1+ 设计时直接照用：

| 量 | 可信度 | 依据 |
|---|---|---|
| `/odom` 反映底盘真实状态 | ❌ **不可信（用于存活判据）** | 通信中断时 `/odom` 照发（D-020/D-021） |
| `imu_raw` / `battery` | ✅ 可作存活判据 | 断线时确实停发 |
| 相机 `header.stamp` | ❌ **不可信，且偏移量会变** | 2026-10-05 为 −0.74 s，2026-10-06 为 **−338.6 s**（随每次开机的时钟前拨而变，#24 / D-022 / D-023）。**必须用本节点自己的实时钟重建** |
| 相机 `header.stamp` 的偏移「是常数」 | ❌ **不可信** | 同一台机器上 24 小时内从 0.74 s 变成 338.6 s（#24） |
| 相机内容本身 | ✅ 新鲜（约一帧） | 亮度探针实测 |
| 相机帧率 = 30 fps | ❌ **不可信** | 实测 20~22 Hz 且随负载变化 |
| `/scan`（LiDAR） | ✅ 可信 | 10.00 Hz / 360°，独立复核过 |
| 底盘「收到 0 就停」 | ❌ **不成立** | 无指令超时保护，必须显式持续发 0（D-020） |

## 3. 踩坑记录

### 坑 1：`amixer` 的 `Mic` 控件是**双向**的

- **现象**：做录音质量验收，录回来的波形峰值 32768、RMS 31588（96% 满量程），
  看起来像「麦克风硬件坏了 / 严重失真」。
- **最初的误判**：差点把削顶当成硬件缺陷写进验收结论。
- **怎么查出来的**：`amixer -c 0 controls` 看清 `Mic` 这个 **simple control
  同时挂了 playback 和 capture 两侧**。我那句
  `amixer -c 0 sset 'Mic' 80% unmute` 把**播放侧**（= 麦克风侧音 sidetone）
  也拧到了 80%，于是「麦克风→扬声器→麦克风」闭成了**啸叫环**，
  自己把自己录削顶了。
- **怎么修的**：`amixer -c 0 sset 'Mic' playback mute` 关掉侧音，
  重新做增益扫描，在 gain=496 拿到干净数据（peak 7565 / RMS 458 / 削顶 0%）。
- **教训**：**改 simple control 之前，先看清它挂的是 `capture` 还是 `playback`。**
  这条已写进 `PROJECT_STATUS.md` §7 与 D-022。

### 坑 2：`pkill -f` 会匹配到**自己的 shell**

- **现象**：`pkill -f 'awake_node.py|asr_node.py|voice_control'` 返回退出码 **144**，
  而且那个终端随后就不正常了。
- **原因**：`pkill -f` 匹配的是**完整命令行**。而执行这条命令的 shell，
  其命令行里**字面上就包含** `awake_node.py` 等字符串 → 它把自己也匹配上了，
  于是把自己杀了。
- **怎么修的**：先列 PID 再按 PID 杀：

  ```bash
  ps -eo pid,args | grep -E 'lib/xf_mic_asr_offline/(awake_node|asr_node|voice_control)' \
    | grep -v grep | awk '{print $1}' | xargs -r kill
  ```

- **教训**：`pkill -f <模式>` 的匹配面包含「正在敲这条命令的你」。

### 坑 3：`ros2 run ... &` 之后 `kill $!` **杀不掉真正的节点**

- **现象**：验收相机 Driver 时，输出话题实测 **27~32 Hz**，而输入只有 20~22 Hz。
  「1:1 透传的输出比输入还快」在物理上不可能 → 说明同时有**多个发布者**。
- **怎么查出来的**：

  ```bash
  ps -eo pid,etime,args | grep camera_driver | grep -v grep
  #  → 竟然有两个进程，一个跑了 1:01，一个跑了 0:37
  ros2 topic info /embodied/camera/image | grep 'Publisher count'
  #  → Publisher count: 2
  ```

- **原因**：`ros2 run` 是一个 **wrapper**，它会再 fork 出真正跑节点的进程。
  `$!` 拿到的是 wrapper 的 PID，`kill $!` 只杀了 wrapper，
  **真正的节点子进程成了孤儿，继续活着**。
- **怎么修的**：清理泄漏进程，按 PID 杀真正的节点；脚本里改用
  `ps ... | grep <可执行路径> | awk '{print $1}' | xargs -r kill` 收尾。
- **教训**：
  1. **验收脚本必须确认「发布者恰好 1 个」**，否则测到的速率是假的；
  2. 「输出比输入快」这类**违反守恒的读数，是幽灵进程的典型指纹**，
     第一反应应该是查进程，而不是怀疑测量工具。

### 坑 4：`.gitignore` 里一个裸的 `src/` 会**静默吞掉**自己的源码

- **现象**：准备在仓库内建 colcon 工作区 `embodied_agent_ws/`，
  包会放在 `embodied_agent_ws/src/...`。
- **怎么查出来的**：动手前先用 `git check-ignore -v --no-index` 探一下：

  ```text
  .gitignore:174:src/   →   embodied_agent_ws/src/my_driver/src/x.cpp   被忽略
  ```

- **原因**：`.gitignore` 里写的是**裸的 `src/`**（不带前导 `/`），
  它会匹配**任意层级**的 `src` 目录。这条规则当初是为了忽略拷进来的
  厂商源码副本而加的，却会连带把**我们自己的工作区源码**一并忽略。
  后果极其阴险：`git status` 看着干净，**代码其实一直没进库**。
- **怎么修的**：
  1. 把参考副本从 `src/src/` 改名为 `vendor_reference/`；
  2. `.gitignore` 里删掉裸 `src/`，改为锚定的 `vendor_reference/`；
  3. 三条语义都验证过：参考副本仍被忽略、工作区源码**不再**被忽略、
     `build/ install/ log/` 仍被忽略。
- **教训**：**新建目录结构前，先用 `git check-ignore --no-index` 验证它会不会被吞。**
  尤其是那些「为了忽略某个东西」而写的规则，往往范围比你以为的大。

### 坑 5：zsh 下 `source /opt/ros/humble/setup.bash` 会**定位失败**

- **现象**：在本会话里 `source` 之后，`ros2 pkg list` 找不到自定义包，
  并报 `/opt/ros/humble/setup.bash:.:11: no such file or directory: <当前目录>/setup.sh`。
- **原因**：ROS 的 `setup.bash` 靠 `BASH_SOURCE` 判断自己在哪；
  **zsh 里没有 `BASH_SOURCE`**，它为空 → 脚本回退到用**当前目录**当自己的位置，
  于是 source 了一堆不存在的东西。恰好当时 CWD 就是工作区根，问题被放大。
- **怎么修的**：把 source 与运行放进显式的 `bash -c '...'`，避开 zsh：

  ```bash
  bash -c 'source /opt/ros/humble/setup.bash
           source ~/ros2_ws/install/setup.bash
           source ~/JetsonRobot/embodied_agent_ws/install/setup.bash
           ros2 pkg list | grep embodied'
  ```

- **教训**：**给 ROS2 用的脚本，一律在 `bash` 里跑**，不要依赖当前交互 shell 是什么。

### 坑 6：一次**主动撤回**的错误怀疑（`uvcvideo.quirks`）

- **经过**：排查相机帧率时，注意到 `uvcvideo` 模块参数
  `quirks=4294967295`（即 0xFFFFFFFF），看起来像「厂商乱设了一个魔数」，
  一度怀疑它就是丢帧元凶。
- **怎么否掉的**：查内核源码，`4294967295` 就是 `uvc_quirks_param = -1`
  的**主线上电默认值**，含义是「不强制任何 quirk」。也就是说它完全正常。
- **结果**：**主动撤回**这条怀疑，并在文档里写明撤回。
- **教训**：怀疑一个参数之前，先查它的**默认值**。
  「看起来奇怪的数字」经常只是某个有符号默认值的无符号表示。
  另外——**撤回到文档里**和提出怀疑一样重要，否则后人会重新掉进同一个坑。

### 坑 7：测量「帧栅格量化」时忘了打散相位，均值会偏

- **现象**：用亮度探针标定相机 `pipeline_latency`，用**固定间隔**（`--settle 3`）重复 14 次，
  每次读到的「该帧时间戳 − 下发时刻」几乎**挤在同一个数上**（+61 / +59 / +60 …），
  只有个别离群值。按均值往前推，得到 117 ms。
- **原因**：这类测量天生带 **±半个帧周期**的量化误差 —— 事件打在帧栅格的哪个位置，
  决定了受影响帧的曝光时刻落在 `t_cmd + U(0, T)` 的哪里。而这个误差**只有在相位随机时**
  才服从均匀分布。固定间隔让 `t_cmd` 每次都落在帧栅格的**同一处**，量化误差就退化成
  一个**固定偏置**，与真正的传输延迟合在一起，**再也分不开**。
- **怎么查出来的**：把事件间隔改成随机（`--jitter`，默认 1 s）后重测 —— 标准差从
  「好得可疑」变成 **14 ms**，而理论值 `T/√12` = 44/3.46 = **12.7 ms**。
  **标准差涨到理论值上，恰恰是"相位确实被打散了"的证据。**
- **教训**：**当一个测量值稳定得"太好"时，先去怀疑采样相位被锁住了**，而不是庆祝精度高。
  量化误差在相位随机时才是均匀分布；相位固定时它只是偏置。
  （同源的教训已经在「坑 3：输出比输入快」里出现过一次 —— **违反统计预期的读数，先查工装**。）

## 5. 小结：这个项目里反复出现的三条

1. **自证不算证据。** 里程计不能证明底盘转了，相机的时间戳不能证明图像新旧。
   要给每一个「被测对象」配一个**独立的**基准。
2. **违反守恒的读数先查环境，别查被测物。** 输出比输入快、录音突然削顶，
   大概率是自己的工装出了问题。
3. **怀疑要能撤回，坑要写下来。** 撤回比提出更需要写进文档。
