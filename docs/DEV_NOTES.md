## 1. 方法论：测不准的量，先给它造一个独立基准

这是本项目到目前为止**最有用的一条思路**，值得放在最前面。

### 1.1 相机：为什么「延迟」和「时间戳」必须先分开

`PROJECT_STATUS.md` #16 / D-022 的核心问题一开始是这样被问的：

> 「相机比真实世界晚多少？」

但真正去测的时候，唯一能拿到的量是：

```text
（我们收到图像的时刻） − （图像自带的 header.stamp）
```

问题在于，**这个差值同时包含两个未知量**：

```text
收到时刻 − header.stamp  =  真实传输/处理延迟  +  时间戳本身的误差
                            └─ 我们想要的 ─┘   └─ 我们没意识到的 ─┘
```

只测这一个数，永远分不清「图像来得慢」还是「图像来得快、但戳写早了」。
这两件事的**修法完全不同**：

| 若是 | 修法 |
|---|---|
| 真实延迟大 | 调管线：缓冲、`io_method`、QoS、驱动 |
| 时间戳陈旧 | 什么都不用调，**重新打时间戳**即可 |

**解法：造一个「世界端」的时间基准，它独立于被测系统。**

我们选的是 `v4l2` 的 `brightness` 控制项：

- 它是 ISP 的**数字偏移**，**逐帧立即生效**（不像自动曝光要收敛几帧）；
- 因此在 `t_cmd` 时刻改亮度 → **世界在 `t_cmd` 变了**；
- 含新内容的那一帧，其**真实曝光时刻 ≈ `t_cmd`**。

于是同一个 `t_cmd` 给出**两个互不混淆**的读数：

```text
端到端延迟   = 含新内容的帧被收到的时刻 − t_cmd     ← 控制真正关心的量
时间戳偏移   = 该帧 header.stamp        − t_cmd     ← ≈0 则时间戳诚实
```

实测结果（D-022）：延迟只有约一帧（20~45 ms），而时间戳**早了约 0.72 s**。
结论直接反转了最初的假设——**问题不在管线，在时间戳**。

### 1.2 同一个思路，之前已经用过一次

测底盘原地旋转角速度时，里程计自己说自己转了多少，是**自证**，不可信。
当时引入 **LiDAR** 作独立仪器：让机器人原地旋转，看周围点云转了多少度，
就得到一个不依赖底盘自述的角速度（`tools/lidar_rotation_probe.py`）。
LiDAR 丢帧免疫，且与电机控制回路完全独立。

### 1.3 一般化

> **当一个量同时耦合了「你要测的」和「你不知道的」，不要硬测它。
> 造一个独立的时间/物理基准，把它拆成两个可分别读出的量。**

本项目里已经建立的独立基准：

| 被测对象 | 独立基准 | 工装 |
|---|---|---|
| 底盘旋转角速度 | LiDAR 点云 | `tools/lidar_rotation_probe.py` |
| 相机内容延迟 / 时间戳误差 | `v4l2` 亮度（ISP 数字偏移） | `tools/camera_latency_probe.py` |
| 底盘是否真的停了 | LiDAR 点云（不靠 `/odom` 自述） | 同上 |
| 雷达近场回波是「自身的」还是「环境的」 | **换个地方再测一次** | `tools/lidar_environment_probe.py` |

### 1.4 「跟着走」= 自身的，「留在原地」= 环境的

2026-10-06 量 LiDAR Primitive 时留下一个悬案：当时摆位下 **67% 的回波在 0.6 m 以内**，
其中 198°~359° 有一整圈 **0.10~0.28 m** 的贴身回波，导致 `path_clear(±30°, 1 m)`
**恒为 false**。问题是：这是**雷达看到了机器人自身的结构**（底盘/轮子/支架），
还是**外部环境**（桌腿/墙/人）？

这两者的区别**不是数值上的，而是行为上的**：

> **自身结构相对雷达是静止且固连的 —— 你把车挪到哪儿，它都在同样的角度上。
> 环境回波则随摆位而变。**

所以判据不是"距离多近"，而是**换一个摆位再测同一张剖面**：

- 2026-10-06（原地、局促）：近场占比 **67%**，贴身环 198°~359° **在**；
- 2026-10-07（挪到另一处）：近场占比 **3.6%**，贴身环 **完全消失**。

→ 两块近场回波都**没跟着车走**，判为**外部环境**（D-028 补充）。

> ⚠️ **这个判据不需要空旷场地** —— 它只需要"两次摆位不同"，而不是"某一次足够开阔"。
> 2026-10-07 这次实测场地其实也不大（用户说明"空间比较小"），
> 但两次差异已经足以定性。要更严的证明，还有一条**与场地大小无关**的判别法：
> **把车原地转 90° 再测** —— 自身结构会跟着转到新角度，环境不会。本次未做。

## 2. 本项目「哪些量可信、哪些不可信」的当前结论

这条清单是被坑出来的，Phase 1+ 设计时直接照用：

| 量 | 可信度 | 依据 |
|---|---|---|
| `/odom` 反映底盘真实状态 | ❌ **不可信（用于存活判据）** | 通信中断时 `/odom` 照发（D-020/D-021） |
| `imu_raw` / `battery` | ✅ 可作存活判据 | 断线时确实停发 |
| 相机 `header.stamp` | ❌ **不可信，且偏移量会变** | 2026-10-05 为 −0.74 s，2026-10-06 为 **−338.6 s**（随每次开机的时钟前拨而变，#24 / D-022 / D-023）。**必须用本节点自己的实时钟重建** |
| 相机 `header.stamp` 的偏移「是常数」 | ❌ **不可信** | 同一台机器上 24 小时内从 0.74 s 变成 338.6 s（#24） |
| 相机内容本身 | ✅ 新鲜（约一帧） | 亮度探针实测 |
| 相机帧率 = 30 fps | ❌ **不可信** | 实测 20~22 Hz 且随负载变化 |
| `/scan`（LiDAR） | ✅ 可信 | 10.00 Hz / 360°，独立复核过 |
| 底盘「收到 0 就停」 | ❌ **不成立** | 无指令超时保护，必须显式持续发 0（D-020） |
| 语音**麦克风**（能否拾音） | ✅ **可信** | 声学回路实测：播 440 Hz，录音中该分量涨三个数量级 |
| 语音**唤醒** | ❌ **当前不可用** | 人声 + 四个本地 TTS 合成词全部零事件；**2026-10-07 根因定位：控制串口完全沉默**（#25） |
| 唤醒词「已经配好了」 | ❌ **不成立** | `enable_setting` 默认 `false` → `set_wakeup_word()` **从未被调用**，唤醒词从没写进硬件（#25 / 坑 14） |
| `/dev/ring_mic` 控制串口**会不会说话** | ✅ **会** —— 但**只在有语音时** | ⚠️ **曾误判为"收方向无活动"**：4 种 RTS/DTR + 180 s 静默监听 + 90 次握手 → 0 字节。**那是静默期的 0**。让人对着麦克风说话 → **9 个 `aa550300fb` 帧**（=「唤醒成功」，见厂商 `wonder_echo_pro_node.py:52`），静默 20 s 对照 → 0 帧。**教训见坑 15 的更正**：测一条"要有外部刺激才会说话"的通道，**必须先去激它** |
| 「初始化服务存在」⇒「初始化成功了」 | ❌ **不成立** | `init_finish` 是**无条件创建**的（#25 / 坑 14） |
| 麦克风的**音频**通路 | ✅ **可信** | 3 s 采集峰值 6.4% FS、无削顶；早前声学回路独立验证过 |
| 「厂商 ASR 栈正常启动」 | ❌ **不可当作"语音可用"** | 那验证的是**节点起得来**，不是能唤醒；唤醒从来没被测过（#25） |
| 厂商「停下」会停 | ❌ **不可信（碰巧成立）** | `voice_control_move.py` **没有 stop 分支**，靠掉进默认零 Twist 成立（#26） |
| `ASR_MODE=online` ⇒ 在线 ASR | ❌ **不成立** | 该变量只被厂商 `large_models` 读取，麦克风栈不读它（#27） |
| 雷达近场回波「是机器人自身结构」 | ❌ **不成立（已判为外部环境）** | 换摆位后 67%→3.6%、贴身环消失（`PROJECT_STATUS` §7 / **D-028 补充**） |
| **墙上钟 `time.time()` 的时长** | ❌ **不可信** | 本机每次开机被 NTP 步进（#24），它**不是单调的**；量时间一律用 `time.monotonic()`（坑 13） |

## 3. 踩坑记录

### 坑 1：`amixer` 的 `Mic` 控件是**双向**的

- **现象**：做录音质量验收，录回来的波形峰值 32768、RMS 31588（96% 满量程），
  看起来像「麦克风硬件坏了 / 严重失真」。
- **最初的误判**：差点把削顶当成硬件缺陷写进验收结论。
- **怎么查出来的**：`amixer -c 0 controls` 看清 `Mic` 这个 **simple control
  同时挂了 playback 和 capture 两侧**。我那句
  `amixer -c 0 sset 'Mic' 80% unmute` 把**播放侧**（= 麦克风侧音 sidetone）
  也拧到了 80%，于是「麦克风→扬声器→麦克风」闭成了**啸叫环**，
  自己把自己录削顶了。
- **怎么修的**：`amixer -c 0 sset 'Mic' playback mute` 关掉侧音，
  重新做增益扫描，在 gain=496 拿到干净数据（peak 7565 / RMS 458 / 削顶 0%）。
- **教训**：**改 simple control 之前，先看清它挂的是 `capture` 还是 `playback`。**
  这条已写进 `PROJECT_STATUS.md` §7 与 D-022。

### 坑 2：`pkill -f` 会匹配到**自己的 shell**

- **现象**：`pkill -f 'awake_node.py|asr_node.py|voice_control'` 返回退出码 **144**，
  而且那个终端随后就不正常了。
- **原因**：`pkill -f` 匹配的是**完整命令行**。而执行这条命令的 shell，
  其命令行里**字面上就包含** `awake_node.py` 等字符串 → 它把自己也匹配上了，
  于是把自己杀了。
- **怎么修的**：先列 PID 再按 PID 杀：

  ```bash
  ps -eo pid,args | grep -E 'lib/xf_mic_asr_offline/(awake_node|asr_node|voice_control)' \
    | grep -v grep | awk '{print $1}' | xargs -r kill
  ```

- **教训**：`pkill -f <模式>` 的匹配面包含「正在敲这条命令的你」。

### 坑 3：`ros2 run ... &` 之后 `kill $!` **杀不掉真正的节点**

- **现象**：验收相机 Driver 时，输出话题实测 **27~32 Hz**，而输入只有 20~22 Hz。
  「1:1 透传的输出比输入还快」在物理上不可能 → 说明同时有**多个发布者**。
- **怎么查出来的**：

  ```bash
  ps -eo pid,etime,args | grep camera_driver | grep -v grep
  #  → 竟然有两个进程，一个跑了 1:01，一个跑了 0:37
  ros2 topic info /embodied/camera/image | grep 'Publisher count'
  #  → Publisher count: 2
  ```

- **原因**：`ros2 run` 是一个 **wrapper**，它会再 fork 出真正跑节点的进程。
  `$!` 拿到的是 wrapper 的 PID，`kill $!` 只杀了 wrapper，
  **真正的节点子进程成了孤儿，继续活着**。
- **怎么修的**：清理泄漏进程，按 PID 杀真正的节点；脚本里改用
  `ps ... | grep <可执行路径> | awk '{print $1}' | xargs -r kill` 收尾。
- **教训**：
  1. **验收脚本必须确认「发布者恰好 1 个」**，否则测到的速率是假的；
  2. 「输出比输入快」这类**违反守恒的读数，是幽灵进程的典型指纹**，
     第一反应应该是查进程，而不是怀疑测量工具。

> **2026-10-06 又踩中一次，只是换了包装。**
> 这次是用工具的后台任务起 `ros2 launch`，停任务时**只杀掉了最外层 shell，
> `ros2 launch` 与真正的节点活了下来**（`ps` 上表现为父进程链还在：
> `zsh -c` → `ros2 launch` → `camera_driver`）。后果和坑 3 一样：
> `/embodied/camera/image` **多了一个幽灵发布者**。
> 判据也还是同一个 —— **`ros2 topic info` 数发布者** + `ps` 看 `lstart` / 父进程链。
> ⚠️ **教训补充：「停掉任务」不等于「进程没了」** —— 凡是用后台任务/包装器起的 ROS 节点，
> 收工时都要按上面两条**再确认一次**，别相信停止命令的返回值。
>
> **2026-10-06 同一坑的第三种形态**：`for p in $(pgrep -f "…motor_driver.launch…"); do kill $p; done`
> —— `pgrep -f` 匹配的是**完整命令行**，而这条命令自己的命令行里就写着 `motor_driver.launch`，
> 于是**把自己所在的 shell 也杀了**（退出码 144），后面的启动根本没执行。
> **判据不变：先列 PID、看清是谁，再杀。**

### 坑 4：`.gitignore` 里一个裸的 `src/` 会**静默吞掉**自己的源码

- **现象**：准备在仓库内建 colcon 工作区 `embodied_agent_ws/`，
  包会放在 `embodied_agent_ws/src/...`。
- **怎么查出来的**：动手前先用 `git check-ignore -v --no-index` 探一下：

  ```text
  .gitignore:174:src/   →   embodied_agent_ws/src/my_driver/src/x.cpp   被忽略
  ```

- **原因**：`.gitignore` 里写的是**裸的 `src/`**（不带前导 `/`），
  它会匹配**任意层级**的 `src` 目录。这条规则当初是为了忽略拷进来的
  厂商源码副本而加的，却会连带把**我们自己的工作区源码**一并忽略。
  后果极其阴险：`git status` 看着干净，**代码其实一直没进库**。
- **怎么修的**：
  1. 把参考副本从 `src/src/` 改名为 `vendor_reference/`；
  2. `.gitignore` 里删掉裸 `src/`，改为锚定的 `vendor_reference/`；
  3. 三条语义都验证过：参考副本仍被忽略、工作区源码**不再**被忽略、
     `build/ install/ log/` 仍被忽略。
- **教训**：**新建目录结构前，先用 `git check-ignore --no-index` 验证它会不会被吞。**
  尤其是那些「为了忽略某个东西」而写的规则，往往范围比你以为的大。

### 坑 5：zsh 下 `source /opt/ros/humble/setup.bash` 会**定位失败**

- **现象**：在本会话里 `source` 之后，`ros2 pkg list` 找不到自定义包，
  并报 `/opt/ros/humble/setup.bash:.:11: no such file or directory: <当前目录>/setup.sh`。
- **原因**：ROS 的 `setup.bash` 靠 `BASH_SOURCE` 判断自己在哪；
  **zsh 里没有 `BASH_SOURCE`**，它为空 → 脚本回退到用**当前目录**当自己的位置，
  于是 source 了一堆不存在的东西。恰好当时 CWD 就是工作区根，问题被放大。
- **怎么修的**：把 source 与运行放进显式的 `bash -c '...'`，避开 zsh：

  ```bash
  bash -c 'source /opt/ros/humble/setup.bash
           source ~/ros2_ws/install/setup.bash
           source ~/JetsonRobot/embodied_agent_ws/install/setup.bash
           ros2 pkg list | grep embodied'
  ```

- **教训**：**给 ROS2 用的脚本，一律在 `bash` 里跑**，不要依赖当前交互 shell 是什么。

### 坑 6：一次**主动撤回**的错误怀疑（`uvcvideo.quirks`）

- **经过**：排查相机帧率时，注意到 `uvcvideo` 模块参数
  `quirks=4294967295`（即 0xFFFFFFFF），看起来像「厂商乱设了一个魔数」，
  一度怀疑它就是丢帧元凶。
- **怎么否掉的**：查内核源码，`4294967295` 就是 `uvc_quirks_param = -1`
  的**主线上电默认值**，含义是「不强制任何 quirk」。也就是说它完全正常。
- **结果**：**主动撤回**这条怀疑，并在文档里写明撤回。
- **教训**：怀疑一个参数之前，先查它的**默认值**。
  「看起来奇怪的数字」经常只是某个有符号默认值的无符号表示。
  另外——**撤回到文档里**和提出怀疑一样重要，否则后人会重新掉进同一个坑。

### 坑 7：测量「帧栅格量化」时忘了打散相位，均值会偏

- **现象**：用亮度探针标定相机 `pipeline_latency`，用**固定间隔**（`--settle 3`）重复 14 次，
  每次读到的「该帧时间戳 − 下发时刻」几乎**挤在同一个数上**（+61 / +59 / +60 …），
  只有个别离群值。按均值往前推，得到 117 ms。
- **原因**：这类测量天生带 **±半个帧周期**的量化误差 —— 事件打在帧栅格的哪个位置，
  决定了受影响帧的曝光时刻落在 `t_cmd + U(0, T)` 的哪里。而这个误差**只有在相位随机时**
  才服从均匀分布。固定间隔让 `t_cmd` 每次都落在帧栅格的**同一处**，量化误差就退化成
  一个**固定偏置**，与真正的传输延迟合在一起，**再也分不开**。
- **怎么查出来的**：把事件间隔改成随机（`--jitter`，默认 1 s）后重测 —— 标准差从
  「好得可疑」变成 **14 ms**，而理论值 `T/√12` = 44/3.46 = **12.7 ms**。
  **标准差涨到理论值上，恰恰是"相位确实被打散了"的证据。**
- **教训**：**当一个测量值稳定得"太好"时，先去怀疑采样相位被锁住了**，而不是庆祝精度高。
  量化误差在相位随机时才是均匀分布；相位固定时它只是偏置。
  （同源的教训已经在「坑 3：输出比输入快」里出现过一次 —— **违反统计预期的读数，先查工装**。）

### 坑 8：Python 节点在 systemd 管道里**块缓冲**——"没有日志"**不等于**"进程卡住了"

- **现象**：排查语音唤醒不通时，翻了厂商服务的 journal，发现 `awake_node`（Python 节点）
  **从启动到现在一条输出都没有**，连它本该打印的 `Wake up word: xxx` 都没有。
  第一反应是"它卡在哪个串口握手上了"——因为按源码，那几行日志确实排在两次握手**之后**。
- **否证**：`/awake_node/init_finish` **这个服务是存在的**，而它建在 `__init__` 的**最末尾**、
  排在两次握手**之后**。服务存在 ⇒ `__init__` 跑完了 ⇒ **没卡住**。
- **真正原因**：stdout 接的是 **systemd 的管道**（不是 tty），Python 于是走**块缓冲**，
  输出攒在缓冲区里不 flush。对照证据：同一份 journal 里 **C++ 节点**（`usb_cam`、`voice_control`）的
  `cout` 都正常出现，而 `voice_control_move.py` 的输出**只在它进程死掉那一刻**才整段冒出来
  （——退出时缓冲区被 flush）。
- **教训**：
  1. **判断一个 Python 节点是否卡住，不能靠"它没打印日志"**，要找一个**必然晚于疑点创建的东西**
     （服务 / 话题 / 定时器）作为存在性证据；
  2. 要看实时日志，就**自己手动起、带 `PYTHONUNBUFFERED=1`**，别指望 systemd 那侧。

### 坑 9：`ros2 launch` 的**未声明参数会被静默忽略**

- **现象**：想给 Motor Driver 做"链路失联"实验，把存活判据话题指向假话题：

  ```bash
  ros2 launch embodied_motor_driver motor_driver.launch.py \
      imu_topic:=/embodied/motor/test/imu battery_topic:=/embodied/motor/test/battery
  ```

  结果**实验完全没生效**：脚本切断了假遥测，节点却毫无反应 ——
  因为**它订阅的还是真的 `/ros_robot_controller/imu_raw`**，而真遥测一直新鲜，
  "失联"根本没发生。表面上一切正常，只有一个"什么都没发生"的结果。
- **原因**：`ros2 launch` 里 `名字:=值` **只有在 launch 文件用 `DeclareLaunchArgument`
  声明过才会传进去**；**没声明的会被忽略**（不报错）。我写那个 launch 时只声明了 `dry_run`。
- **怎么发现的**：`ros2 node info /motor_driver` 看它实际订阅了哪些话题 —— 一眼看出还是真话题。
- **教训**：**用 `ros2 launch` 传参之后，必须用 `ros2 node info` / `ros2 topic list` 确认它真的生效。**
  "命令行没报错"不等于"参数传进去了"。
  （这与坑 2、坑 3 是同一条元教训：**别相信"看起来成功"，去查实际状态。**）
- **2026-10-07 补充：同一个症状还有第二种成因。** 又一次"`x:=y` 没生效"，但这次
  `DeclareLaunchArgument` **明明声明了**。查下来是**文件里有两份
  `generate_launch_description()`** —— 一次编辑把整个文件体重复插了进去，
  而 **Python 取的是最后一份**，于是执行的是旧的那份（少声明了几个参数）。
  > **判据**：`ros2 launch <pkg> <file> --show-args` **列出的是哪几个参数**，
  > 与文件内容对不上，就往"是不是有重复定义"上查（`grep -n "^def " <file>`）。
  > 症状与坑 9 一模一样，成因完全不同 —— **同一个现象不要只留一种解释。**

### 坑 10：`MutuallyExclusiveCallbackGroup` 会把「拒绝」悄悄变成「排队」

- **现象**：Control Skill 的设计意图是"一次只跑一个动作，运动中来新请求**直接拒绝**"。
  代码里也明明写着 `if self._goal is not None: return busy`。但实测：
  运动中的第二个请求**没有被拒绝，而是等第一个跑完又照做了** ——
  变成了一条隐藏的队列。更糟的是 **`~/stop` 超时无响应**，
  因为它的回调排在那个"正阻塞到运动结束"的回调**后面** ——
  也就是排在了**最需要它的那一刻之后**。
- **原因**：三个服务都用的 `MutuallyExclusiveCallbackGroup`。它保证同一时刻只有一个回调在跑，
  而本层的服务回调会**阻塞到运动结束**（等控制循环把 `threading.Event` 置位）。
  于是后来者只能排队。
- **怎么修的**：服务回调改用 `ReentrantCallbackGroup` + `MultiThreadedExecutor`，
  共享状态用 `threading.Lock` 保护。这样后来的请求能真的跑起来、看到 `_goal` 已占用、返回 busy；
  `~/stop` 也能立刻进来。（`~/stop` 与动作服务**不需要**分开成两个组，
  关键在于"能不能并发"，不在于"是不是同一个组"。）
- **教训**：**只要回调里会阻塞，"并发语义"就不是 `if busy: return` 这种代码能决定的，
  而是由回调组类型决定的。** 这类东西**光看代码看不出来**（那行 `if self._goal is not None` 写得好好的），
  **必须实测**。

### 坑 11：两个线程共用一个状态对象，一方把它置 `None` 后，另一方还在下标访问

- **现象**：节点在第一次收到运动请求后**直接崩了**（exit code 1）：
  `TypeError: 'NoneType' object is not subscriptable`。
- **原因**：控制循环收尾时把 `self._goal = None`；而服务回调在 `event.wait()` 返回后
  仍然去读 `self._goal['success']` —— 读到的是 `None`。
- **怎么修的**：**在启动这次动作时就把那条 goal 的引用抓在手里**，收尾时读自己那份。
  （那次访问本来就不该去读"当前共享状态"，而该读"我这次请求自己的结果"。）
- **教训**：**判据要绑在"这次请求"上，不要绑在"当前全局状态"上。**
  后者随时可能被别人改掉 —— 而在多线程里，"随时"就是"在你脚下"。

### 坑 12：`git push` 报 `Permission denied (publickey)` 可能只是**瞬时**的

- **现象**：一轮开发做完，`git push` 报

  ```text
  git@ssh.github.com: Permission denied (publickey).
  fatal: Could not read from remote repository.
  ```

  ⚠️ 而**同一条命令 20 分钟前刚刚成功过**（`31acf71` 那次）。
- **第一反应（错的）**：密钥失效 / `~/.ssh/config` 坏了 / 网络又被封了 —— 于是想去动密钥。
- **怎么查清楚的**：分两步，都不改任何东西：
  1. `ssh -T git@github.com` —— 实际回的是
     `Hi Piggy-two! You've successfully authenticated...`，**认证本来是通的**；
  2. 检查 agent 与私钥：没有 agent 在跑、私钥也**没有口令**（`ssh-keygen -y -P "" -f` 能读）——
     排除了"代理没了、签名要口令"这条常见解释。
- **结论**：**是瞬时失败，重试即可**（重试一次就成功了）。
- **教训**：**先区分"瞬时"与"配置坏了"。** 判据是**同一条命令近期成功过** 与
  `ssh -T` 的直接结论 —— 有这两条在手，就不该去动 `~/.ssh` 或改 remote。
  另外，`Server accepts key ...` 后面跟 `Permission denied` 这类日志**看起来像**签名失败，
  实际也可能只是这一轮握手中途断了 —— **别只凭一行日志下结论**。
  （与"坑 2/3/9"是同一件事：**别相信一次观测，去查实际状态**。）

### 坑 13：用墙上钟（`time.time()`）量时长，会被 NTP 步进污染

- **现象**：新写的 LiDAR 剖面工装（`tools/lidar_environment_probe.py`）报
  `/scan` 是 **16.85 Hz**，而同一时刻 `ros2 topic hz /scan` 明明是 **10.000 Hz**，
  且显示的帧间隔 `min 0.096s max 0.104s` 高度均匀。**两个读数不可能同时为真。**
- **原因（不是雷达）**：工装用 `time.time()`（**实时钟**）算首末帧时间差。
  本机**每次开机时钟都会被 timesyncd 恢复、再被 NTP 前拨**（正是 **#24**）——
  墙上钟**不是单调的**。采集窗口里只要发生一次步进，算出的"时长"就是错的，
  而**帧数是对的**，于是速率被算成一个不存在的值。
- **怎么修的**：改用 `time.monotonic()`；并**直接报帧间隔中位数**（对个别异常间隔免疫），
  这样即便时钟出问题也能一眼看出。
- **教训**：**#24 那条坑不是「`usb_cam` 的毛病」，而是本机时钟的普遍性质。**
  凡是量时间的地方都要先问一句"**这钟会不会跳**"。本项目已经因同一性质踩了两次：
  第一次是厂商 `usb_cam` 冻结了 `(实时−单调)` 换算基准，这一次是我们自己的工装。
  > 📌 顺带：`ros2 topic hz` 用的是它自己的节拍，**它是对的** ——
  > 与自己的工装对不上时，**先怀疑工装**（见 §5 第 2 条）。

### 坑 14：**无条件执行**的东西，不能当「那个条件分支执行过」的证据

- **现象**：文档里写着「`/awake_node/init_finish` 服务存在（该服务建在 `switch_mic` /
  `set_wakeup_word` **两次串口握手之后** → **握手成功过**）」，并据此判定
  "硬件是通的，卡点在唤醒这一环"。于是下一轮把力气花在**发音、音量、解析**上。
- **真相**：读源码 —— 那个服务在 `AwakeNode.__init__` **末尾无条件创建**；
  而握手发生在 `CircleMic.send()` 里，**只有 `enable_setting` 为真时才会被调用**。
  服务存在只证明「节点构造完成、串口打开了」，与握手**半点关系都没有**。
- **真正的判据**：去找**只在那条分支里才会产生的副作用** —— 这里就是那两行
  `print('setting wakeup keywords need about 30s')`。它们**在 journal 里从来没出现过**，
  一条命令就能定案。
- **教训**：一个"存在性"证据（服务在 / 进程活着 / 日志里有一行），
  **如果它的出现不依赖那个条件，它就完全不能证明那个条件成立。**
  问一句：「**这东西是只有走那条路才会有，还是无论如何都会有？**」
  （与坑 8「没有日志 ≠ 卡住了」是同一枚硬币的两面：**日志的有无都要先问"它凭什么会有"**。）

### 坑 15：收到 **0 字节**，和「波特率不对」是两回事

- **现象**：探 `/dev/ring_mic` 时，四种 RTS/DTR 组合下**一个字节都收不到**；
  第一反应是"是不是波特率设错了"。
- **为什么不是**：**波特率错会收到「乱码」，不会收到「什么都没有」。**
  采样率不匹配时电平跳变仍会被采到，只是解成垃圾字节。
  **0 字节意味着这条线的收方向上根本没有电平活动** —— 是"对端没在发/没接上"，
  不是"我解读错了"。据此才敢把结论从"配置不对"升级为"**这条线是死的**"。
- **附带**：厂商 `CircleMic.send()` 的握手等待是 `while True:` **没有超时**。
  所以它一卡住，外面看到的是**进程正常存活、日志一个字没有**
  （状态是 `do_select`）—— 没有读数、没有报错、没有退出。
  **给任何"等对端回应"的循环加超时**，否则失败会伪装成"正在运行"。
- **教训**：**"没有数据"也要能被区分成"没在发"还是"我没读懂"。**
  前者靠"零字节 vs 乱码"，后者靠独立基准（同 §1）。

> 🔴 **本条推理的更正（2026-10-07 当天晚些时候，必须连着读）**
>
> 上面说「0 字节意味着这条线的收方向上根本没有电平活动」—— 这个推理**本身没错**，
> 但它**被用在了错误的场景**：当时我是在**静默**中监听一条 **要有外部刺激才会说话** 的通道
> （讯飞环形麦：你不说话，它就不发）。
>
> **实测反例**：同一段代码、同一根线、同一个人 —— 只是这次**让他对着麦克风说话** ——
> **立刻收到 9 个 `aa550300fb` 帧**（=「唤醒成功」）；而**静默 20 秒的对照实验是 0 帧**。
> 也就是说：**那 180 秒的 0 字节，测的是"没人在说话"，不是"这线不会说话"** ——
> 我却据此写下了"唤醒在结构上不可能产生"，并推着排查方向走偏了一整轮。
>
> **补上第三条判据**（前两条是"没在发"与"我没读懂"）：
>
> | 现象 | 说明 | 怎么区分 |
> |---|---|---|
> | 零字节 | **本来就没在发** | ← 先确认**该发的东西被激发了吗** |
> | 乱码 | 波特率/格式不对 | 换个波特率再听 |
> | 零字节但**本该有动静** | 对端没接 / 没上电 / **在等一个刺激** | **去激它**（说话、发命令、按键）再听 |
>
> **教训**：**测一条"被动上报"的通道时，静默期的 0 字节什么也证明不了。**
> 先问一句：「**这东西凭什么会在我观察的这段时间里说话？**」
> 如果答案是"它得有输入才说"，那第一步就是**给它输入**，而不是延长观察时间。
> （与坑 14 同源：证据的有无，都要先问"它凭什么会有/没有"。）

### 坑 16：私有属性名和 **`rclpy.Node` 的内部属性撞名**，报错点离原因隔了好几层

- **现象**：Skill 网关一启动就在**第一次创建服务客户端**时崩掉：

  ```text
  AttributeError: 'dict' object has no attribute 'append'
    File ".../rclpy/node.py", line 1439, in create_client
      self._clients.append(client)
  ```

- **原因**：我把自己的客户端缓存命名成了 `self._clients` —— 而 `rclpy.Node`
  **内部本来就有**一个同名的 `list`，`create_client()` 要往它 append。
  我用一个 dict 把它**覆盖**了，于是 rclpy 的内部簿记被破坏。
  报错信息里出现的是 **rclpy 的源码行**，完全看不出「是我起了个重名」。
- **怎么修的**：改名 `self._srv_clients`，并在代码里写明原因。
- **怎么**系统性地**查出来的**（这一步值得复用）：

  ```python
  import inspect, re, rclpy.node
  used = set(re.findall(r'self\.(_[A-Za-z_][A-Za-z0-9_]*)', inspect.getsource(rclpy.node)))
  print(sorted(set(['_clients','_lock','_clock','_context', ...]) & used))
  ```

  ⚠️ **第一版检查是错的**：我用的正则只匹配 `self.x = ...` 这种**简单赋值**，
  所以漏掉了 `_clients`（它在 rclpy 里不是那样赋值的），得出"无冲突"的错误结论。
  **改成抓所有 `self._xxx` 的出现（读或写都算）才暴露出来** ——
  与"坑 15"同一条教训：**检查方法本身也要能被怀疑。**
  查出会撞的名字：`_clients` / `_clock` / `_context`。
- **教训**：**继承来的类里，`self._xxx` 不是你的自留地。** 给节点自己的状态起名时，
  要么用足够具体的名字（`_srv_clients`），要么先查一遍基类用了哪些。
  另：报错栈指向**第三方库内部**时，先想"是不是我破坏了它的前置条件"。

### 坑 17：日志夹在**两个副作用之间** —— 它一抛异常，关键的那个就丢了

- **现象**：验收里有一条任务**永远等不到终态事件**，调用方一直耗到自己的 30 s 超时。
  网关日志暴露了真相：

  ```text
  派发时异常：ValueError('Logger severity cannot be changed between calls.')
  状态迁移被拒（000003）：FAILED 是终态，没有出边
  ```

- **两个问题叠在一起**：

  1. **直接原因**：我把 `self.get_logger().info` / `.warn` **取出来存成变量**再按级别调用，
     rclpy 不接受这样在两次调用之间切级别 → 抛 `ValueError`。
  2. **真正致命的是顺序**：在 `_finish()` 里，那行日志夹在
     「**置终态**」与「**发事件**」之间。日志一抛，任务在表里**已经是终态**、
     而**事件从来没发出去** —— 调用方等一个永远不会来的东西。

- **怎么修的**：
  ```python
  # ① 先发事件，再打日志 —— 事件是调用方在等的那个东西，日志只是给人看的
  self._publish_event(...)
  # ② 按级别显式分支，不要把 get_logger().info 存成变量
  if state == FINISHED: self.get_logger().info(text)
  else:                 self.get_logger().warn(text)
  ```
  并给工作线程加了兜底：**任何异常都必须落成终态**（`if not rec.terminal: finish(FAILED)`），
  否则就是"幽灵任务"—— 上层会一直等，而它此时**已经无法判断机器人到底停没停**。
- **教训**：**一串副作用里，唯一不能被省掉的那个要排在最前面。**
  日志、通知、统计都可以丢；**状态变更与"告诉别人状态变了"不能丢**。
  写 `A(); log(); B();` 时先问一句：**log 抛异常的话，A 和 B 少一个会怎样？**

### 坑 18：`ros2 launch` 会把 `x:=y` 的值**当 YAML 解析**，JSON 字符串会变成 dict

- **现象**：给节点传一张规则表：

  ```bash
  ros2 launch ... rules_json:='{"向前走一小段":{"skill":"..."}}'
  ```

  ```
  [ERROR] [launch]: Caught exception in launch:
  Allowed value types are bytes, bool, int, float, str, Sequence[...].
  Got <class 'dict'>.
  ```

- **原因**：`ros2 launch` 对 `名字:=值` 的**右侧做 YAML 解析** —— `{...}` 被解析成
  一个真正的 dict，而参数系统只接受标量与标量序列。所以**JSON 字符串根本传不进去**。
  （这与坑 9「未声明的参数会被静默忽略」是同一套机制的两面：那一条是"名不对"，
  这一条是"值不对"。）
- **怎么修的**：**不传 JSON 字符串，改传文件路径**（`rules_file:=/path/to/rules.yaml`）。
  规则表本来就是**数据**，与注册表（`files/registry_file`）保持同一种做法。
  顺带还得到了一个好处：文件写错时能在**启动时**报错（而不是运行时才表现为
  "什么都规划不出来"）。
- **教训**：**复杂的结构化参数不要走命令行。** 命令行是给"开关和标量"的；
  一旦要传结构，就该有一个文件。这既绕开了这个坑，也让配置可版本化、可 diff。
  （若确实非要传字符串，得在 YAML 里再套一层引号把整串变成标量 —— 别那么干。）

### 坑 19：验收工装里，「**我没在看**」和「**系统没动**」的读数**一模一样**

- **现象**：验收第 12 项报 `ARRIVED`（技能自报走了 0.3 m），而工装量到的
  `∫vx = 0`、非零帧 = 0 —— 看起来像"技能谎报"。查 Control Skill 日志，
  它**确实老老实实走了三步**（0.100 m × 3，耗时 2.13 s）。
  另写一个独立探针去测同一条话题，**20 Hz 收得整整齐齐**，积分也对。
  → **被测对象没问题，是工装自己那一轮没在收帧。**
- **为什么危险**：`∫vx = 0` 有两种完全不同的原因 ——
  「车没动」与「我没在看」，而**它们在输出上长得一模一样**。
  没有区分手段时，会去怀疑一个根本没问题的系统（这一轮就白查了半天）。
- **怎么修的**：
  1. 在【12】里**把"等终态期间收到多少帧"打出来**（`42 帧，非零 39 帧`）——
     让"没在看"变成一个**看得见的数**；
  2. 开头加一道**流量预热**：先等到干跑话题真的在送帧（≥15 帧）才开始测，
     否则直接提示"后面的判读不可信"；
  3. 积分窗口取**等终态期间**那一段，而不是"再等 1 s 之后"——
     后者会把静止段混进来，把问题盖掉。
- **教训**：**每一个"零"都要能被区分成"确实没有"还是"我没采到"。**
  这与坑 15（0 字节 vs 乱码）是同一件事的不同形态：**观测手段本身要先被观测。**

### 坑 20：同一个物理量，**换个工况信号就换了轴** —— 照搬上次的判据会得出相反的结论

- **现象**：架空运动验收里，`set_motor` 明明发出了 **0.5968 rps**（与运动学逐位吻合），
  Control Skill 也报 `success`，但 IMU 的 `angular_velocity.z` 幅度**纹丝不动**
  （静止 0.0045 → 运动中 0.0044）→ 判据报"**电机没转**"。
  **差一点据此写下"板子根本没驱动电机"的结论。**
- **原因**：D-020 那次是**在地上**测的，"电机在转"的信号在 **`gyro_z`（偏航）** 上
  （振动经**地面**耦合上来）。而这次车是**悬空**的 —— 轮子一转产生**反作用力矩**，
  机身**前后俯仰** → 信号跑到 **`gyro_x`（俯仰）** 上去了。
  实测：`gyro_x` **0.0106 → 0.0751（7 倍）**，而 `gyro_z` 几乎不动。
- **教训**：**"上次这个量的读数在哪"不等于"这次它还在那儿"。**
  判据要绑在**物理机制**上（"轮子转 → 反作用力矩 → 机身俯仰"），
  而不是绑在"上次我读的是哪一栏"。换个工况先问一句：
  **这次它该走哪条路？**
  （与坑 15 同源：**观测手段本身要先被观测**。）

### 坑 21：同一个传感器，**能回答的问题是有边界的** —— IMU 说得出"在动"，说不出"停了"

- **现象**：【3】里 Motor Driver 锁存停车后，IMU 跨度反而从 **0.0496 涨到 0.0635**
  → 判据报"锁存后电机没停"。
- **原因**：悬空时 IMU 测的是**机身晃动**，不是电机振动。运动激起的摆动
  在电机停了之后**还会继续荡**一两秒 —— 所以"跨度没降"完全正常，**与被测对象无关**。
- **怎么修的**：判"停"改用**轮速指令归零**（"还在不在施加力矩"的直接答案）；
  IMU 跨度只用来回答"有没有力矩在作用"。两条判据各管一个问题。
- **教训**：**换判据之前先问"这个问题该由哪个量来回答"。**
  拿一个灵敏的传感器去回答一个它不擅长的问题，得到的是
  **一个看起来很硬的错答案** —— 比"没有读数"危险得多。

### 坑 23：`/cmd_vel` 上**没有仲裁** —— 「我有独立通道」不等于「我的通道会赢」

- **现象**（2026-10-07，做避障时读代码发现，**不是在测试里发现的**）：
  `/cmd_vel` 上有**两个并列发布者** —— Motor Driver 以 **20 Hz** 持续发布它算出来的速度
  （`motor_driver.py:159`），Safety Runtime 锁存期间以 **10 Hz** 发零（`safety_runtime.py`）。
  厂商 `odom_publisher` 是"**收到一条就转一条**"，没有优先级、没有超时、没有仲裁。
- **推论**：两边同时发的时候，底盘收到的是 `0.2 / 0 / 0.2 / 0 …` **交替**的指令 ——
  那是**抖着走**，不是停车。
- **那么现在的急停为什么有效？** 因为 `_trigger` 里还有一次 best-effort 的
  `/motor_driver/stop`，**让 Motor Driver 自己**锁存发零。于是两边都在发零，才真停下来。
  ⇒ 真正停车的是**下游锁存**；本节点那条"独立零速通道"是**Motor Driver 已经死了**时的后备。
- **最要命的一点**：这两条路的分工**从来没被测过**。D-027 的验收是
  **刻意在 Motor Driver 不跑的情况下做的**（为了证明"零速通道独立"）——
  而那恰好是"零速通道确实足够"的**唯一**情形。**Motor Driver 活着、并且正被命令运动**那一档，
  是空白。
- **教训**：**"我发了零"和"零说了算"是两件事。** 判据不是"我发出去了"，
  而是"**对方也在发的时候，谁的话算数**"。
- **对本次设计的直接影响**：避障停车因此选**锁存**（复用下游 `stop` 这条已被验证的路），
  而不是"只发零、等车自己停"—— 后者在当前架构下不可靠。
- **2026-10-07 实测（`tools/cmd_vel_arbitration_probe.py`）—— 上面这条已经从推断变成读数。**
  手法：Motor Driver 保持 `dry_run=true`，把 Safety 的零速通道**也指到那条干跑话题**
  （`zero_channel_topic:=/embodied/motor/cmd_vel_dryrun`），两路发布者就被放进**同一条话题**、
  交替关系完整复现，而**真的 `/cmd_vel` 上发布者数 = 0**（工装自己先断言这一点，
  不是 0 就拒测 —— 这是"本工装不可能驱动底盘"的依据）。然后照常 20 Hz 命令 0.15 m/s、调 `~/estop`：

  | 工况 | 锁存前 | **锁存后** | Motor Driver 侧 |
  |---|---|---|---|
  | **A：下游 `stop` 能调通**（现状） | 61 帧，**100% 非零** | **121 帧，非零 0%** | 锁存 = True，状态码 3(stopped) |
  | **B：下游 `stop` 调不通**（还活着、还在转发） | 61 帧，**100% 非零** | **121 帧，非零 66%**；后半段仍 66%（**不衰减**） | 锁存 = **False**，状态码 0(ok) |

  **66% 正是速率比 `20/(20+10) = 2/3`** —— 与从代码推出来的完全一致。
  ⇒ B 档下底盘收到的是 **0.15 m/s 三分之二的时间**，那就是**抖着走**。
  而且**不衰减**：只要那个 `stop` 调不通，它就一直这样，不会"慢慢停下来"。
  ⇒ **现有急停的成立与否，完全押在"下游 `stop` 调得通"这一件事上**；
  而代码里对它只有 `service_is_ready()` 一次检查 + 一条 WARN，之后**没有任何补偿**。
- **2026-10-07 当天就修了（D-037）：把否决权从「咨询性」改成「结构性」。**
  Motor Driver **直接订阅** `/embodied/safety/status`，安全层锁存期间它**自己**输出零 ——
  否决不再依赖"谁先谁后"，**也不依赖任何服务调用是否成功**。
  改完用同一个工装、同一档（下游 `stop` **故意调不通**）复测：
  **锁存后从 66% 非零 → 0%（121 帧全零）**，Motor Driver 状态码报 **5 = `safety_blocked`**、
  **锁存标志是 False** —— 说明拦住它的确实是**读到的状态**，而不是那次调不通的调用。
  > **这一格（66% → 0%）就是修复的证据。** 工装的两档现在都必须是 0%；
  > 哪一档不是 0%，就说明否决权又退回去了。

### 坑 24：`sector_min_range` 把「扫描陈旧」和「扇区真的空」返回成**同一个值**

- **现象**：想用 LiDAR 原语判"这个方向有没有东西"，核对它的两种失败/正常态：

  | 情况 | `valid` | `range` | `angle` | `points` |
  |---|---|---|---|---|
  | 扫描**陈旧/从没收到** | `False` | `-1.0` | `0.0` | `0` |
  | 扫描**新鲜**、扇区内**没有回波** | `False` | `-1.0` | `0.0` | `0` |

  **逐字段完全相同**（`lidar_driver.py:95-108` 与 `scan_query.py`）。
- **后果（严重）**：直接拿它判"前面没东西"，就会在**传感器挂了**的时候
  告诉上层"路是通的" —— 正是 D-028 那条「**不知道 ≠ 安全**」要防的错误。
  原语在 `path_clear` 上把这两种情况分得很开（陈旧 `clear=false` / 新鲜空 `clear=true`），
  偏偏 `sector_min_range` 上分不开。
- **怎么修的**：新鲜度**不由被监视的答案自己声明**，另取一路**心跳** ——
  订阅原语每收到一帧扫描就发的 `/embodied/lidar/front`，**只看到达时刻，不看内容**。
- **教训**：接口"返回得看起来像那么回事"是不够的。**"这两种情况必须能被区分"
  本身要当成接口要求**；区分不了，调用方就只能猜，而安全层的"猜"等于错。

### 坑 25：「我还没看」≠「我看不见」 —— 又一次栽在"没有数据"上

- **现象**（2026-10-07，真雷达第一次验证避障）：喂一条 0.03 m/s 的假速度，
  守卫报 **`obstacle:unknown_scan`** 锁存。而雷达好好的、前方 0.154 m **确实有东西**。
  ⇒ **结论碰巧是对的，理由是错的。**
- **原因**：判定要求"回答新鲜"，而回答只能**问**出来。代码在**同一拍里**发问并判定，
  `_reply` 还是 `None` → 被当成"不知道" → 立刻锁存。
  ⇒ **每一段运动的头一拍都会这样**（从静止起步时尤其明显）。
- **怎么修的**：加一条**有界宽限** —— `_reply is None` 且"开始问"至今不超过一个
  回答超时（0.5 s）时，视为「**还没看**」，不判停；超时后仍无回答，才照「不知道」停。
- **为什么宽限是安全的**：它只覆盖"刚问出去"的那 <0.5 s，且此时车刚从静止起步
  （最坏走出 10 cm）；而"原语根本不答"的情况在 0.5 s 后照样停。
- **教训**：这与**坑 15 是同一条教训的第二次出现**（那次是把"静默期没有数据"
  读成了"这条线不会说话"，已写过更正）。**"没有数据"至少有两种：
  ①还没问 ②问了没答。** 混成一种，就会在最正常的时刻报警。
- **附带一条**：这次"**错理由、对结论**"的巧合值得单独记下来 ——
  如果我只看到"锁存发生了"就收工，会把一个假阳性当成验证通过。

### 坑 26：「静默复动」防的是**潜伏的旧指令**，不是「新指令」

- **现象**（2026-10-07，架空实测结构性否决）：给 Motor Driver 加了"被安全层拦下时若
  底盘可能还在动，恢复后要求显式 `~/resume`"之后，工装报 **"发生了静默复动"** ——
  解除安全层后底盘就动了。**看起来是安全机制失效。**
- **查下来是判据写错了，不是机制坏了**：那个工装用 **Control Skill 当"上层的客户端"**，
  而 Control Skill 被 `~/stop` 中止时会**补发一帧零**（`control_skills.py:266`）。
  于是 Motor Driver 在"被拦下那一刻"看到的 `_cmd` **已经是零** →
  判定"底盘不可能还在动" → **不要求重新使能**（这是自洽的：没有潜伏指令就没有静默复动）。
  工装随后又发了一条**新**命令 —— 新命令被立即执行，**那不是静默复动**。
- **正确的场景是"不会停的客户端"**：一个**不理会任何 stop**、以 20 Hz 一直发同一条
  非零指令的东西（RawPublisher）。换上它之后：拦下 → 只解除安全层 → 底盘**仍然不动**、
  状态报 `rearm_required`；显式 `~/resume` 后才动。**全过。**
- **教训**：验"会不会自己跑起来"时，**客户端必须真的具备"自己会一直发"这个性质**。
  用一个"会被劝停"的客户端去验，测的是另一件事 —— 而且它会**恰好**给出一个
  看起来像失败的读数。
- **顺带一条时序教训**：该工装第一版进【3】段时安全层**还锁着**，客户端从头到尾推不动车，
  "它确实在驱动轮子"这条直接失败。⇒ **先把被测的初始条件真的建立起来，再去验它**
  （与坑 19、坑 22 同族）。

### 坑 22：基线不安静时，工装应当**拒绝出结论**，而不是把阈值调松

- **现象**：一次运行里基线跨度到了 **0.4863**（车在荡，是安静时 0.011 的 **44 倍**），
  于是"比基线 1.5 倍"这个门槛高到**永远达不到** → 整篇都是**假失败**。
- **怎么修的**：基线超过阈值（`QUIET_BASELINE_MAX`）就**直接退出**并提示
  "把车扶稳/挂稳再跑"，退出码 2。
- **教训**：**阈值调松只会把"假失败"换成"假成功"，两种都是坏数据。**
  物理条件不合格时，正确的动作是**拒测**，不是把尺子弯一弯。
  （配套：工装里还加了"**等到状态真的变好再往下走**"——
  之前只发一次 `~/resume` 就假定解锁成功，结果 `stopped` 还没转成 `ok` 就发了运动请求，
  报"链断了"，而其实只是**锁还没解开**。）

### 坑 27：验收工装的一个常量**同时兼了两端**，中间长出一段"工装说该拦、被测物看不见"的死区

- **现象**：`safety_chain_suspended_acceptance.py --phase direction` 要拿"通畅方向必须放行"
  和"受阻方向必须拦下"做对照。它只有一个常量 `CLEAR_MARGIN = 0.40`，**两端共用**：

  ```python
  clear   = [p for p in probed if p[3] > CLEAR_MARGIN]        # 通畅
  blocked = [p for p in probed if 0 < p[3] <= CLEAR_MARGIN]   # 受阻 ← 这里错
  ```

- **为什么错**：守卫（`obstacle_guard.py`）真实算的是
  `stop_range = min(max_range, max(min_range, 速度 × lookahead))`，
  0.15 m/s 下 = **0.225 m**；而且它是**带着 `max_range = stop_range` 去问服务**的 ——
  比它远的回波**根本不返回**，`scan_valid=False`，**不会拦**。
  于是 `(0.225, 0.40]` 这一段成了死区：工装判它"受阻、守卫该拦"，
  守卫却连看都看不见 → 把障碍物放在 **0.30 m** 就会**假失败**。
  而 0.40 本来是给"通畅"那端留的余量（≈ 真实阈值的 1.8 倍），
  **它和"受阻"的上界在物理上根本不是同一个量**。
- **怎么修的**：把"受阻"的上界改回守卫的真实阈值并与之**同源**（三个参数从守卫的默认值
  写在一处算出来，注释里指名道姓说清来源），`CLEAR_MARGIN` **只用于"通畅"这一端**。
  同时把"1 m 内无回波"（读数 −1）判成**通畅** —— 之前它两头都不算，被静默忽略。
  另外加了 `--dry-classify`：**只量摆位、不发任何运动**，摆位不合格直接说清缺哪一边。
- **附带的一条**：原来"没有受阻方向就跳过对照继续跑"也一并改成**拒测**。
  只验"放行"不验"拦下"，等于把"守卫是不是一刀切"放过去了 ——
  而那一刀切正是 D-036 要防的东西（**什么都拦的守卫会被关掉，等于没有**）。
- **教训**：**写"应该发生什么"的判据时，那个数必须是被测物自己用的那个数。**
  凡是被测物手里已经有一个阈值，"该不该触发"就不能另拍一个数 ——
  两个数只要不相等，中间就有一带**既测不出真失败、也测不出真通过**的死区。
  （与坑 19「我没在看 vs 系统没动」同族：**判据与被测物理量脱节**。）

### 坑 28：守卫拿**上一个方向**的读数，去判**这一个方向** —— "有一个别人问题的答案"

- **现象**（2026-10-08，真机、地面、`--phase direction`）：

  ```text
  【2】往受阻的「前」走 → 守卫拦下，obstacle:0.20m@+0deg        ✅ 对
  【3】往通畅的「左」走 → 守卫**又**拦， obstacle:0.15m@+90deg
                          而同一时刻用同一个原语量「左」是 0.83 m
  ```

  那个 **0.15 m 是前面那个物体的距离**，被当成了**左方扇区**的读数。
- **根因**：守卫每拍按当前运动方向发 `sector_min_range`，但**只存回答、不存"这是问哪个方向得到的"**，
  判定时拿「上一次的回答」配「当前的方向」。回答在 `obstacle_reply_timeout = 0.5 s` 内都算"新鲜"，
  **方向对不对完全不管**。
- **和坑 25 的区别**（很重要，别混）：坑 25 是"**压根没有回答**"（`_reply is None`），
  用一条有界宽限解决了；这里是"**有一个别人问题的答案**" —— 宽限那条路**根本没被走到**，
  因为 `_reply is not None`，看起来一切正常。**"有数据"比"没有数据"更难发现是错的。**
- **怎么修的**（**D-039**）：回答**和问题配对**才作数（方向要在 5° 内；说"没看见"时，
  问的范围还得盖住当前阈值 —— "0.20 m 内没有东西"不能担保 0.225 m 的阈值）；
  配不上的**丢掉重问**，走既有的有界宽限。判定规则放纯函数里，6 项单测，含一个用真机读数做的回归。
- **教训**：**缓存的每一条读数，都要连着"它是关于什么问题的"一起存。**
  只存答案不存问题，任何一次"问题的参数变了"都会静默地用错数据 ——
  而且因为缓存非空，所有的"没有数据"防线**一条都不会响**。

### 坑 29：阈值**从雷达算**，可撞上去的是**车头** —— 量的是 A，保护的却是 B

- **现象**：地面验收里，守卫按 0.225 m 的阈值正确拦下，**车却把 0.20 m 外的瓶子撞倒推走了**。
- **量出来的数**（从 `base_link_mec.stl` 的包围盒算）：车长 **0.2755 m**、
  雷达在 `base_link` 前方 0.011 m ⇒ **车体最前端在雷达前方 13.1 cm**。
  于是 0.225 m 的阈值，**留给车头的实际余量只有 9.4 cm** ——
  而"从下令到守卫锁存"这一段的蠕动（实测 **2.2 cm**：瓶子 0.191 → 0.169 m）还要从里面再扣。
  把障碍物放在 0.200 m，车头离它只有 **6.9 cm** ⇒ 撞上是必然。
- **含义**：当前 `obstacle_min_range = 0.20 m`（**从雷达算**）**护不住车体自己** ——
  它只比车头伸出量（0.131 m）大一点点。标定阈值时必须把**车体前伸量**算进去，
  而不是只算刹车距离。这条是 D-028 那句"避障阈值必须按部署环境实测标定"的**具体输入**。
- **教训**：**先问清"这个数是从哪儿量起的"，再问"它够不够大"。**
  传感器装着的位置和要保护的东西的位置，往往不是同一个地方 ——
  这种错不会报错，只会让"看起来有 22 cm 余量"变成"其实是 9 cm"。

### 坑 30：独立基准的**几何**没对齐，量出来的"位移"是错的（±30° vs ±10°）

- **现象**：地面验收里闭环技能自报 `travelled = 0.500 m`，我那边的独立基准读出 **0.381 m** ——
  差 **24%**，看着像"技能的计账在撒谎"。
- **真因**：我用的是**守卫那套几何（±30°）**去量位移。而这个房间里 ±30° 内有**两个不同深度的面**
  （正对面 1.48 m、偏左 −18° 一块 1.30 m）。**车一动，最近的回波就从一块面跳到另一块面上**，
  Δ距离于是不再是位移。
  改成 **±10°**（盯住正对面那一段）之后，同一段运动读出 **0.2000 m vs 自报 0.2000 m**，**逐位吻合**。
- **怎么发现的**：单段 0.5 m 走整条链只差 **−3%** —— 如果技能真的短走 24%，
  长段也该短走。**两段对照**把"是技能错了"排掉，剩下的只能是"是我量错了"。
- **教训**：**"独立基准"要独立的不只是数据来源，还有几何。**
  传感器的扇区一旦宽到能看见两个不同的东西，那个读数就不再有单一的物理含义 ——
  它会**静默地**在两块面之间跳，而每一帧看起来都完全正常。
  （与坑 29 同族：**先问清"这个数是从哪儿量起的"，再问"它够不够大"。**）

### 坑 31：**不重试就下结论** —— 同一天在同一个工装里栽了两次

- **现象 A**：工装运行时 `~/resume` 报"已完成"，但底盘状态还是 3（`stopped`）→ 拒测。
  真因：那次 `~/resume` 是在 **服务还没被发现**时发出去的，`service_is_ready()` 为假 ⇒
  `call()` 直接返回 `None`，**被静默丢掉**。
- **现象 B**：参照物检查报"正前方没有回波"立刻拒测，30 秒后同一个量又正常了。
- **怎么修的**：底盘恢复改成**循环重试直到状态真的变对**；参照物给**几秒窗口**再决定拒测。
- **教训**：**"我发过了"不等于"它生效了"。**
  异步接口的**返回**才是事实，发出动作只是请求。凡是"发一次然后假定成功"的地方，
  都该问一句：**这个动作有没有一个可观测的结果？我看了吗？**
  （与坑 22「拒测而不是调松阈值」同族：**先确认条件真的建立了，再往下走。**）

### 坑 32：判据里少了「**接下来要动多远**」这一项 —— 抬高阈值之后它才露出来

- **现象**：把避障阈值从 0.225 抬到 0.30、准备重跑方向性验收时，摆位分类**通过了**
  （「右」0.478 m 被算作"通畅"），可我心里一算发现不对：**【3】要往那儿真的开 0.3 m**，
  开完只剩 0.178 m —— **低于阈值**，守卫会在半路锁存，于是【3】**假失败**。
- **真因**：原判据是"通畅 = 读数 > 1.5 × 阈值"。**它只问"现在通不通"，没问"走过之后还通不通"。**
  阈值低的时候这个缺口被余量盖住了，阈值一抬就露出来。
- **怎么修的**：改成由物理量直接导出 ——
  `通畅门槛 = 阈值 + 本工装要走的距离(WALK) + 小余量`
  （0.30 + 0.30 + 0.10 = 0.70）。**阈值一改它自动跟着走**，不用再靠人记得同步。
- **教训**：**判据要按"整段做完之后还成不成立"来写，不是"开始那一刻成不成立"。**
  凡是"发一条指令、然后看结果"的验收，判据里的每个门槛都得问一句：
  **这条指令自己会改变被它检验的那个量吗？**（与坑 27/31 同族：判据与事实脱节。）

### 坑 33：厂商环形麦的**硬件唤醒上报不可用** —— 而且"响了两下"会让人以为它只是不稳定

- **背景**：`#25` 悬了很久「唤醒不通」。2026-10-07 已经查明**不是硬件坏**，
  是**跑错了节点**（模块说 `aa55` 那套，`awake_node` 只认 `a5 01 04` + JSON）。
  于是 2026-10-08 的这次本以为是"换个解码器就好"。
- **实测（独占串口，逐个排掉）**：

  | 测试 | 结果 |
  |---|---|
  | 独占 `/dev/ring_mic` 后对着它说话（最早一次） | **2 帧** `aa550300fb`，之后 3.5 分钟归零 |
  | 唤醒词说 5 遍（带停顿） | **0 字节 / 210 秒** |
  | 握手包 × 4 种 (RTS, DTR) | **0 字节** |
  | **拔插 USB 断电重启后再试**（唤醒词 ×3） | **0 字节** |

- **结论**：**采集通路可用（D-022 验过录音/播放），上报通路不可用**。
  那条"2 帧"最害人 —— 它让人相信"硬件是好的，只是不稳"，于是继续在上面花时间。
  **2 帧之后彻底归零，且断电重启不复现**，这是"不能用"，不是"不稳定"。
- **教训**：**"偶尔能工作"和"能工作"是两回事，而在验收里前者更容易骗人。**
  判据应当是"连做 N 次成功几次"，而不是"至少成功过一次"。

### 坑 34：把"我没检出"读成"它聋了" —— 又一次在没有独立真值时下结论

- **现象**：KWS 在录音上检出 11 次，全部集中在 **25.5–51.5 s**，之后到 76 s 一次都没有。
  我当场的判断是"**跑一阵子就聋了**"，并去查了 `reset_stream` 的语义、试了"每隔几秒换一条新流"。
- **真因**：**用户就是在 51.5 s 停止说唤醒词的。** 后面 54 s 起是那 3 句不相干的话。
  器件没聋，是**我把"检测窗口的末端"当成了"系统的失效点"**。
- **怎么查出来的**：**用 ASR 把整段录音转录出来**，拿到"每一秒到底说了什么"这个**独立真值**：

  ```text
  [22.0s → 51.5s]  小坏小坏小坏…小坏小坏     ← 连说约 27 遍
  [54s  → 59s]     今天天气不错 / 打开灯 / 往前走
  ```

  换新流的实验（10 → 9 → 6 → 6）本来就是这个假前提下的徒劳 —— **它没有变好，
  但也不是证据**，因为前提是错的。
- **顺带拿到两个真数**：**召回 13/27 = 48%**、**误报 0**。
  而在"单流 / 每 10 s 换流"之间来回试的那几步，**没有一步能替代真值**。
- **教训**：**"它什么时候不响了"必须配一个"我什么时候没喊"才能成为结论。**
  没有独立真值时，"检测到的时刻表"怎么解释都行 —— 而这正是这个项目反复栽的那一类
  （坑 19「我没在看 vs 系统没动」、坑 30「基准的几何没对齐」）。

### 坑 35：推进结果里**少带一个 id**，计划就"判出来了、却不动"

- **现象**（真机端到端第一次跑多步计划）：日志明明打出了
  `计划继续：第 2/3 步报 BLOCKED ⇒ 继续下一步｜下一步 第 3 步`，
  **而第 3 步永远没有发生** —— 没有报错，没有任何异常，
  计划就那么停在"还剩一步"的状态里。
- **真因**：事件里带的是**网关任务号**（第 2 步是 `000002-…`），而调用方要按
  **计划 id**（`000001-…`）去取计划记录。`on_event` 顺手把 `msg.task_id` 当计划 id 用了，
  于是 `get(plan_id)` 返回 `None`，`_dispatch_next` **静默返回**。
- **为什么会静默**：`_dispatch_next` 开头就是 `rec = get(plan_id); if rec is None: return`。
  查不到 = "这个计划不在我这儿" —— 对**别人的**事件这是对的（事件话题是共享的），
  但对**自己计划的下一步**，那就是把"我找不到"当成了"不关我的事"。
- **怎么修的**：让推进结果 `Outcome` **自己带出 `plan_id`** ——
  "这个结论是关于哪个计划的"本来就是这个结论的一部分，
  让调用方从别处去凑，就是逼它猜。
- **教训**：**凡是"这里有个 A 的 id、那里有个 B 的 id"的地方，都要问一句
  "它们什么时候会不同"。** 单步时它们恰好相同（计划 id 就是第 1 步的任务号），
  所以**单步测试永远发现不了它** —— 只有跑到第 2 步才露出来。
  （与坑 30「基准的几何没对齐」同族：**两个东西看着一样，是因为还没走到不一样的那一步。**）

### 坑 36：`pkill -x` 杀不掉 —— `comm` 只存 **15 个字符**

- **现象**：调多步计划时反复出现「正有一个动作在执行，拒绝新请求」，
  而我明明每次都重新起过栈。查下去发现**同时有三个 `autonomous_skills` 实例在跑**，
  互相抢"一次只跑一个动作"的标志位。
- **为什么没杀干净**：`pkill -x autonomous_skills` **匹配不到** ——
  内核的 `comm` 字段只存 **15 个字符**，进程名被截成 `autonomous_skil`。
  于是它看起来"杀过了、也复查过没残留"，而实际上一个都没死。
- **怎么发现**：不靠 `pgrep`，直接 `ps -eo pid,comm,args` 看**完整命令行**。
- **教训**：**"我杀过了"要用一个不会撒谎的检查来确认** ——
  按 `comm` 精确匹配时，**长名字会被静默截断**，命令跑成功、结果没生效。
  （与坑 2「`pkill -f` 会匹配到自己的 shell」是同一个工具的两个不同陷阱：
  一个是**多杀**，一个是**少杀**，而两者都表现为"我以为收拾干净了"。）

## 5. 小结：这个项目里反复出现的三条

1. **自证不算证据。** 里程计不能证明底盘转了，相机的时间戳不能证明图像新旧。
   要给每一个「被测对象」配一个**独立的**基准。
2. **违反守恒的读数先查环境，别查被测物。** 输出比输入快、录音突然削顶，
   大概率是自己的工装出了问题。
3. **怀疑要能撤回，坑要写下来。** 撤回比提出更需要写进文档。
